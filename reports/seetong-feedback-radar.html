代码定位

  • 涉及模块：Seetong5.0_ios/Seetong_tps/KMP/Router/KMPRouter.m、KMP/View/KMPCloudPlaybackVideoView.m、KMP/View/KMPPlayBackVideoView.m、Classes/TPS/View/IjkPlayerVideoView/IjkPlayerVideoView.m。
  • KMPRouter.m:299-317：PlayBackPage 每次都新建 STKuiklyRenderViewController 并直接入栈，入口没有按 devId + alarmTime + 当前页面 做单飞或重复点击门禁。短时间重复打开时会叠加 KMP 页面、IJK 状态机和视频资源。
  • KMPCloudPlaybackVideoView.m:544-578：playVideo 每轮都会重建播放器并登记请求序号，但页面本身的推栈尚未建立幂等保护；页面多发并不意味着播放器状态能安全并发收敛。
  • KMPCloudPlaybackVideoView.m:57、:490-505：解析完成后固定等待 1.2 秒，即使首帧仍未到达也调用 kmp_resolvePendingPlayCallback:YES。这会让业务层误以为播放已成功，页面可能仍卡在不可交互或无画面的状态。
  • IjkPlayerVideoView.m:722-749：IJKMPMovieFinishReasonPlaybackError 与 IJKMPMovieFinishReasonPlaybackEnded 进入同一结束回调；上层 KMPCloudPlaybackVideoView.m:862-896 随后使用同一完成事件，业务层无法区分正常结束、解码失败和播放错误。
  • KMPCloudPlaybackVideoView.m:684-722：releasePlay 与 unbindView 在主线程同步执行停止、清理过渡帧、取消回调和停止 IJK。正常路径可以完成，但缺少各阶段耗时与超时观测，无法判断哪一段在“点不动”时占用主线程。
  • 当前 feature_v8.4.2_lan 分支 HEAD 44ef9c45e 仍保留 1.2 秒成功兜底及错误／正常结束合流；近期提交没有针对本次“页面交互卡死”完成修复。主要代码责任人可定位到欧阳荣与谭伟。

根因结论

  • 置信度：🟡 中。两名用户的现象独立重复，代码存在明确的状态机缺口，但目前只有一条反馈有可读现场，且日志未捕获主线程阻塞或崩溃栈。
  • 一句话根因：iOS KMP 回放链路没有把“页面入口幂等、首帧确认、错误终态、资源释放”统一成唯一状态机；解析后无首帧仍可被标记成功、错误可被当成正常结束，重复进入还会叠加页面与播放器实例，最终表现为 loading 结束但页面仍不可操作或卡死。
  • 关键证据链：两名不同系统版本和地区的 iOS 8.4.1.6 用户均描述回放页点不动 → 259584 日志证明 KMP 页面可进入且曾成功出帧，但短时间连续创建 3 次并出现解码参数不一致 → 源码直证 1.2 秒无首帧可回报成功、错误与结束共用事件、路由无重复打开保护 → 友盟未记录同版本卡顿或崩溃尖峰，进一步说明需要客户端内部可观测性而不是只看 APM。
  • 明确不下的结论：不能据此认定所有 iOS 回放都会卡死，不能把 47% 的云回放非 200 业务码直接当作真实失败率，也不能把 259584 的进程切换认定为系统崩溃或用户主动重启。

建议下一步

  • 分配给：欧阳荣负责 iOS KMP 回放状态机与路由门禁，谭伟复核 IJK 错误透传和资源释放；沿用任务 T-20261020-090554-09c5，状态保持 P1 / captured。
  • 优先修复：PlayBackPage 以 devId + alarmTime + playbackMode 做入口单飞，页面存在或正在创建时复用现有实例；loading 只能在首帧、明确失败或最终超时三者之一结束时关闭，禁止 prepared_fallback 返回成功。
  • 错误分层：把 IJK 的 PlaybackError、正常结束、页面离场和用户停止拆成互斥事件，并透传 devId、请求序号、片段 URL、解码宽高、已播放时长、错误码和重试次数。
  • 响应性观测：记录 openPlaybackPage 推栈耗时、prepareVideo、playVideo、首帧、解绑、停止和页面离场耗时；主线程连续阻塞超过 500 ms 时上报专用 watchdog 事件，避免下一次仍只能依赖用户文字反馈。
