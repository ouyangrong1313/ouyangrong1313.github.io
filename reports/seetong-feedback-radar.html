4. 代码定位（详细）

涉及仓：~/seetong-app-harmony（宿主 UI 与桥接）+ ~/seetong-kmp（摇杆组件）。

  • 入口 A（界面已显式支持的方向控制）：PtzControlView
  • moduleBase/src/commonMain/kotlin/com/seetong/base/view/PtzControlView.kt:145-166：把触点按三等分区域映射成 up/down/left/right，抬指走 handleTouchEnd()。
  • 同类 :169-171：handleTouchEnd() 把 currentCmd 清空、摇杆回中，并 event.directionHandler?.invoke("stop")。
  • 也就是说，方向和停止语义在 KMP 组件里是完整的，问题不在摇杆本身。
  • 入口 B（横屏电子变倍按钮）：FullElectronicZoom
  • feater/playDevice/src/main/ets/view/videoPreview/comp/FullComp.ets:192-201 setZoom(value, isLong)：
  • isLong=false → 直接 ToastUtil.showToast('长按后触发') 并 return，单击变倍被设计成不可用；
  • 只有 value != PTZ_CMD.PTZ_STOP 才震动；
  • 末行无条件下发 this.devService?.setElectronicZoom(this.devId, value)。
  • :215-219 与 :230-234：放大/缩小两个按钮各自是 GestureGroup(Exclusive, TapGesture, LongPressGesture{repeat:false,duration:200})，onAction 下发 zoomtele/zoomwide，onActionEnd 下发 PTZ_STOP。
  • :185-189 capacityChange()：isSupport 只由 DeviceUtils.isSupportDigitalZoom(this.capacity) 决定，而 :243 的 .visibility() 依赖 isSupport——能力判定不通过就整组按钮不显示。
  • 关键缺陷 1：stop 指令永远下发不出去
  • feater/playDevice/src/main/ets/service/DeviceServiceImpl.ets:2115-2130 setElectronicZoom(devId, cmd)：
"<cmd>" + cmd + "</cmd>" + "<duration>3000</duration>" + "<panspeed>5</panspeed>" + "<tiltspeed>5</tiltspeed>"

cmd 被原样拼进 <cmd>，而形参类型是 PTZ_CMD，合法值包含 PTZ_STOP = "stop"、PTZ_ZOOM_TELE = "zoomtele"、PTZ_ZOOM_WIDE = "zoomwide"。

  • 松手时传进来的 "stop" 会变成 <cmd>stop</cmd>，而这条 XML 依然带着 <duration>3000</duration>——即使设备端认可 stop，也会被组件自身的 3 秒持续语义与 setTimeout(resolve,1000) 掩盖；
  • 更关键的是 setElectronicZoom 没有任何 checkIsSupportPTZ 或指令白名单校验，directionHandler 传入空串时同样会拼出 <cmd></cmd> 下发。
  • 后果两种，取决于设备固件如何处理 stop：能识别 → 恰好停止；不能识别 → 忽略未知 cmd，继续按上一个 duration=3000 匀速变倍直到设备端超时。用户感知就是「松手了还在变倍」或「一变就失控」。
  • 对照 :1940-2017 的其它云台方法：setLinkagePosition / setCurrentDigitZoom 都显式拼了合法 cmd 名（setCurPos、x、y、mul），只有 setElectronicZoom 把枚举当字面量直接用，这是实现上的破例。
  • 关键缺陷 2：两套能力判定口径不一致
  • basic/src/main/ets/utils/DeviceUtils.ets:927-933 isSupportDigitalZoom()：要求 ipc_IsSupportPTZ 且 is_iot_ptz_control_bigball（能力位 iot_ptz_232_support）。
  • basic/src/main/ets/utils/DeviceUtils.ets:566-571 is_SupportDigitZoom()：只要求能力位 iot_ptz_dig_scale。
  • feater/playDevice/src/main/ets/view/ViewPage.ets:652-680：页面主链路（capacityChange 里的 zoomModel）用 is_SupportDigitZoom（iot_ptz_dig_scale），横屏按钮用 isSupportDigitalZoom（iot_ptz_232_support）。
  • 结论：同一台设备可能「页面侧认为支持、横屏按钮侧认为不支持」，表现为 261394 所述「不能变倍」（按钮根本不显示），或反过来显示了但 ndk 侧无 232 支持导致指令石沉大海。
  • 关键缺陷 3：能力集取不到时静默降级
  • basic/src/main/ets/utils/DeviceUtils.ets:668-678 ipc_IsSupportPTZ()：capacity 为空或 undefined 时返回 true（乐观放行）。
  • feater/playDevice/src/main/ets/view/ViewPage.ets:620-636：getDeviceCapacity 两条路径都 catch 后返回 ''，只打 =-=获取设备能力集报错，不重试、不提示。
  • 叠加后：鸿蒙 6/7 上若能力集拉取失败 → 按钮按「支持」显示（因为 ipc_IsSupportPTZ('')=true）但 isSupportDigitalZoom('') 在 :928 直接 return false，两者矛盾时按钮隐藏；若能力集「拉到了但缺 iot_ptz_232_support」→ 按钮同样隐藏。用户看不到入口，也拿不到任何解释——与 261394 的措辞完全吻合。
  • 修复方向锚点：
  1. DeviceServiceImpl.ets:2115 增加 cmd 白名单 + 区分「启动变倍」与「停止变倍」两条分支；停止必须走不带 duration 的短指令或专用停止命令。
  2. FullComp.ets:192-201 的 setZoom 里，PTZ_STOP 必须是独立分支（不受 isLong 拦截），且 onActionEnd 无论长按是否成立都要尝试停止，避免手势被打断后指令悬挂。
  3. FullComp.ets:185-189 与 ViewPage.ets:652 统一到同一能力判定函数（建议以 iot_ptz_dig_scale 为准，iot_ptz_232_support 只作增强），并把空能力集的乐观放行改为「隐藏入口 + 可重试」。
  4. ViewPage.ets:620-636 能力集失败补一次重试与超时后置文案，禁止静默返回空串。

5. 根因结论

  • 置信度：🟡 中（代码链路证据清晰，但缺运行时日志与神策分母）
  • 一句话根因：横屏电子变倍把平台枚举 PTZ_CMD 当字面量拼进 <cmd>，导致 stop 与空指令都变成非法命令；同时横屏按钮与页面主链路使用两套不一致的能力位判定，使部分鸿蒙 6/7 机型要么看不到入口、要么下发后不停止。
  • 关键证据链：261394 原话「鸿蒙 6 和 7 下不能变倍」→ FullElectronicZoom 的能力判定只认 iot_ptz_232_support，比页面主链路窄 → 按钮被 visibility 隐藏 → 用户认为「功能没了」；261308「云台转不动」→ doCommand 走 ipc_IsSupportPTZ 乐观放行 + SDK 下发，若指令非法则设备静默丢弃 → 表现为无反应。两条链路都指向「指令与能力判定不严谨」，而非网络或权限。
  • 明确不下的结论：不判定为「鸿蒙 6/7 系统 API 兼容性故障」——目前没有一条日志能证明是 setElectronicZoom 被系统拦截；也不把 1.1.2.3 与 8.4.2.4 合并为一个版本缺陷。

  1. 落实「修复方向锚点 1、2」——停止指令必须可下发、必须区别于启动指令；
  2. 统一能力判定口径，并让能力集失败可见、可重试。

2. 神策证据（核心数据源）

  • 客户端确实预留了「设备时间异常」的观测口径，但它在结构上不可能为真：
  • PreviewSessionSummaryEvent.checkTimeAbnormal()（lib_base/src/main/java/com/seetong/lib_base/utils/sensors/PreviewSessionSummaryEvent.kt:540-550）的判定逻辑是：
if (bean.enterPreviewTimestampMs <= 0L || currentTimeMs >= bean.enterPreviewTimestampMs) return

currentTimeMs 来自 :234 的 System.currentTimeMillis()，而 enterPreviewTimestampMs 是同一台手机在进入预览时记录的毫秒时间戳——正常时序下 currentTimeMs 永远大于等于它，所以第一行就直接 return，timeAbnormalFlag 恒为 false。

  • 更要紧的是：这里传入的是手机系统时间，全程没有任何设备 OSD 时间输入。也就是说，即便逻辑写对，它检测的是「手机时间倒流」，根本不检测设备画面时间。
  • 当日既有日志佐证该字段恒定为假：反馈 261415 的 PreviewSession save 快照里 "timeAbnormalFlag":false,"timeAbnormalGapMs":0，且温度检查同样发生在 onAction（即用户点击）时——不点击就没有任何采样。
  • 因此神策侧没有可用的「画面时间异常率」，本节明确标注该指标当前不可信，不能用 time_abnormal_flag 证明「时间异常很少」。

4. 代码定位（详细）

涉及仓：~/Seetong-App-Android/Seetong5.0ForSeetong/Seetong5.0。

  • 时间语义来源：OSD 时间由设备侧叠加，客户端只负责透传画面。因此「画面日期不对」只有三条可能：①设备时钟漂移；②下发了错误的时区/夏令时；③下发了错误的时间。
  • 缺陷 1：云同步模式下仍强行覆盖设备时间
  • app/src/main/java/com/seetong/app/seetong/ui/TimeZoneUI.java:317-357 saveData()：
  • :328-332 按下拉项设置 TimeMode：位置 0 → "MANUAL"，否则 → "SEETONG"（云时间同步）；
  • :340 无条件下发 SetDevConfig(m_dev, CMD_SET_SYSTEM_TIME_CONFIG, xml)；
  • :347-352 无论 TimeMode 是哪一个，都继续构造 SimpleDateFormat("yyyyMMdd HH:mm:ss")，把 m_time 拼成
<REQUEST_PARAM Time="…" TimeZone="tz" />

并下发 SET_SYSTEM_TIME（1005）。

  • 对照 :465-469 refreshTimeTableRow()：「如果为 Seetong 云时间同步方式，不能对时间进行修改」——UI 已经明确告诉用户云同步模式下时间不可改，代码却仍然把本地算出来的时间强制写进设备。这是口径与行为直接矛盾的一处。
  • 而 m_time 来自 :244-255 getLocalTime()，其中注释自述「其实这里不用减，直接设置 SimpleDateFormat 的时区为选择的时区…就好了」，实现上还保留了一段 (c - p + z) 的补偿运算。当设备时区与手机时区不一致（如设备在中国、手机在海外，或夏令时切换）时，这段补偿会把偏差直接写进设备。
  • 缺陷 2：不存在自动校时路径
  • 全仓检索 SET_SYSTEM_TIME 只有两处调用：TimeZoneUI.java:351（用户手动保存时区页）与 WifiEtcUI_STEP4.java（配网最后一步）。冷启动、首次连上设备、每天定时都，没有任何自动校时。
  • 结论：设备一旦漂移（断电久置、无 NTP、更换电池），App 端不会自愈，只能靠用户自己找到「设备设置 → 时区」再保存一次——而这正是 261383 这种用户不会做的事。
  • 缺陷 3：埋点检测器结构错误（已在第 2 节说明）
  • PreviewSessionSummaryEvent.kt:540-550 比较方向写反且无设备时间输入；:229-236 只在 onAction 采样。
  • 叠加后果：线上「画面时间异常」既没有修复路径，也没有观测口径，两头都空。
  • 修复方向锚点：
  1. TimeZoneUI.java:340-352：TimeMode == "SEETONG" 时禁止下发 1005，只下发时区/夏令时配置；MANUAL 时才允许写时间，且写入值必须以「设备当前时区」解释，不再叠加 (c - p + z) 补偿。
  2. 新增自动校时：设备上线/唤醒后读取设备时间（GET_TIME_PARAMETER，1048），与手机时间比对，差值超过阈值（建议 60 秒）时按当前 TimeMode 提示或自动校正；注意 SiotDevConnectResult 每设备只埋一次，不能拿它当触发源。
  3. PreviewSessionSummaryEvent.checkTimeAbnormal：改为「设备 OSD 时间 − 手机时间」，且采样点从 onAction 扩展到首帧到达与退出预览。

5. 根因结论

  • 置信度：🟡 中
  • 一句话根因：客户端在云时间同步模式下仍无条件下发 1005 强行覆盖设备时间，且全链路没有自动校时与设备时间读取，设备时钟一旦漂移就无法自愈；同时埋点检测器既不读设备时间、比较方向也写反，使该问题长期不可观测。
  • 关键证据链：261383 明确反馈「画面日期不对」+ Logan 证明手机时钟正确（握手 timestamp 与日志时间一致）且该会话内无任何校时下发 + 代码证明云同步模式下仍会写时间、平时完全不写 → 偏差只能来自设备自身漂移或被历史错误写入，且不会被修正。
  • 明确不下的结论：不把本次偏差归因为「服务端时间下发错误」——Logan 里没有 1005 的响应包，也拿不到设备侧时间；不与第 262 期「报警推送时间快 60 分钟」合并，两者链路不同。
