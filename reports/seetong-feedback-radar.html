6. 代码定位（详细）

  • 涉及模块：~/seetong-app-harmony（HarmonyOS 端），音频资源集中在 basic 与 feater/playDevice 两个模块。
  • 关键类 / 文件：

  • customSound.ets（feater/playDevice/src/main/ets/setting/customSound.ets）：PlayAudioRenderer 的唯一使用方——报警提示音录制/试听/文字转语音试听。
  • ReplayPage.ets / SdCardRePlayPage.ets / LPDeviceRePlayPage.ets / PlaybackNVR.ets：回放页音频开关，全部走 setReplayVideoAudioEnable → TSNapi.ts_P2PSetNVRReplayAudioEnable（DeviceServiceImpl.ets:934-943），即 SDK 私有通道，不经鸿蒙系统播放器。
  • ViewPage.ets:73 @State monitor: boolean = true、:583-587 setMonitor()、:747-749 checkMonitor()：预览页「监听」开关，走 setVoiceDetect → TsNativeUtils.setVoiceDetect（DeviceServiceImpl.ets:621-628），同样是 SDK 通道。
  • 调用链（本反馈最可能的路径）：ViewPage（预览）或 ReplayPage（回放）启动音频 → 用户切后台 → ViewPage.ets:591-596 的 appRunStatueEventCallback 在 RUN_STATE_BACKGROUND 只处理了「正在通话则关闭通话」，未关闭监听 → 若 monitor 为 true（checkMonitor 默认值 true，ViewPage.ets:747），setVoiceDetect(devId, true) 保持开启 → 音频会话在后台持续持有。
  • 关键分支与证据缺口（必须说清「不确定」的部分）：
  • SDK 走的是私有协议还是 AudioRenderer，TSNapi 是 native 层封装，ArkTS 侧看不到它用的是 AudioRenderer 还是 OHAudio，也没看到任何 audioInterrupt / InterruptEvent 监听、AVSession 注册或 backgroundTaskManager.startAudioPlayback。全仓检索 avSession 只有 PlaybackNVR.ets:52 一行 import、无任何调用，属死代码。
  • 若播放确实落到 PlayAudioRenderer，其 usage: STREAM_USAGE_VOICE_ASSISTANT 在鸿蒙上会参与系统音频场景切换与音效（音频效果模式）管理；aboutToDisappear（customSound.ets:119-123）与切 Tab（:525-529）都只调 destroy()，而 destroy()（playPcmUtils.ets:147-176）在状态为 STATE_RELEASED / STATE_NEW 时直接 return 且不置空静态引用，audioPlayer 这一 static 字段会一直指向已释放实例，后续 start()（:132-145）的状态守卫又允许在 STATE_STOPPED 上重启——存在「重复 init → 旧实例未释放 → 会话残留」的结构性风险。
  • 结论性质：代码侧存在明确的资源回收缺陷与后台音频不释放路径，但「是不是这两处导致系统音效锁死」尚未被运行时日志证实，故置信度只到「中」。

7. 根因结论

  • 置信度：🟡 中
  • 一句话根因：鸿蒙端把音频播放职责全部交给了 SDK 私有通道与一个 STREAM_USAGE_VOICE_ASSISTANT 的全局单例 PlayAudioRenderer，切后台时既不关闭预览监听、也不释放音频会话、更不监听系统音频中断，导致 App 在后台长期占用音频会话，进而劫持系统的音效（静享/音效切换）设置。
  • 关键证据链：用户原话「结束后台后音效切换功能恢复」（= 因果锁定在进程存活期）+ 神策证明后台保活是常态（暴露面成立）+ 代码证明 appRunStatueEventCallback 后台分支未关监听、destroy() 不置空静态引用、全仓无 audioInterrupt / AVSession 注册（机制成立）。三者指向同一方向，但缺运行时日志这一环。

8. 建议下一步

  • 分配给：鸿蒙端负责人（ViewPage.ets 预览监听生命周期、playPcmUtils.ets 音频会话回收），协同 SDK 侧确认 setVoiceDetect 的底层播放实现。
  • 优先处理项：
  1. ViewPage.appRunStatueEventCallback 的 RUN_STATE_BACKGROUND 分支补 setVoiceDetect(currentDevId, false)，并在回前台时按用户设置恢复；回放页同样处理。
  2. PlayAudioRenderer.destroy() 在 release 成功后把 PlayAudioRenderer.audioPlayer 置 null（当前是静态字段，永不置空），并给 init() 增加「已存在实例先销毁」的前置判空。

  • 关键分支：唯一失败分支就是「checkCode 过期/已消费」，且被归并进通用 else，与网络失败、参数错误共用同一提示。
  • 修复方向锚点：STOneKeyResetPwdViewController.m:132-149（拿到 30000126 时立即重新发起 /local-number/check 并静默重试一次提交）、:170-196（为该码单列分支，提示「验证已过期，正在重新验证」）；STLoginViewController.m:285-290（记下 checkCode 的取得时间，超过阈值在进入填写页时就预刷新）。

7. 根因结论

  • 置信度：🟢 强
  • 一句话根因：一键重置把 checkCode 当作永久有效凭据保存，而服务端对它有有效期/一次性消费约束；页面停留超过 TTL 后提交必然 30000126，且失败分支既不重取也不提示原因，用户陷在死循环里。
  • 关键证据链：Logan 两次请求体完全相同 + 服务端两次同码 30000126 + 取码与提交相隔 69 分钟 → 排除弱网、排除密码错误、排除服务端抖动；代码确认取码后无 TTL、失败后无重取。

8. 建议下一步

  • 分配给：iOS 账号模块负责人（STOneKeyResetPwdViewController.m），服务端确认 checkCode TTL 与一次性消费语义。
  • 优先处理项：
  1. 失败分支对 30000126 做专门处理：自动重新 /local-number/check 拿新码后重放提交（最多 1 次），仍失败再提示「请重新获取手机验证」。
  2. 客户端记录 checkCode 取得时间，超过 TTL 的 80% 时提前静默刷新，或在进入页面时就按服务端返回的 expireIn 起倒计时。
  • 验证方法：iPhone 26.x + iOS 8.4.1.6，分别停留 1 / 30 / 60 / 90 分钟后再提交，各 10 次，要求全部成功或给出可继续的明确引导；同时回归「验证码已消费后再提交」「连续点击重置 3 次」两个场景。
