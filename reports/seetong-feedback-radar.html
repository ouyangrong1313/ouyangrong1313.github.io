代码定位

  • 涉及模块：Seetong-App-iOS/Seetong5.0_ios/Seetong_tps/Classes/Login。
  • STLoginViewController.m:1125-1130：微信成功回调直接使用 response.code 发起登录，没有校验 response.state、code 非空、重复回跳或请求代次。
  • STLoginViewController.m:1438-1462：每次微信授权使用固定字符串 state = @"xxx"，无法区分旧回调、重复回调和当前授权请求。

  • STLoginViewController.m:854-907：失败分支只对账号冻结、验证码不存在和安全验证做专门处理，30100225 落入通用错误提示；没有清空授权态、重新拉起微信或引导其他登录方式。
  • STResponseModel.h:105-113：30100225 明确定义为 STRequestLoginVerfityFail，即“授权码校验失败”，但页面层未使用该枚举建立专用恢复路径。

根因结论

  • 置信度：现象 🟢 强；请求确实到达服务端并被拒绝 🟢 强；单一客户端根因 🟡 中。
  • 一句话根因：微信回调缺少随机一次性 state、单飞门禁和授权码消费标记，30100225 又落入通用失败分支；服务端拒绝后客户端保留旧授权态，用户只能看到错误码，无法自动获得新的有效授权。
  • 关键证据链：259063 明确反馈登录失败 → Logan 证明微信 code 非空 → 服务端以 30100225 拒绝 → 页面直接展示通用错误 → Sensors 在 8 小时内记录 188 次、107 名受影响用户，且跨 Android、iOS、HarmonyOS 持续存在。
  • 明确不下的结论：现有服务端响应只说明“授权码校验失败”，没有区分 code 过期、已被消费、微信应用配置不匹配或微信侧风控。不能把 107 名用户全部归因于客户端重复提交。

建议下一步

  • 分配给：位冬负责 iOS 微信授权与登录恢复，欧阳荣复核登录状态机和埋点口径；Android、HarmonyOS 登录负责人共同核对各自第三方登录 code 的消费与重试逻辑。
  • 先在服务端按 rid=c92f00cbafbd463582d02a33376ad549 查询微信授权码换取用户信息的原始结果，确认本次是过期、已消费、应用配置不符还是微信侧拒绝。
  • 每次授权生成随机一次性 state；在回调入口校验 state、errCode、code 非空和请求代次，并对同一回调做幂等与单飞去重。
  • 授权码一经提交即从当前会话与恢复缓存中消费。遇到 30100225 时禁止复用旧 code，应清理授权态、明确提示“授权已失效”，提供“重新微信授权”和“其他登录方式”两个出口。
  • 补齐 login_platform + error_code + rid + auth_attempt_id + code_age_ms + callback_count + state_match 埋点；服务端与三端客户端使用同一 rid 串联，避免只能看到笼统错误码。
  • 回归微信热启动回跳、冷启动 Universal Link、重复回调、同一 code 双击提交、进程重启恢复、用户取消、code 过期、code 已消费、微信应用配置异常九类场景。
