4. 代码定位（含锚点与调用链）

  • AlarmMessagePage.kt:301 → created 分支无条件调用 requestSystemNotificationPermission("created")；
  • AlarmMessagePage.kt:330 → pageDidAppear 分支再次调用 requestSystemNotificationPermission("pageDidAppear")；
  • AlarmMessagePage.kt:1010 requestSystemNotificationPermission → bridgeModule.getSystemPermissionStatus(SystemPermissionType.NOTIFICATION)。
  • iOS 桥接侧：Seetong-App-iOS/Seetong5.0_ios/Seetong_tps/KMP/Modules/KMPBridgeModule.m:1294 getSystemPermissionStatus:
  • KMPBridgeModule.m:1310 → [STSystemPermission getNotificationPermission:block]，注释写的是"异步查询当前宿主的系统权限状态"，但实际语义不止查询。
  • 缺陷点：Seetong-App-iOS/Seetong5.0_ios/Seetong_tps/Tools/SystemPermission/STSystemPermission.m:190 getNotificationPermission:
  • if (settings.authorizationStatus == UNAuthorizationStatusNotDetermined) → 直接 [center requestAuthorizationWithOptions:options completionHandler:...]。
  • 该分支把"读权限状态"升级成"发起授权请求"。系统授权弹窗由 SpringBoard 呈现，requestAuthorizationWithOptions 的回调要等用户操作，而这期间宿主 App 的主线程处于等待与系统转场交织的状态。

  • 修复方向锚点：
  1. STSystemPermission.m:190 拆成两个方法：queryNotificationPermission（只读 getNotificationSettings，NotDetermined 直接回 granted=NO, status=notDetermined）与 requestNotificationPermission（真正弹窗，仅由用户主动操作触发）。
  2. AlarmMessagePage.kt:301/330 改为调用只读版本；首次授权询问挪到启动后的空闲时机或"报警开关"页，不放在页面加载路径。
  3. 给 getNotificationPermission 与 requestAuthorizationWithOptions 之间补耗时日志（进入时间、回调时间），让下次回归能量化，而不是再靠主线程空档反推。

5. 根因结论

  • 置信度：🟡 中。
  • 一句话根因：报警页把"查询通知权限"实现成了"发起系统授权请求"，且在 created 与 pageDidAppear 各触发一次；首次进入时授权弹窗与系统转场叠加，主线程被独占，出现两次约 14.7 秒静默，列表数据虽已在 216 毫秒就绪却无法渲染。
  • 关键证据链：Logan 主线程空档两段共 29.47 秒，起点精确落在 requestSystemNotificationPermission 之后 → 代码里该调用在 NotDetermined 分支确实会弹授权 → 神策崩溃率正常，排除崩溃解释。
  • 证据边界（必须保留）：日志里 iOSLogFile_*_20261027104747.zip 在 10:47:47.180 才执行归档，未捕获 10:47:02 之后的现场；且本次没有 Instruments 采样，"授权弹窗直接导致 14.66 秒"仍是相关性推断而非因果闭环。另一个未排除的候选是 loadInitialData 内的 MMKV 首挂与 Kuikly 页面首帧渲染的同步开销，日志显示 10:46:45.943 主线程正在 loadMMKV（loading [seetong_kmp] with 13946 actual size）。两者需要在真机上分别去掉其一后复测才能定论。

  • WebSocketManager.m:391 RMWebSocketClose → 置 isActivelyClose = YES、[self.webSocket close]、_webSocket = nil、destoryHeartBeat、destoryNetWorkStartTesting；
  • WebSocketManager.m:208 webSocket:didCloseWithCode: → if (self.isActivelyClose) 走"主动断开"分支后 return，不重连；否则走 reConnectServer。

  • 现象与代码的对应关系：
  • 日志里 RMWebSocketClose 与 destoryHeartBeat 交替紧邻出现，而 RMWebSocketClose 只在主动关闭路径被调用，说明每次 open 之后存在一个主动 close 的调用方；
  • isActivelyClose = YES 一旦置位，只有重新走到 RMWebSocketClose 之外的路径才会复位，代码中没有在 webSocketDidOpen 里显式清 isActivelyClose，这会让"主动关闭"和"被动重连"两种状态互相污染；
  • 每次 open 都 resetReconnectCount，退避上限被反复归零，于是退避时间永远是 1～6 秒级，形成"高频但永不熔断"的循环。

  2. initHeartBeat 内部的 destoryHeartBeat 与另一处 close 并发；
  3. SystemSetViewController / STImproveViewController 内的 RMWebSocketClose（grep 命中，需确认是否在页面出现时被调用）。
  • 修复方向锚点：
  1. WebSocketManager.m:127 内补 self.isActivelyClose = NO；
  2. getNetty（WebSocketManager.m:410 附近，有"1 秒内已调用则忽略"的限流）处补打调用方堆栈，锁定主动 close 的来源；

5. 根因结论

  • 置信度：🟡 中。
  • 一句话根因：iOS 8.4.1.6 存在一条"open 后立即主动 close"的路径，配合 webSocketDidOpen 内无条件 resetReconnectCount，退避与熔断双双失效，导致长连接以 1～12 秒为周期重建，并在多个接入节点之间轮换。
  • 关键证据链：Logan 四轮 open→close 时序 + 每轮 reconn:1 + 代码里 RMWebSocketClose 与 resetReconnectCount 的实际行为 + 同期网络状态正常。
  • 与"卡顿/闪退"的关系：频繁重建会持续占用主线程（每轮 open 都是主队列任务）并与 FTS 写库、报警页刷新竞争，是 259896 所说"卡顿得无法操作"的合理放大因素，但本期没有证据把 3 次进程切换判定为闪退，两者不能写成因果。
