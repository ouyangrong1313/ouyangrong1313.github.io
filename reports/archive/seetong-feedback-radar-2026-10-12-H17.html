4. 代码定位（详细）

  • 涉及模块：Seetong-App-iOS（Seetong_tps）灯光配置链路
  • 关键类与位置：
  • CameraLightControlViewController.m:418（保存回调 setLightConfigBlock）
  • STLightingConfigViewController.m:225（另一处同名为 setLightConfigBlock 的回调）
  • UserClient.mm:5091（CMD_SET_IOT_LIGHT_CONFIG / 1108 响应 → 触发 setLightConfigBlock(nError)）
  • UserClient.mm:5099（CMD_SET_IOT_LIGHTSWITCH_CONFIG / 1521 响应 → 同一 setLightConfigBlock(nError)）
  • UserClient.mm:1504（CMD_LIGHTBOARD_CONFIG_SET / 1301 响应 → 同一 block）
  • 调用链：保存点击 → 1301 + 1108 + 1521 三条协议并发下发 → UserClient.mm 分别收响应 → 三处都调用同一个 setLightConfigBlock → UI 以最后一次回调的 nError 决定成败。
  • 关键分支：CameraLightControlViewController.m:426 的 if(0 == weakSelf.setLightConfigBlock_result) → 1521 的 -1 落到该分支 → QMUITips showError 提示失败并 popViewController；而此时设备已按 1108 / 1301 生效。
  • 修复方向锚点（按优先级）：
  1. UserClient.mm:5091 / 5099 / 1504 三处回调需去重：只有当实际承载用户意图的那条协议（1301 灯板 + 1108 IoT 模式）失败时才判失败，1521（网络指示灯子开关）不应独立否决整次保存；
  2. 客户端拼装 1521 时，应对不含网络指示灯能力的设备省略 NetworkIndicatorEnable，或按能力位下发合法值（当前恒定下发 "-1"，属越权字段）；
  3. NetworkIndicatorEnable="-1" 这一「未设置」哨兵值是否被设备固件接受，需固件侧确认（本期在成功场景见到 Result="0"、失败场景见到 Result="-1"，同一 payload 结果不一致，说明还有时序/并发因素，见「待补证」）。

5. 根因结论

  • 置信度：🟡 中（Logan 协议原文为硬证据，能确定「1521 失败被误当整次保存失败」；但同一 payload 成功场景 Result="0"、失败场景 Result="-1"，尚无法排除并发时序，故不上探到「强」）
  • 一句话根因：iOS 端把 1301 + 1108 + 1521 三条独立协议的结果汇聚到同一个回调 block（UserClient.mm:1504 / 5091 / 5099），任一条失败即判定整次保存失败；当 1521 携带设备并不支持的 NetworkIndicatorEnable="-1" 字段时返回 Result="-1"，UI 因此报「配置失败」，而 1301 / 1108 已生效 → 用户看到「提示失败、实际成功」。
  • 关键证据链：Logan 1521 请求体含 NetworkIndicatorEnable="-1" × 1521 响应 Msg_flag="-1" / Result="-1" × 同批次 1108 响应 Result="0" × 设备能力串含 NoSetLightBrightness × iOS 三处回调共用同一 block。

6. 建议下一步

  • 分配给：iOS 端（灯光配置模块，主）+ 固件 / SDK 侧（辅）
  • 优先处理项：
  1. 拆分回调语义：让 1521（网络指示灯）的失败不再否决 1301 / 1108 的成功判定，消除误导性失败提示。
  2. 按能力位下发：NoSetLightBrightness / 无网络指示灯能力的设备，1521 不下发 NetworkIndicatorEnable（或下发合法值），避免恒定 "-1"。
  3. 回访账号 17674575864，确认 16:59 第三次提交后界面是否仍报失败，以量化「失败提示」的复现率。
  • 验证方法：修复候选包中，同一设备连续 3 次进入灯光配置页修改灯光模式并保存，每次均提示成功；同时 Logan 中 1521 若返回 -1，UI 不再翻转为失败提示。
