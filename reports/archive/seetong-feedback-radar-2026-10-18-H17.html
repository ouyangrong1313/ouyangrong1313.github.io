🔴 问题 1：HarmonyOS 画中画状态导致切换设备后仍显示前一路画面 ｜ 负责人：张跃译

  • 共 3 条反馈、2 名独立用户，覆盖 2 个版本、2 个机型、2 个省级地区。不能把同一用户 9 分钟内的两次反馈算成两名用户。
  • 严重度评分：90 / 100。
  • 反馈量 20：3 条同域反馈，处于 3～5 条档。
  • 共性广度 30：版本、机型、地区三个维度均有两项，满足至少三个维度。

  • 证据边界：当前只能确认“当前账号下切换设备时画面没有随选择更新”，不能仅凭症状认定跨账号视频串流或隐私泄漏；尚缺设备 ID、实际流来源和 Logan 的对应关系。

神策证据

  • 本期尝试查询 PreviewSessionSummary 的 HarmonyOS 版本分布、MonitorFrameResult.fail_reason 和 AccountBind.error_code，三条聚合查询均超时；随后神策 MCP 服务断开。按本 skill 的同一查询失败阈值，已停止继续重试，因此本期没有可用于证明该问题影响面的线上聚合数据。
  • 现有神策事件中没有“点击目标设备 ID”与“实际渲染设备 ID”的一致性字段，即使服务恢复，也只能提供预览会话量和版本背景，不能直接替代客户端状态链证据。
  • 因此根因判断主要依赖两份独立用户的文本复现、明确的画中画开关对照，以及代码中的单例覆盖路径；不把缺失的神策数据填成 0。

Logan 关键日志

  • 258003、258004、258008 的 loganFileDownloadUrl 均为空，没有类名、错误码、控制器创建结果或实际流设备 ID 可引用。
  • 这三条反馈发生在 09:31～09:37，用户没有提供日志；不能在报告中伪造类名、行号或 PiPWindow 状态码。
  • 下一步必须补采日志，并至少记录点击的 devId、PipManager.savId、PipManager 当前控制器对应的设备、XComponentController 所属画面、PiPWindow.create/startPiP/stopPiP 返回值。没有这些字段时，只能把根因置信度定为中，不能定为强。

代码定位

  • feater/playDevice/src/main/ets/view/videoPreview/comp/SingleVideoComp.ets:193-205：每个画面组件把自己的 XComponentController 写入同一个 PipManager，随后调用 creatPip(this.devId)；异步完成后，未校验结果是否仍对应当前选中的设备，就更新全局 savId 并持久化该画面的 pipModule。
  • basic/src/main/ets/utils/PipManager.ets:61-106：PipManager 是单例，只持有一个 mXComponentController 和一个 pipController；creatPip() 可被多个画面并发调用，创建新控制器前没有先停止并注销旧控制器，也没有请求代次或取消机制。较晚完成的旧请求可覆盖新请求。
  • feater/playDevice/src/main/ets/view/videoPreview/comp/SingleVideoComp.ets:479-495：点击新画面时只更新共享的 currDevId 和 selectedIndex，没有先解绑旧的画中画控制器；随后 currDevIdChange() 在 :207-216 触发新画面再次 pipInit()，形成新旧控制器的切换竞争。
  • basic/src/main/ets/utils/PipManager.ets:149-167：状态回调继续使用共享的 savId 和持久化 pipModule；当旧创建任务最后完成时，ABOUT_TO_RESTORE/STARTED/STOPPED 都会落到旧设备，和当前界面选择不一致。
  • basic/src/main/ets/utils/PipManager.ets:170-180：stopPip() 的完成回调还会注销监听，但没有“仅注销当前代次”判断；在快速切换设备时，旧 Promise 完成可能清理新控制器刚注册的监听。
  • 调用链：点击设备卡片 → SingleVideoComp.onClick 更新 currDevId → 新画面 currDevIdChange/pipInit → PipManager.updateXComponentController → PiPWindow.create → 旧请求与新请求异步竞争 → 全局控制器/持久化设备号可能保留第一路画面。
  • 修复方向锚点
  • 将 deviceId + XComponentController + generation 作为一个原子参数传给 PipManager，禁止分两步更新全局选择。
  • 每次切设备先停止并销毁旧 PiPController；若 API 不支持并发创建，则把创建串行化。
  • 每个异步 create/start/stop/restore 完成后校验 generation；旧请求只能释放自己的资源，不能写 savId、偏好缓存或新控制器的监听。
  • onStateChange、controlEvent、ABOUT_TO_RESTORE 均应显式绑定创建时的 devId，不再读取共享的“最后一次写入”状态。
  • 关闭画中画时应彻底注销控制器和本页面监听，不能让上一画面的系统画中画会话继续持有首个 XComponent。

根因结论

  • 置信度：🟡 中。
  • 一句话根因：多个 HarmonyOS 画面共享一个无代次、无串行化、无旧控制器清理的 PipManager，切换设备时旧创建任务和新选择竞争，最终把第一路 XComponent、savId 或恢复状态保留下来。
  • 关键证据链：两名独立用户均描述第二路持续显示第一路；其中 258008 直接证明关闭画中画后恢复；代码确认每个画面都异步改写同一单例且没有“当前选择”校验。缺少 Logan，因此不能判断是 create 失败、控制器复用还是偏好回写最先触发。
  • 安全边界：当前证据不足以宣称跨账号画面泄漏；应作为高优先级画面身份一致性缺陷处理，并在复现时核对两个设备是否属于同一账号。

建议下一步

  • 分配给：冉博麟（画面组件与画中画切换）、张跃译（PipManager 单例和控制器生命周期）；欧阳荣复核 HarmonyOS 行为并确认是否存在跨账号风险。
  • 先修单例生命周期：切换画面时停止旧控制器、串行创建新控制器、引入请求代次并禁止旧 Promise 回写。
  • 回归矩阵覆盖 1.1.1.11 与 1.1.2.3、同账号两台 IPC、NVR 多通道、快速连点 A→B→C、画中画开启／关闭、应用前后台切换、画中画恢复、页面返回后再次进入八种场景。
  • 每个场景记录点击目标、currentDevId、displayDevIdList、savId、控制器所属 devId、XComponent 所属 devId、首帧设备标识及 PiPWindow 状态；确认画面身份后才允许把任务升级或关闭。
  • 任务账本：沿用 T-20260924-090202-a811，保持 P1 / captured，本期新增两名独立用户和画中画关闭对照证据。
