4. 代码定位

  • Android 预览入口与状态显示
  • PreviewPlayerView.kt:427-569：playVideo 先设置 PlayState.LOADING，再调用 iPlayerController.startPlay；随后无条件执行 clearVideoInfo()。
  • PreviewPlayerView.kt:640-642：clearVideoInfo() 固定设置 video_play_tip，中文资源值为“视频播放中”。
  • PreviewPlayerView.kt:950-976：真正的成功状态只在 onRecvFirstFrame 中设置；因此当前顺序会让“尚未收到首帧”的页面提前显示播放成功。
  • PreviewPlayerView.kt:761-835：10 秒求流定时器在无首帧时反复停止再开流，但没有单独的“首帧超时”页面状态或错误原因。
  • LibImpl.java:1468-1544：addWatch 返回 SDK 调用结果并写入 m_add_watch_result；异步 TPS_AddWachtRsp 与首帧是后续事件。现有日志已经出现“调用返回 0、首帧未到”的合法中间态，调用方不能把 ret=0 当作播放成功。
  • HarmonyOS 回放入口
  • ReplayPage.ets:155：isOffline 只有声明，后续未找到在设备在线态或连接失败时赋值的路径。
  • ReplayPage.ets:3875-3898：卡回放页只有在 isOffline=true 时才显示“设备离线”提示，所以该提示在当前状态下无法可靠触发。
  • DeviceServiceImpl.ets:5533-5548：ts_AddWatchEx 最终只返回 ret == 0，没有把失败码、连接类型或首帧超时传给回放页。
  • KMPCloudPlaybackVideoView.ets:70-78：播放器 onError 只向页面发送固定字符串 video onError，原始错误码被丢弃。
  • KMPCloudPlaybackVideoView.ets:191-209：准备失败和播放失败回调只带通用 message，前端无法区分无录像、设备离线、网络失败和播放器解码失败。

5. 根因结论

  • 置信度：🔴 弱。
  • 已确认事实：Android 257947 在设备在线、P2P 与 AddWatch 请求均被接受的情况下，10.2 秒内没有首帧，并且页面提前显示“视频播放中”。
  • 跨端共同缺口：各端把“请求已发送”“播放器已创建”“首帧已渲染”混在同一个用户状态中；超时或播放器错误没有稳定的结构化失败码，导致用户看到卡死、黑屏或空白。
  • 不能确认的推断：不能把 6 条反馈全部归因为同一客户端 bug；HarmonyOS 的 4 条没有日志，可能分别来自设备录像为空、设备离线、服务端时间轴异常、播放组件失败或真实卡顿。
  • 一句话根因：远程视频链路缺少从请求、连接到首帧的统一状态机与超时门禁，Android 已出现“无首帧仍显示播放中”的直接缺陷，HarmonyOS 则缺失离线态赋值和错误码透传，导致多点故障看起来相同但无法合并为同一根因。

6. 建议下一步

  • 分配给：欧阳荣（Android 预览与首帧监控）、李国涛（HarmonyOS 回放状态）、陈宝旺（AddWatchEx 与跨端播放回调）。
  • Android 先修用户可见假状态：在 onRecvFirstFrame 前显示“正在连接／等待画面”，10 秒超时后进入独立失败态，保留重试入口，不再固定显示“视频播放中”。
  • 将 10 秒求流限制为有限次数，并记录每次 devId + requestId + addWatch ret + P2P 状态 + firstFrame elapsedMs；禁止在无首帧时持续叠加同一通道的开流请求。
  • HarmonyOS 补齐 ReplayPage.isOffline 的赋值链路，并让 ts_AddWatchEx 返回结构化错误；KMPCloudPlaybackVideoView 的 onError 必须把原始错误码传到页面。
  • 回归矩阵：Android 8.4.1.6 与 8.3.14.2、HarmonyOS 1.1.1.11 与 1.1.2.3，各覆盖在线设备、设备离线、无录像、录像为空、首帧超时、播放中断、重试恢复七种场景。
  • 任务账本：沿用 T-20260923-170444-60dc、T-20260926-170258-2226，状态保持 P1 / captured。

  • STLoginViewController.m:777-880：授权码通过 kEmptyStr(authCode) 直接进入请求体；通用空值兜底会把缺失值转换为空串，而不是在提交前终止。
  • STLoginViewController.m:889-907：失败分支没有识别 STRequestLoginVerfityFail，仅落进通用错误提示；没有清理 self.authCode，也没有自动重新拉起授权。
  • STLoginViewController.m:655-665：滑动验证完成后会再次使用 self.authCode 请求，存在复用已消费授权码的风险。
  • STRequestManager.m:175-190：老版本恢复登录路径直接从持久化状态取 loginCode 再提交微信登录，没有“一次性消费标记”。

5. 根因结论

  • 置信度：🟡 中。
  • 一句话根因：微信回调与恢复登录没有一次性 state、幂等锁和授权码消费机制，重复回跳或重试会把同一个单次授权码再次发给服务端，服务端以 30100225 拒绝后客户端仍保留旧状态。
  • 关键证据链：两份 Logan 均证明 code 非空；同一用户在同一失败时段重复提交完全相同的 code；服务端两次均返回“授权码校验失败”；代码侧确认固定 state、无单飞门禁、无 30100225 专用恢复路径。
  • 证据边界：服务端只返回“授权码校验失败”，没有区分 code 过期、已消费、应用配置错误或微信侧状态异常；不能把全部 30100225 都归因于客户端重复提交，但本窗口两例的重复 code 特征明确。
