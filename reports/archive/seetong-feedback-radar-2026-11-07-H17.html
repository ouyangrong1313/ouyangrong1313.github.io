4. 代码定位（详细）

  • 涉及模块：
  • Seetong-App-Android/Seetong5.0ForSeetong/Seetong5.0（Android 宿主与 SDK 桥接）
  • KMP 共享层回放页（日志中的 PlayBackPage / PlaybackVM / RecordPlayerView）——本机仓库内未找到该页 Kotlin 源码（Seetong-App-Android 全仓 grep PlayBackPage / fetchEventList 无命中，kmp/libs/shared-debug.aar 仅 5.4KB 且不含业务类），KMP 源码仓不在标准路径，故本节对 KMP 侧只做行为级定位，不臆造行号。
  • 关键类与方法（已核对到源码）：
  • kmp/src/main/java/com/seetong/kuikly/export/RecordPlayerView.kt:222-267（startReplay）——ensureReplayAudio → device.m_video = openglesRender → IO 线程 startNvrReplay，失败重试一次后回调 onReplayError
  • kmp/src/main/java/com/seetong/kuikly/export/RecordPlayerView.kt:370-383（seekReplay）——每次 seek 都直接下发 NVR_ACTION_SEEK，无节流、无单飞、无上一请求取消
  • app/src/main/java/com/seetong/app/seetong/provider/BridgeServiceImpl.kt:1886-1896（startNvrReplay / controlNvrReplay）——直接透传 LibImpl
  • app/src/main/java/com/seetong/app/seetong/sdk/impl/LibImpl.java:2251-2285（onNvrReplayResp）——GetProtAgent → OpenStreamAgent → PlayAgent(port, 0)，末尾统一 KuiklyEvent.INSTANCE.sendPlaybackFailedEvent(dev.m_devId, String.valueOf(result))
  • lib_base/src/main/java/com/seetong/lib_base/utils/KuiklyEvent.kt:41-50（sendPlaybackFailedEvent）——事件名 kmp_playback_play_failed_event，载荷 {"devId":..,"result":..}
  • app/src/main/java/com/seetong/app/seetong/ui/VideoRecordActivity.java:3705-3711——原生侧 TPS_MSG_RSP_NVR_REPLAY 分支同样无条件 sendPlaybackFailedEvent(mFirstDeviceId, String.valueOf(flag))
  • 调用链（本问题触发路径）：

PlayBackPage.pageDidAppear → loadPlaybackData → fetchEventList（设备服务取当日录像块，等待上限 15s）→ 超时 → loadEventData timeout, auto retry once → 重试成功 → prepareTimelinePosition → RecordPlayerView.startReplay → BridgeServiceImpl.startNvrReplay → LibImpl.onNvrReplayResp → OpenStreamAgent/PlayAgent →（同时）sendPlaybackFailedEvent(result) → PlayBackPage.receive playback play failed event → RecordPlayerView.onRecvFirstFrame → mark card playback first frame

  • 关键分支（哪条路径会踩到）：
  1. 首次事件列表请求的等待上限是 15 秒，且超时后才 auto retry once；用户在这 15 秒内看到的就是「加载不出来」。日志中该请求最终返回 count=15，说明设备服务能应答、只是慢。
  2. 重试与首次请求无取消关系：07:24:18.212 count=15 与 07:24:23.101 count=9 是两份不同结果，后到者覆盖前者，时间轴与录像块会用哪一份取决于回调顺序。
  3. sendPlaybackFailedEvent 的 result 语义不统一：LibImpl.onNvrReplayResp 末尾传的是 result（解码/开流结果），VideoRecordActivity 传的是消息 flag；两者为 0 时下游仍按「失败」处理，于是出现「PlayAgent ret=0」与「play failed result=0」并存。
  4. TPS_ReplayDevFileRsp is invalid 在 stopReplay 后必现，属退出时的空响应，会额外产生一次失败事件与一次异常上报，抬高同类问题的日志噪声。
  5. seekReplay 无节流：拖动条每次滑动都可能下发一次 NVR_ACTION_SEEK，在 4K 通道（3840×2160@25fps、bitrate=2048）上叠加大量在途开流请求，与 261961「拖动卡顿」的体感方向一致（该反馈因未进入回放页无法直接证实）。
  • 修复方向锚点：
  • 事件列表首次请求等待上限由 15s 下调到 3~5s，超时先渲染「历史录像块」骨架 + 「正在加载更多」占位，避免整页空白；
  • loadPlaybackData 的重试与首次请求改为单飞 + 可取消，迟到的响应按请求序号丢弃；
  • KuiklyEvent.sendPlaybackFailedEvent 调用点统一语义（失败才发，或增加 code 字段区分「开流结果」与「失败原因」），KMP 侧对 result=0 不做失败态切换；
  • stopReplay 后对 TPS_ReplayDevFileRsp is invalid 做静默处理，不再抛异常；
  • seekReplay 增加 200~300ms 防抖与单飞，拖动中只保留最后一次目标时间；
  • 4K/H265 通道回放前预置解码参数、延长首帧门禁窗口，并记录 open→PlayAgent→firstFrame 分段耗时。

5. 根因结论

  • 置信度：🟡 中
  • 一句话根因：回放页把「首次拉取录像列表」的等待上限设为 15 秒且超时后才重试，重试与首次请求互相覆盖；同时 SDK 开流成功与失败事件共用 result=0，导致页面先进入失败态再出首帧——用户看到的就是「加载不出来」。
  • 关键证据链：Logan 中 07:24:02.756 发起 → 07:24:17.759 超时（正好 15 秒）→ 重试后 count=15/count=9 两份结果 + onNvrReplayResp 打印 video codec=H265 3840×2160 与 PlayAgent ret=0 + 同刻两次 play failed result=0 + 167ms 后 onRecvFirstFrame（客户端时序事实）；NvrAiSearch 同设备同刻也出现 capacity request timed out 与 -10003 操作超时（同源「设备服务慢」的旁证）；神策 DeviceVideoPlayback 总量平稳（排除服务端整体故障）。未能拿到：事件列表请求在服务端/设备侧的实际处理耗时，故「为什么慢」仍待设备服务侧确认。
