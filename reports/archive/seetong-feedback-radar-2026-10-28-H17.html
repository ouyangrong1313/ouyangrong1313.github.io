4. 代码定位（详细）

涉及模块：seetong-kmp/modulePlayback（KMP 共享层）+ Seetong-App-Android/…/ui/ext/TimeLine.java（Android 原生时间轴）。

调用链：

PlaybackServiceImpl.parseCloudBaseEvents()        // 服务端 times[]/events[] → TcsEventBean(st, et)
  → PlayBackPageViewModel.buildCardTimelineRecords()   // 事件区间 → TimeLineRecord(startSec, durationSec)
  → CardPlayBackPageTimeline.buildTimeLineSection()    // 传给 KMPTimelineView（原生渲染）
  → KMPTimelineView → Android TimeLine.drawRecords()   // 按 (startsAt - 当天0点) / (当天末 - 当天0点) 映射到像素

两套比例的不一致点：

  1. KMP 侧 moduleBase/src/commonMain/kotlin/com/seetong/base/view/TimeLineView.kt:197-198
val recStartPx = (rec.startSec.toFloat() / SECONDS_PER_DAY) * totalW
val recWidthPx = (rec.durationSec.toFloat() / SECONDS_PER_DAY) * totalW

即固定 86400 秒 × 整个 view 宽度。

  1. Android 原生侧 TimeLine.java:247-300（drawRecords）
double fb = (OFFSET * mDensScaleFactor) + xb;
double fe = xe - (OFFSET * mDensScaleFactor);
double rb = fb + ((fe - fb) * ((double) (r.startsAt() - t1) / (double) (t2 - t1)));

即先扣掉左右各 16dp 的 OFFSET，再按 时长 / (当天末 - 当天0点) 映射。

当 OFFSET > 0 而 KMP 侧没有扣 OFFSET 时，两条公式在一天的两端会产生固定偏移：越靠近 00:00 和 24:00，色块相对刻度尺的偏差越大；中间段几乎看不出来。这与用户「时间轴显示不对」而非「完全错」的描述一致。

  1. 刻度尺本身走的是另一套：TimeLine.timestampToFrameX()（TimeLine.java:381-397）按 mFrameW - OFFSET * 2 缩放，convertPositionToTime()（:571-586）用 mFrameX + OFFSET 做换算。也就是说刻度、色块、游标三者各自有一套坐标基准，任何一个漏改都会表现为「看着对不上」。
  1. 时间文本还有一处独立换算：PlayBackPageViewModel.kt:225 与 :2304 在格式化时额外 +8 小时（(timestampMs / 1000 + 8 * 3600) % SECONDS_PER_DAY），而 TimeLineRecord.startSec 传入时没有再减去时区偏移。若服务端 st 是 UTC 秒、KMP 侧按当天秒直接上传，色块整体会偏 8 小时——这条与用户「时间有问题」的表述也很吻合，但本期无日志，无法确认是哪一条。

修复方向锚点（按可疑度排序）：

  • TimeLineView.kt:197-198：色块映射是否应与 drawRecords 共用 fb/fe（含 OFFSET）而不是 0..totalW。
  • PlayBackPageViewModel.kt:2118 附近 buildCardTimelineRecords 的 startSec 基准，是否与服务端 st 的时区口径一致。
  • PlayBackPageViewModel.kt:225 / :2304 的 +8 * 3600 是唯一时区换算点，需确认 TimeLineRecord 是否绕过了它。

5. 根因结论

  • 置信度：🟡 中（代码层面存在明确的多套坐标基准，但没有任何本问题的日志或截图，无法指认具体是哪一处偏移）
  • 一句话根因：卡回放的时间轴在 KMP 层、原生绘制层、刻度层各自维护了一套「秒 → 像素」换算，且至少有一处未统一 OFFSET 与时区基准，导致色块/刻度在部分区间对不上。
  • 关键证据链：反馈（同一用户 18 分钟内两次同诉 + 同一 NVR 场景先报不出图）+ 代码（三套换算基准并存）；神策与 Logan 均未提供证据。
