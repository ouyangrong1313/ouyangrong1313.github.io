4. 代码定位（详细）

  • 涉及模块：iOS 推送入口与 KMP 回放路由
  • 关键类与锚点：
  1. 通知响应入口
  • AppDelegate.m:503-562：userNotificationCenter:didReceiveNotificationResponse:withCompletionHandler:
  • AppDelegate.m:508：仅当 content.userInfo 包含 "content" 时进入离线报警 JSON 解码
  • AppDelegate.m:520-551：Base64 还原 → STRemotePushModel → 按 bizType 分流；offline_alarm 进入 ReceivePushMessage
  • AppDelegate.m:554-558：无 "content" 字段时只按标题和正文调用旧入口，不会携带报警 deviceId / alarmTime
  1. 推送消费与页面路由
  • AppDelegate.m:1074-1121：ReceivePushMessage:Title:，解析成功后保存 lineoffPushMsg，并调用 KMPRouter
  • KMPRouter.m:458-499：openOfflinePushPlaybackPage，依次校验推送模型、设备列表是否就绪、导航控制器是否可用，再调用 openAlarmPlaybackPageWithParams
  • KMPRouter.m:503-535：先切换报警 Tab，0.1 秒后进入回放；以 devUid|alarmTime 作为请求键防止重复打开
  • 调用链：

APNs 通知 → didReceiveNotificationResponse → dict["content"] 解码 → ReceivePushMessage → saveLineoffPushMsg → KMPRouter.openOfflinePushPlaybackPageBySelectingAlarmTab → openAlarmPlaybackPageWithParams → PlayBackPage

  • 关键分支：
  • dict["content"] 缺失会走标题 / 正文回退，报警定位参数丢失。
  • popModel.devUid 为空或 alarmTime 无法转成毫秒时间戳时，offlinePushPlaybackPageData 返回空，路由直接消费消息而不打开回放。
  • 设备列表未就绪属于暂时失败，保留未读态等待后续重试；设备已就绪但目标设备不在账号则永久失败。
  • shouldHandlePushInViewController 返回 NO 时，不会调用 KMPRouter，但当前日志未打印该分支结果。
  • 代码缺口：AppDelegate.m 未检索到 UIApplicationLaunchOptionsRemoteNotificationKey 冷启动兜底处理。当前依赖 iOS 10+ 的 userNotificationCenter:didReceiveNotificationResponse: 回调；如果该回调缺失，现有代码没有从 launchOptions 二次提取报警推送的路径。
  • 修复方向锚点：
  1. 在 didFinishLaunchingWithOptions 与 didReceiveNotificationResponse 同时记录通知来源、userInfo key、bizType、deviceId、alarmTime 和路由结果，先补齐可观测性。
  2. 对冷启动增加 launchOptions[UIApplicationLaunchOptionsRemoteNotificationKey] 兜底解析，或在通知响应缺失时从待处理推送模型中恢复。
  3. 为 shouldHandlePushInViewController 的拒绝分支补日志和可重试状态，避免通知被静默吞掉。
  4. 将 KMP 路由失败结果回传到原生入口，便于区分「已请求打开但回放失败」与「从未请求打开」。

5. 根因结论

  • 置信度：🟡 中

  • 关键证据链：
  • 当前 Logan：didFinishLaunchingWithOptions 出现，didReceiveNotificationResponse / PlayBackPage 缺失。
  • 同用户历史 OBS：9 月多个日期同一 offline_alarm payload 可完整走通通知 → KMP 回放。
  • 神策：iOS 8.4.106 离线推送回放每日存在超过 60 秒的长尾，且当天 62 次 >60 秒，说明该入口确有不稳定信号。
  • 反馈原话与 Logan 观察互相吻合：关闭 App 再进入后能看到视频，指向冷启动入口而不是视频解码或设备离线。
  • 明确不成立的推断：不得写成「iOS 8.4.1.6 报警回放整体失效」。10-16 09:00 前 iOS 8.4.106 仍有 14,006 次离线推送回放在 3 秒内出图，且历史日志多次成功。

4. 代码定位（详细）

  • 涉及模块：Android KMP 宿主容器、原生桥接、KMP 回放页
  • 关键类与锚点：
  1. 关闭页桥接
  • KMPBridgeModule.kt:856-858：closePage(params) 仅执行 activity?.finish()，无日志、无 Promise / callback、无 isFinishing 结果
  • KRRouterAdapter.kt:19-21：框架路由关闭同样只执行 (context as? Activity)?.finish()
  • KuiklyRenderActivity.kt:564-572：closePages(pageNames) 按页面名查找 Activity 后调用 finish()
  1. 返回键处理
  • KuiklyRenderActivity.kt:288-295：注册 OnBackPressedCallback，若无框架消费则关闭当前 callback 后再次调用 dispatcher
  • KuiklyRenderActivity.kt:410-419：dispatchKeyEvent 在 ACTION_UP 再次调用 kuiklyRenderViewDelegator.onBackPressed()；未消费时再委托 super.dispatchKeyEvent
  • 风险点：一次系统返回键可能先后经过 dispatchKeyEvent 与 OnBackPressedCallback 两套入口；如果前端某次返回 true 但没有真正执行关闭，事件会被吞掉，表现为“点了没反应”
  1. 检测到页面仍在活动
  • KMP_SCAN_TRACE-onCreate page=PlayBackPage
  • PlaybackScreenAwake applied=true
  • RecordPlayerView-startReplay 与 onNvrReplayResp act=0
  • 调用链（界面关闭按钮，推断）：

PlayBackPage 关闭按钮 → KMPBridgeModule.closePage → activity?.finish() → KuiklyRenderActivity.onDestroy

  • 调用链（系统返回键）：

KeyEvent.ACTION_UP → dispatchKeyEvent → kuiklyRenderViewDelegator.onBackPressed → [消费则返回 true]；[未消费则 super → OnBackPressedCallback → onBackPressedDispatcher → finish]

  • 关键缺口：
  • closePage 未记录 pageName、调用来源、Activity 是否为空、调用前后 isFinishing。
  • 无 KMP 前端页面源码，无法确认关闭按钮是否一定调用了 closePage；当前仓库只看到原生桥接。
  • 无关闭失败的统一错误回调，用户点击后前端无法显示失败或回退。
  • 修复方向锚点：
  1. 在 KMPBridgeModule.closePage 增加结构化日志与回调，记录 pageName、activity null、isFinishingBefore/After。
  2. 统一返回键处理为单一路径，消除 dispatchKeyEvent 与 onBackPressedDispatcher 的双重消费风险。
  3. 在前端关闭按钮点击处补埋点，区分「未调用桥接」「桥接收到但未 finish」「Activity 已 finish 但 UI 未消失」。

5. 根因结论

  • 置信度：🔴 弱
  • 一句话根因：当前只能确认 KMP 回放页成功创建并出流、用户随后进入其他页面，无法确认关闭请求是否到达 closePage；最可疑点是关闭桥接缺少结果反馈，以及返回键存在双重消费路径，但尚未形成直证。
  • 关键证据链：
  • Logan 证明 257578 在 08:33:04 创建 PlayBackPage。
  • 下层 onNvrReplayResp act=0 证明播放链路已启动，问题不在首个出流请求。
  • 反馈原文只描述关闭窗口失败，与关闭桥接 / 返回键路径直接相关。
  • 当前代码中 closePage 仅 finish 且无日志，无法自证调用成功或失败。
  • 明确不成立的推断：不得写成「8.4.1.7 回放页完全无法退出」。后续日志显示用户已进入账号管理、系统设置和消息中心等页面，说明页面栈并非绝对卡死；问题可能仅限于某个关闭按钮、弹层或返回键分支。
