4. 代码定位（详细）

  • 涉及模块：Seetong-App-iOS（Seetong_tps）录像回放链路 + 设备分组模型
  • 关键类与位置：
  • STPlaybackVC.m:1416-1432（nvrPlaybackPlayFailBlock 装配与 -7 / -14 判定）
  • STPlaybackVC.m:1497-1510（updateLimitUIWithLimit:，文案与 UI 降级）
  • STPlaybackVC.m:3555、3621、4829（读取 hintLabel.text 判断是否处于上限态，进而禁用批量下载等能力）
  • STPlaybackVC.m:5082、5663（updateLimitUIWithLimit:NO，清除上限态）
  • STPlaybackVC.m:5478-5482（按 cloudId 取设备数组）、6046-6048 / 6501（camera_nvr = cameraArray.firstObject）
  • STDeviceListModel.m:645-657（cloudId 与 uid 的构造规则）
  • DeviceListModel.m:56-96（devGroupDict 按 cloudId 分组）
  • STDeviceListService.m:194-205（getDevicesWithCloudId: 按分组取数组，返回不可变副本）
  • Camera.h:500（cloudId 声明与「不带 -CH-」语义）
  • 调用链（可复算）：

回放页进入 → STPlaybackVC.setupUI → camera_nvr = cameraArray.firstObject（:6046）→ 请求回放 → NVR 返回 -7 / -14 → TSCameraBlock.nvrPlaybackPlayFailBlock（:1416）→ updateLimitUIWithLimit:YES（:1422）→ stopAndResetPlayback + hiddenFunctionView + hintLabel.text = replay_limmit_tips（:1504）→ 用户看到「当前同时播放人数已达上限」且回放不可用

  • 关键分支（本期认定的结构性缺陷所在）：cloudId 是 NVR 主设备与它全部通道的公共键（Camera.h:500 注释「不带 -CH-」、STDeviceListModel.m:657 赋值）。因此 getDevicesWithCloudId: 返回的数组同时包含主设备与 8 个通道；而回放上下文取 firstObject，在切换通道 / 重新进入回放时会在「主设备」与「通道」之间来回绑定。若 NVR 侧把「主设备会话」与「通道会话」计为不同并发，则客户端在单用户单设备场景下就可能把自己的额度占满 → 返回 -7 / -14 → 弹出「人数已达上限」。
  • 修复方向锚点（按优先级）：
  1. 统一会话归属：在 STPlaybackVC.m:6046-6048 / 6501 取 cameraArray.firstObject 时，明确只取本次回放的目标通道（按 uid 含 -CH-n 匹配），避免主设备与通道交替占据回放会话；
  2. 回调去误报：STPlaybackVC.m:1416-1432 的 -7 / -14 分支在 updateLimitUIWithLimit:YES 之前，应先核对本地是否只有一个活跃回放会话（如 recPlayBlock 无其他活跃 devId）；若无其他会话，则应按「设备侧额度瞬时竞态」处理为自动重试而非直接判「人数已满」；
  3. 文案分层：replay_limmit_tips（Localizable.strings:1744）目前同时承担「设备并发满」「NVR 路数满」「瞬时竞态」三种语义，建议区分文案，避免把可自愈的竞态直接呈现为不可用；
  4. updateLimitUIWithLimit:YES 内的 stopAndResetPlayback 属破坏性降级，建议改为「保留时间轴 + 顶部提示 + 自动重试」，避免单次误判把整个回放体验打断。
