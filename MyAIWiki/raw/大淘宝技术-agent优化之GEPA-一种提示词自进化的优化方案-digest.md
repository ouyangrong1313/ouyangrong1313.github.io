## 一句话

GEPA 把 Prompt 优化做成“推理 → 评分 → 反思 → 选择”的数据闭环：错误样本先被归因到 Prompt 规则，再生成候选变体，最后用 Pareto 前沿保留多目标权衡，而不是依赖人工盲调或只追逐单一最高分。

## 五个核心观点

1. **反思式变异**：优化器不只看到分数，还让 Judge 说明错误发生在哪里、Prompt 哪条规则没有阻止它，以及应如何修正。
2. **Pareto 择优**：精确率、召回率、成本或长度等目标可能互相冲突，候选集应保留非支配解，避免一次修补牺牲另一项能力。
3. **任务无关适配层**：把数据加载、输出解析、评分和反馈抽象成组件与协议，新场景主要通过配置接入，而不是重复编写 Adapter。
4. **零配置推断**：Inspector 画像字段、推断标注列和任务类型，并给出模板与种子 Prompt；用户仍应确认关键评分偏好和数据切分。
5. **业务化需要控制面**：冻结硬约束、Schema 和工具协议，把可变决策规则交给优化器；同时保留回归、长度门禁、人工标注和线上业务指标对齐。

## 七个分析角度与开头钩子

### 1. 为什么人工 Prompt 盲调难以复用

- Prompt 改了很多次，为什么团队仍说不清“哪条规则解决了哪类错”？
- 真正的瓶颈不是不会写提示词，而是没有把错误变成可比较的证据。
- 没有数据闭环的优化，经验只能停留在个人直觉里。

### 2. 反思式变异到底多了什么

- GEPA 不只问“这次得分多少”，还追问“为什么错、该改哪条规则”。
- 把 Badcase 变成结构化诊断，Prompt 优化才从随机搜索变成定向改写。
- Judge 的价值不是替任务模型作答，而是提供可供变异模型消费的文本梯度。

### 3. 为什么要保留 Pareto 前沿

- 一个候选把召回率拉高，却让误判暴涨，算不算进步？
- 业务真正需要的常常不是唯一冠军，而是一组可解释的权衡方案。
- Pareto 前沿把“指标对抗”显式留在选择阶段，而不是藏在一个总分里。

### 4. 从论文原型到业务服务

- 每个场景都写一套 Adapter，规模一上来就会变成维护负担。
- 配置层、引擎层、组件层和服务层的分工，决定了算法能否被复用。
- 任务无关不等于没有差异，而是把差异放进可插拔协议和配置。

### 5. 评估器如何与业务对齐

- 离线高分却线上翻车，通常不是优化循环缺失，而是目标不一致。
- 人工标注对齐提供基础准确性，线上业务指标提供真实价值约束。
- 评估器、数据集和 Prompt 都要版本化，否则提升无法复现。

### 6. 自动进化的边界在哪里

- 让反思模型重写整段 Prompt，可能把安全约束和输出协议一并改掉。
- 冻结区与可变区分离，是结构性防护，不是事后扣分。
- Prompt 变长可能带来分数上涨，却同时损害成本、延迟和可维护性。

### 7. 没有 Ground Truth 时怎么办

- 没有标准答案时，离线指标和线上业务效果可以提供两条排序信号。
- 历史策略回溯适合做排序或否决，不应直接回流为反思依据。
- 没有可靠判据时，优化器越强，奖励黑客和保守化的风险也越大。

## 最小实践

1. 先选一个有标注、低副作用、结果可复核的 Judge 或分类任务。
2. 固定数据切分与输出 Schema，记录原始 Prompt、候选 Prompt 和每轮反馈。
3. 先用确定性解析与评分，再引入 Judge 做错误归因；不要让 LLM 直接决定最终分数。
4. 同时观察质量、成本、长度和线上相关指标，保留非支配候选并设置硬门禁。
5. 将硬约束放入冻结区，候选变更通过回归和人工 review 后再发布。
