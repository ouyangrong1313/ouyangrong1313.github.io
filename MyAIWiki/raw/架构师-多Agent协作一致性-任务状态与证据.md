架构师（JiaGouX）

我们都是架构师！
架构未来，你来不来？




上周面试了一位做 Agent 开发的候选人。

简历里写了一个多 Agent 系统。我让他简单讲讲架构：Planner 负责拆任务，Researcher 负责查资料，Executor 负责执行，Reviewer 负责检查。

这张图看上去没有什么问题。

我没有继续追框架名称，也没有问用了几个模型，而是换了一个具体场景：

“线上 user-service 突然变慢。Researcher 查完日志，说问题在数据库。接下来，你准备把什么东西交给 Executor？”

他说：“把分析结果传过去。”

于是我继续问：

“哪一版代码？”

“哪段日志？”

“这个结论是已经确认的事实，还是 Researcher 的判断？”

“Executor 改完以后，Reviewer 测的还是这一版吗？”

聊到这里，问题才真正开始。

很多多 Agent 系统，角色很多，工具很多，流程图也画得很完整。但只要追问几次“现在是哪一版”“这句话谁确认过”“失败以后从哪里恢复”，架构里的空白很快就会暴露出来。

多个 Agent 最危险的情况，不是意见不同，而是每个 Agent 都在自己的世界里正确。

我更在意的“一致”，也不是让几个 Agent 最后说出同一个答案。Researcher 和 Reviewer 本来就可以有不同判断，甚至应该有人专门提出反例。

真正需要对齐的是三件事：它们处理的是不是同一个任务，依据的是不是同一份事实，推进的是不是同一套状态。

推理可以有分歧，协议不能含糊。

第一问：这个任务为什么要拆成多个 Agent？

如果只看表面，user-service 变慢确实适合分工：有人看监控和日志，有人查代码和配置，有人验证修改结果。

但这三个动作真的可以同时做吗？

查监控和查资料，也许可以并行。可如果 Executor 不知道 Researcher 基于哪个版本查出来的，Reviewer 也不知道 Executor 改的是哪一份代码，所谓并行只是把几个不完整的任务同时推了出去。

面试里我会把两个问题分开问：任务本身能不能并行，以及系统是不是把并行关系在一开始就固定了。前者看的是任务依赖，后者看的是编排方式。任务之间没有强依赖时，可以静态地拆成几个子任务；但如果执行过程中会不断产生新线索，编排就要支持动态调整。把任务静态拆开，不等于整个流程也要静态编排。

比如 Planner 一开始把任务拆成“查监控”“查数据库”“查连接池”。三个 Agent 看起来各有分工，实际可能都去读同一批日志，也可能都把“数据库变慢”当成自己的结论。任务粒度太粗，会重叠；粒度太细，又会让 Agent 一直等别人补上下文。并行不是把任务复制几份再同时发出去，而是要先说清楚每个子任务的边界和输入。

执行过程中，事实还可能发生变化。Researcher 新发现了一条线索，原来的任务图就可能需要暂停、合并或重新拆分。任务不能只在开始时扇出一次，之后就靠几个 Agent 自己往前跑；至少要允许调度器根据新证据收回、合并或补派任务。

Google Research 关于多 Agent 系统扩展性的研究提供了一个很直观的对照：在可以并行探索的金融分析任务上，集中式多 Agent 架构相对单 Agent 基线提升了 80.9%；在严格按顺序推进的 PlanCraft 任务上，多 Agent 方案反而下降了 39% 到 70%。这些数字对应的是那次实验的口径，不是所有任务的通用比例，但至少说明了一件事：任务结构比 Agent 数量更重要。

Anthropic 的多 Agent 研究系统也采用了宽度优先的拆法，把可以独立搜索的方向交给不同 Agent；前后步骤高度依赖同一份上下文的工作，就没有那么适合拆开。

图 1：控制面、执行面与一致性边界

所以，面试里如果只听到“我们做了并行执行”，我还会问：怎么证明同一个子任务没有被分给两个 Agent？

假设两个调度器同时读到一个 pending 任务。如果系统只是先读再写，两个 Agent 都可能认为自己已经拿到了任务。解决这个问题，不能只在调度器里多写一个 if。更稳的做法是给全局任务和子任务分配稳定的身份，再用带条件的认领、租约和唯一约束，把“不重复”变成数据库和状态服务可以检查的事实。

任务拆分带来的收益，也要覆盖通信、上下文复制、等待、重试和汇总的成本。这个账算不清楚，Agent 越多，协调工作越容易超过实际工作。

第二问：第一个 Agent 到底交给下一个 Agent 什么？

Researcher 说：“慢在数据库。”

这句话可以作为线索，但还不能直接交给 Executor 改代码。Executor 至少要知道问题发生在哪个时间段，对应哪条 SQL，引用的是哪一版日志，当前代码和配置是什么版本，哪些方向已经排除，以及改完以后怎样验收。

否则下游拿到的不是任务，只是一句传闻。

所以，Agent 之间需要的不是一份更长的聊天记录，而是一份拿来就能继续工作的状态：

Task
  ├─ 基于哪一版：snapshot / commit
  ├─ 已确认什么：evidence refs
  ├─ 仍在猜什么：assumptions
  ├─ 允许做什么：capability / constraints
  ├─ 产物在哪里：artifact refs
  └─ 怎样算完成：acceptance

这不是固定格式，关键是不要把输入快照、证据、推测、权限、产物和验收条件混成一段自然语言。

我们前面讨论长任务时反复提到过 HANDOFF。它解决的不是“如何把聊天记录写得更漂亮”，而是上下文被压缩、工具重试或 Agent 更换以后，下一棒仍然知道自己接的是什么。

Agent 之间真正要传的不是聊天上下文，而是可以继续执行的工作状态。

这里还要把三件事分开：聊天记录是历史，摘要是当前工作集的一部分，代码库、测试系统、部署平台和业务数据库才可能是某类事实的权威来源。摘要能让下游快速进入状态，但不能替代事实出处。

Agent 交接对象与权威事实

图 2：交接对象、当前工作集与权威事实来源

任务状态也不能只放在消息里。实际系统里，至少要有一份类似 agent_task 的执行记录，能回答“谁在做、做到哪一步、基于哪一版、已经尝试过几次”：

agent_task
  ├─ global_task_id / sub_task_id
  ├─ agent_id
  ├─ input_snapshot
  ├─ status / version
  ├─ attempt / lease_until
  └─ result_ref

global_task_id 串起一次全局任务，sub_task_id 识别具体工作，attempt 区分不同执行尝试，version 帮助系统拒绝过期更新，lease_until 则表示当前认领在什么时候失效。

通信消息会延迟、重复，也会乱序。比如 Executor 的第一次执行看起来超时了，但其实已经在远端完成；调度器以为失败，启动第二次尝试。第二次先回报完成，第一次迟到的消息又把任务改回失败。

这就是通信状态不同步。状态更新如果只按消息到达顺序处理，旧消息就可能覆盖新状态。attempt、version 或带时间条件的更新，至少要让系统识别这是一条过期消息。

如果全局状态和子任务记录在同一个数据库里，可以在同一事务中更新。跨服务时就不能默认有这个事务边界，通常要用事件记录、Outbox 或补偿流程来把两边重新对齐。Outbox 的意思很简单：先把待发送事件和本地状态写进同一个事务，再由后台任务异步投递，避免数据库已经变更、消息却没有留下来的情况。

第三问：两个 Agent 的结论不一样，谁来拍板？

不一样不一定是问题。

一个 Researcher 认为瓶颈在数据库，另一个认为连接池才是主因。只要它们的证据、假设和时间范围写清楚，这种分歧反而有价值。多 Agent 的独立探索，本来就不是为了让大家从第一句话开始保持一致。

真正麻烦的是，它们基于不同的现实，却被系统当成同一份现实来汇总：

一个基于 commit-a，另一个基于 commit-b；
一个引用线上 14:00 的日志，另一个引用 16:00 的指标；
一个看到的是发布前配置，另一个看到的是发布后的配置。

Orchestrator 如果只是把几段自然语言拼成一段流畅总结，表面上没有冲突，实际上已经丢掉了判断依据。

数据汇总不能只做文本拼接。不同 Agent 至少要对齐结果的结构和状态，让每条结论都能回到输入快照、来源、证据和产物。结果可以先标成“候选”“已验证”“冲突”或“已否决”，汇总器据此决定哪些内容能进入最终结果，哪些只能作为待处理线索。

异构 Agent 的问题也会在这里暴露出来：一个返回指标和证据，另一个只返回自然语言，第三个把“执行成功”和“业务问题已经解决”放进同一个字段。它们都能传输，不代表它们可以比较。

我会先定义版本化的结果契约，或者在接入层加适配器，把不同 Agent 的输出转换成同一种结构。这里的协议不是为了让 JSON 看起来整齐，而是为了让系统知道这条结果基于什么、证明了什么、还缺什么。

Agent 产出的内容也不适合一生成就写进共享记忆。更合适的顺序是先作为带来源的候选主张保存，经过实体、关系、时间和来源检查后，再进入可复用的事实层。共享记忆可以记录引用和状态，但不能取代代码库、测试系统、部署平台或业务数据库。

Reviewer 也不只是再生成一段意见。它要能回到原始证据，明确什么情况需要否决，并且有权让任务退回重查、换一条路线、缩小范围或请求人工确认。如果审查结果不能改变后续状态，那它更像一条评论，不像系统的一部分。

Google Antigravity 的 Teamwork 值得参考的地方，正是把候选生成、压力测试、综合和迭代放进一个循环。被否定的路线和反对意见还能影响下一轮综合。审查只有改变了后续动作，才算进入了系统，而不是多了一段评论。

第四问：Agent 说“完成了”，系统为什么相信它？

“代码已经写入”，只能证明文件发生了变化，不能证明问题解决了。

“测试通过了”，也不能只看 Agent 回复里的这一句话。至少要知道测的是哪个 commit，执行了什么命令，退出码是多少，报告在哪里，Reviewer 有没有留下 blocker，测试之后工作区有没有继续变化。

所以，“完成”应该由验收条件定义，并由运行时留下证据。

完成是状态机里的一个状态，不是 Agent 回复里的一个句号。

工具超时也是同一个问题。查日志的工具超时了，通常可以再查一次；发消息、发布代码、修改数据库或发起退款的调用超时，调用方没有拿到结果，却不能据此断定外部动作没有发生。

这时不能把所有失败都处理成“再试一次”。写操作先带幂等键，超时后查询远端状态，再根据“未执行、已执行、状态未知”进入不同分支。只有确认可以安全重放时，才重新调用；无法确认，就保留人工确认或补偿入口。状态未知，不等于失败。

多 Agent 还要继续追问：部分 Agent 失败以后，究竟重试哪一段？

假设 Researcher 和 Executor 已经成功，Reviewer 因为网络问题失败了。如果调度器把整个全局任务重新跑一遍，前面的查询会重复执行，Executor 的写操作甚至可能再次落库。查询重复一次通常只是浪费，带副作用的动作重复一次就可能产生脏数据。

因此，失败状态应该落在子任务层，而不是只在全局任务上记一个失败。子任务至少要能区分“未执行、执行中、已完成、失败、状态未知”。重试优先针对失败的子任务；状态未知时先查远端；确实需要重放时，用 global_task_id、sub_task_id 和业务动作组成幂等键，再由数据库唯一约束或下游接口保证不会产生第二次副作用。

调度器重启以后，也不能把所有未结束任务重新派发一遍。任务认领通常需要租约和心跳：在租约有效期内，任务属于当前 Agent；租约过期后，新的执行者才可以接管。接管前还要结合执行记录确认，避免旧 Agent 只是暂时失去联系，却被两个执行者同时操作。

全局任务状态机加上子任务的最终一致性补偿，是一个比较稳的起点。某次状态更新没有同时到达所有服务，后续补偿任务可以根据记录把它们重新对齐。这不意味着所有场景都要上分布式事务。

到了生产环境，我会继续看任务重复率、状态冲突率、补偿成功率、调度可用性和状态未知的积压量。历史任务归档前，要确认没有活动租约、重试或补偿；具体保留多久，应由业务和审计要求决定。

Agent 说发生了什么，不等于系统能证明发生了什么。版本、工具结果、副作用和验收证据，最后都要回到运行时记录里。

把 Agent 放回传统架构里

这些问题放回传统架构，其实都能找到对应物：任务边界像服务边界，交接对象像 API 契约或领域事件，权威事实像主数据，状态推进像工作流，超时恢复像幂等命令和补偿事务。换个说法，多 Agent 并没有绕开分布式系统那些老问题，只是把执行者从服务和线程换成了会自主判断的 Agent。

Agent 只是把问题放大了。同一个输入不一定得到同一个输出，上下文会变化，工具调用还可能产生真实副作用。模型可以负责判断下一步做什么，但不能独自定义事实、状态和完成条件。模型负责判断下一步，运行时负责证明这一步确实发生过。

这也是 Harness 需要承担的部分：给 Agent 正确的工作集，限制它能做的动作，记录真实发生的结果，并在失败以后把任务带回可以继续处理的状态。

回到最开始的面试，我真正想听的不是一串架构名词，而是能不能围绕 user-service 把这条链讲完整：为什么拆，交什么，依据哪一版，冲突怎么处理，失败从哪里恢复，凭什么算完成。

技术选型可以不同，边界不能空着。
