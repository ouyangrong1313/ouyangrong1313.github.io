## 文章导语

这篇文章的起点很直接：很多人以为“模型够强，剩下交给提示词”。但把 Agent 真正做成能在生产环境稳定完成任务的产品后，会发现模型只承担其中一层；工具接入、上下文组织、权限边界、结果验证、反馈纠正和跨会话延续，都会直接影响产品是否可靠。

作者把全文拆成两段：前半段解释 Function Call / System Prompt / MCP / Skill / Plugin 这些用户在 Agent 产品里能感知到的概念；后半段进入 WorkBuddy 的产品实践，讨论 Context Engineering、Memory、Harness Engineering、Loop Engineering，以及这些工程层为什么最后仍然会撞上“业务正确性验证缺口”。

它最大的价值不是某个单点技巧，而是把“模型 -> 能力层 -> 上下文 -> 记忆 -> Harness -> Loop -> 验证边界”串成一条连续链路。

## 一、先把模型看成一个无状态函数

作者建议产品侧先把模型抽象成一个函数：

`输出 = 模型(系统提示词 + 工具 + 会话历史 + 其他上下文 + 用户指令)`

这个抽象背后有两条工程约束：

1. **模型无状态**：它不会自动记住上一次调用的内容。产品必须在模型外维护对话历史、工作进度、Memory、数据库等状态，再按需注入当前调用。
2. **知识有截止日期**：训练之后发生的事，模型默认不知道。实时信息、外部数据、文件内容、数据库记录都要通过工具拿到，再放进上下文。

围绕这个抽象，作者顺带复盘了模型的三段训练：

1. **预训练**：在海量文本上做“根据前文预测下一个 token”，学语言、世界知识和部分推理。
2. **后训练**：用问答、工具调用、安全边界等数据把模型变成能听指令的助手。
3. **偏好优化 / 强化学习**：在多个候选回答或执行路径里，通过人类反馈和评分，让模型更倾向选对结果、效率和规范都更好的路径。

结论是：模型本身负责语言理解、推理和生成；但像联网、读文件、查数据库、改代码、发请求这种动作，都需要产品额外提供工具和运行环境。

## 二、用户能感知到的四个概念：Function Call / MCP / Skill / Plugin

### 2.1 工具调用：模型怎么请求执行动作

Function Call 的分工非常清楚：

- **模型**：根据用户目标生成结构化调用请求
- **Agent / 宿主系统**：校验参数、检查权限、执行 API / 脚本 / 本地函数、把结果写回上下文

作者强调一个很容易被忽略的点：真正持有 API Key、发请求、改数据的不是模型，而是 Agent。因此高风险操作能不能被拦住，关键不在 prompt，而在模型外的执行层：

- 参数校验
- 权限审批
- 审计日志
- 错误回传

### 2.2 System Prompt：给 Agent 一个稳定角色

有了工具调用，Agent 具备执行能力，但还缺一个稳定的工作角色。System Prompt 在 WorkBuddy 里的职责包括：

- 角色与目标
- 能力地图
- 工作原则
- 安全与权限边界
- 交互风格
- 当前环境信息

文章给出的原则是：System Prompt 只能引导，不能强制。真正的权限校验、Sandbox、Approval Gate 和审计仍然必须由模型外部机制执行。

### 2.3 MCP：外部系统怎么标准化接入

MCP 解决的是外部能力接入的标准化问题，而不是“再多一个工具协议”。

作者用很清楚的方式把 MCP Server 的三种原语拆出来：

1. **Resources**：只读材料，由 Agent 或用户决定何时读取并注入
2. **Tools**：模型在推理时主动触发的动作
3. **Prompts**：由用户主动点选的模板消息

关键点有两个：

- MCP 统一的是连接协议，不是底层实现；Server 背后仍然可以是 REST、数据库或 SDK
- 设计 MCP Server 时，不要照搬底层 API，而要按用户意图组织工具；例如把多个“创建 / 更新 / 关闭 Issue”的接口，抽象成少数对 Agent 更好理解的动作

文章还提到 MCP Apps 这条新路线：面向模型的摘要继续进上下文，面向用户的结构化界面数据直接交给 UI 渲染，以减少上下文占用。

### 2.4 Skill：一类任务应该按什么流程做

Tool 解决“一个动作”，Skill 解决“一类任务的做法”。

文章用“提交 PR”举例：它不是一次 API 调用，而是一串经过验证的工作方法：

1. 读 AGENTS.md / WORKBUDDY.md / 仓库规范
2. 检查 git status，不覆盖未提交修改
3. 阅读 diff，识别范围与风险
4. 运行格式化、类型检查和测试
5. 仅在验证通过后生成标题和描述
6. 确认用户授权后再 push 和创建 PR

Skill 的价值在于把“长期有效的做法”沉淀成可复用的流程、约束和完成标准。

### 2.5 Plugin：一组能力怎么打包分发

Plugin 解决的是能力组合怎么安装和分发。它通常把这些东西打成一包：

- MCP / Connectors
- Skills
- Rules
- Hooks
- Assets / Templates

所以四个概念的边界可以概括为：

- **Function Call**：模型如何请求动作
- **MCP**：外部系统如何标准化接入
- **Skill**：一类任务怎么做
- **Plugin**：一组能力如何安装和分发

### 2.6 外接能力怎么选形态

作者最后补了一层很实用的判断：设计一个外接能力时，不能只问“能不能接进来”，还要问“该以什么形态接进来”。

- 稳定、底层、低延迟的能力，优先做内置 Tool
- 外部系统接入，更适合 MCP / Connector
- 高频、稳定的流程，更适合 Skill
- 同时包含连接、规则、Hooks 和模板的能力，更适合 Plugin

判断标准包括：

- 能力边界
- 更新频率
- 权限风险
- 上下文成本
- 执行延迟
- 跨产品复用价值

## 三、一次完整任务的信息流

文章用一个真实的调研任务，把前面所有概念串起来：

“调研 OpenAI、Anthropic、LangChain 在 Harness Engineering 上的实践，整理核心观点、解决的问题和对团队的借鉴，输出一份带引用的大纲。”

WorkBuddy 的执行过程大致是：

1. 检查当前 Workspace 里有没有现成资料
2. 读取与任务相关的 Memory
3. 查找适用的 Skill 和规则
4. 连接内部数据源
5. 拆分任务并分配给 Sub-agent 并行调研
6. 汇总各子任务结果
7. 补齐缺口
8. 生成大纲并保存任务状态

作者把这个过程归到 ReAct 循环：

**判断 -> 行动 -> 观察 -> 再判断**

而正是因为每轮观察结果都会回到上下文里，主上下文才会不断变长，这就逼着产品做 Context Engineering。

## 四、Context Engineering：模型这一刻该看到什么

作者给了一个非常清晰的定义：

> 在一次模型决策前，设计哪些信息进入上下文、以什么形式进入、放在什么位置、何时更新或移出，以提高模型做出正确下一步决策的概率。

它被拆成五个动作：

1. **Write**：把目标、规则、环境和任务状态显式写进上下文
2. **Select**：只挑当前一步需要的信息进窗口
3. **Retrieve**：把当前不在手的信息按需拉进来
4. **Compress**：把长内容外置到文件，只留结论和证据位置
5. **Isolate**：把旁支任务放进独立会话或 Sub-agent，避免污染主上下文

### 4.1 Prompt Cache：上下文管理的第一要义

多轮对话不是每轮都重新算全部前缀。Prompt Cache 依赖前缀复用，所以 WorkBuddy 在上下文组织上遵循几条规则：

- System Prompt、基础工具定义、长期规则放前面并尽量稳定
- 对话历史采用追加，不修改旧消息
- 文件、任务进度、时间、工具结果等动态内容追加到后面
- 工具和 Skill 按需加载
- 只有在过长需要压缩或必须纠错时，才接受前缀变化和缓存重算

作者的判断是：随着用户对积分和成本越来越敏感，缓存命中率会成为越来越重要的工程指标。

### 4.2 渐进式加载：长结果和大工具集

工具和 Skill 越多，占的上下文越大，模型选择越困难。WorkBuddy 的做法是：

- 先暴露工具名称和简要描述
- 任务需要时再加载更完整的工具定义
- Tool Result 过长时分页、截断或写入文件
- 截断时明确告诉模型“结果未完整”，并附带继续读取的方法

Skill 也采用同样机制：先看名称和描述，确认匹配后再读完整 `SKILL.md` 和参考材料。

这让作者得出一个非常重要的判断：**Context Engineering 追求的是相关、准确、及时，而不是单纯堆 token。**

## 五、Memory：让正确的过去在正确的时候重现

文章把和记忆有关的内容拆成三层：

1. **聊天历史**：事情发生过，但不一定该影响未来
2. **当前工作空间的工作记忆**：例如项目进度
3. **长期 Memory**：在用户发起当前任务前，就能默认影响后续行为的信息

### 5.1 WorkBuddy 长期 Memory 的五类记忆

作者把长期记忆分成五类：

1. **稳定事实**：城市、工作语言、长期默认假设
2. **用户知识背景**：决定解释深度和术语密度
3. **行为信号**：多次观察到的稳定使用模式
4. **表达偏好**：只影响“怎么说”，不改变“事实是什么”
5. **会话延续信息**：当前任务的进度、未完成项、下一步

### 5.2 为什么 Procedural Memory 不进长期记忆

这是全文很有启发的一段。作者明确反对把“做事方法”写进长期 Memory：

- 一次局部经验容易被误升为通用策略
- 会干扰模型根据当前证据重新推理
- 实际上相当于偷偷改写动态 System Prompt
- 如果缺少稳定的评测和回滚，会积累偏见而不是经验

因此 WorkBuddy 的分工是：

- **用户事实和历史状态** -> Memory
- **经过验证的工作方法** -> Skill

这让工作方法具备版本化、可评审、可测试、可回滚和按需加载的条件。

### 5.3 记忆的作用域分层

同一种记忆还分作用域：

- 当前轮临时上下文
- 会话 / Thread 记忆
- 项目 / Workspace 记忆
- 用户级记忆
- 团队 / 组织记忆

作者总结得很准确：**让正确的过去，在正确的时候，以正确的作用域，正确的方式重新出现。**

## 六、Harness Engineering：引导、约束与整合

到这里，文章把问题从“Agent 是否知道得够多”切到“Agent 开始行动后，怎么不失控”。

作者把 Harness 拆成三类能力：

1. **驾驭（Steer）**：控制方向、速度和停止时机
2. **约束（Constrain）**：防止越权、误删、误发和高风险操作
3. **整合（Integrate）**：把 tools、memory、hooks、agents、automation 组装成可运行系统

### 6.1 三家实践对照：OpenAI / Anthropic / LangChain

文章把 WorkBuddy 放进三家公开实践里做对照：

- **OpenAI**：Codex 侧重点在代码内部质量、结构约束、浏览器验证和周期性重构
- **Anthropic**：关注长任务的状态化交接、过早完成、自评不可靠、执行与验收分离
- **LangChain**：给了一个更宽的定义，几乎把模型之外的一切都纳入 Harness，并强调 compaction、tool offloading、skills 渐进加载和 loop 持续执行

### 6.2 WorkBuddy 的五层 Harness

WorkBuddy 把 Harness 设计成一个“前馈 + 反馈”的控制系统。

五层结构如下：

1. **运行环境层**：文件系统、Shell、Sandbox、Browser、MCP / Connectors、权限边界、Approval Gate、Allowlist / denylist
2. **引导层（Feedforward）**：项目上下文、环境上下文、规则与风格、工具使用规则、Skills、规则文件、Prompt Cache 组织方式
3. **反馈层（Feedback）**：工具结果里的可纠正信息、时间戳保护、lint / 类型检查 / 测试 / 构建 / 审查 Agent / Audit log
4. **编排层**：渐进式加载、意图识别、路由、多模型路由、Teams、多 Agent 协作、并行工具调用
5. **迭代层**：随模型能力升级精简上下文、根据失败模式补约束、适配不同模型、根据重复反馈补新机制

作者的核心原则是：

- 能用确定性程序解决的问题，优先交给程序
- 需要语义判断的问题，再交给审查 Agent
- 新机制必须基于重复出现的失败证据，而不是一次偶发现象

### 6.3 使用者视角的四类组件

借用 OpenAI Codex 的实验总结，作者把使用者侧 Harness 归成四类：

1. **上下文工程**：分层规则文件、OpenSpec、Skills、Slash 命令
2. **架构约束**：本地检查、Git Hooks、CI 门禁、审查 Agent
3. **反馈循环**：Post-edit checkpoint、本地检查、CI、Dogfood Skill、Agent Browser
4. **熵管理**：周期性扫描规则漂移、历史代码违例、过期依赖、运行时健康

## 七、Loop Engineering：任务如何跨时间继续

作者把 Loop 定义为：让 Agent 可以被持续触发、连续执行、验证结果、记录进度并再次运行的工程机制。

它和前面三层的关系被清楚地区分出来：

- **Prompt Engineering**：这次请求怎么表达
- **Context Engineering**：这次决策前模型该看什么
- **Harness Engineering**：Agent 如何被引导、约束、验证和纠正
- **Loop Engineering**：任务如何被触发、流转、重试和停止

文章强调一个非常关键的辨析：

> Goal 不等于 Loop。

长期目标只是状态组件；真正的 Loop 还需要：

1. Trigger / Automation
2. Isolated Workspace / Worktree
3. Skills
4. Tools / Connectors / MCP
5. Sub-agents
6. Memory / Durable Artifacts
7. Sensors / Evals
8. Stop Conditions / Budget

作者用“每天检查依赖安全更新”的例子说明一个完整 Loop：

- 09:00 定时触发
- 创建独立 worktree 和任务记录
- 读取仓库规则和 `dependency-update` Skill
- 查询更新和漏洞
- 选择可独立验证的一项修改
- 运行安装、类型检查、单测、构建、漏洞扫描
- 失败则回传错误并在限定轮数内修正
- 通过则生成 PR 草稿和风险摘要，交由人审批
- 写入本轮结果、未解问题和下次运行的交接信息

## 八、还没解决的问题：业务正确性验证缺口

文章最后的落点很克制。它没有说“只要 Harness 做好了就能全面自治”，反而把没解决的问题摊开讲。

最核心的是**业务正确性验证缺口**，原因包括：

1. PRD 往往只描述单功能，不覆盖组合行为
2. 实现和测试可能共享同一个误解
3. 很多业务意图没有可计算的判定标准
4. 核心业务错误成本极高

因此作者给出一个很实用的判断框架：当业务正确性缺少可靠验证时，AI 自治度必须随风险提高而降低。

- 一次性脚本、内部工具 -> 自治度可以高
- 公开 API、跨系统改动 -> 中等
- 支付、风控、订单等核心业务逻辑 -> 低

文章还补了另外几个边界：

- **代码库的 Harnessability** 决定建设难度
- **案例有适用边界**，不能直接照搬
- **AI 可能推动技术方案标准化**
- **Harness 需要持续投入，不是一次性配置**
- **人仍然负责目标、标准和最终责任**

## 九、总结

作者最后把全文压成五句：

1. 模型是推理和生成引擎，但不会自动保留状态、联网或执行外部动作
2. Function Call / MCP / Skill / Plugin 构成 Agent 的能力层
3. Context Engineering 决定模型当前看到什么，Memory 决定哪些过去会重新出现
4. Harness Engineering 把指引、能力、权限、反馈、验证与编排组成可信系统
5. Loop Engineering 把这套系统放进时间维度，让任务能被反复触发、检验、交接和收敛

全文真正的两句核心结论是：

- **模型决定能力上限；上下文和 Harness 决定这个上限能否稳定落地。**
- **人负责选择方向、定义标准并承担责任；Agent 负责执行、验证和加速迭代。**
