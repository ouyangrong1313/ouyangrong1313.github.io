## 正文

当 Agent 成为团队一线生产力，知识供给的问题随之暴露：检索不准、注入低效、过时内容越堆越多。本文记录安全中心团队从定目标、搭体系到跑通知识飞轮的完整过程，包括关键决策背后的思考、踩过的坑，以及可直接复用的方法。

当团队开始用 Agent 做研发和运营，一个问题很快浮出来：Agent 的输出质量，直接取决于你能给它什么质量的知识。怎么让知识「产得出、找得准、喂得进、淘汰得掉」，是每个上了 Agent 的团队都要解决的工程问题。

### 为什么 AI 时代需要重新建知识库

团队以往的知识散落在需求文档、评审记录、代码审查评论、个人经验里。新人要搞清某个模块的历史决策，得翻 iWiki、问老同事、再去代码仓库看提交记录；同样的坑会被不同人反复踩。

过去知识管理是「人写 -> 人找 -> 人读」。Agent 上一线后，关键变成两件事：检索精度，即面对两千篇文档时准确找到当前问题相关的两三篇；注入效率，即使找对文档也不能把整篇塞进上下文，因为 token 有成本、无关内容会干扰。结构化知识应写明适用条件、核心结论、应做和不应做项，但不应把给人看的知识和给 Agent 看的知识做成两套：好的结构化知识应当人能读懂、Agent 也能消费。

传统知识库追求存得多；AI 时代的知识底座追求匹配准、注入快、过时内容可淘汰。模式相应从人写人读转为流程自动生产、Agent 消费、人做决策纠偏；从长文档转为人机共读的结构化内容；从静态存储转为有保鲜、退场和复活机制的飞轮。

### 先定义目标和边界

动手前先回答四个问题：服务什么场景、谁来消费且如何消费、知识库装什么、怎么算成功。文章的案例是端到端研发交付，12 个研发 Agent 是第一消费者，研发同学审核纠偏，新人也可学习历史决策；知识包括技术方案骨架、踩坑、需求模板、复盘和仓库架构。

成功指标包括注入命中率、画像覆盖率、盲搜下降率、返工下降率和对话采纳率。原文案例称需求交付从天级压到小时级、代码审查轮次从 2-4 轮降到 1.1 轮，且 99% 以上知识由流程自动沉淀；这些均为作者团队自述，未在本次归档中独立核验。

知识沉淀绑定在研发流程的必经节点。作者设置硬规则：没上线或没关联仓库的知识只能暂存，不能进入 Agent 引用池；上线后才自动转正。通用原则是让知识成为流程副产品，而不是额外写作任务。

### 六步搭建 AI 知识底座

1. **知识盘点**：按四层盘点。L1 公共基础（规范与代码示例）、L2 业务领域（平台文档和架构）、L3 场景策略（规则和 Prompt 模板）、L4 事件增量（新规则和上线后的踩坑卡片）。
2. **知识库选型**：文档型用于背景、教程和架构说明；结构化存储用于规则明确、需要精确匹配的内容；RAG 向量型用于大规模语义匹配。作者建议组合使用。
3. **工具平台**：优先使用现有中台；以 MCP 适配层将数据库、日志和模型能力封装成标准工具。按业务域拆分多个 MCP Server，避免单 Server 工具过多造成 token 消耗和隔离不足。
4. **知识生产**：流程自动沉淀、复盘 Agent 周期性更新、Agent 自动生成结构化知识并做准召评估、运营处置时即时沉淀四种模式并行。
5. **知识治理**：准入双门禁、三层质量分级、有效期保鲜、自动退场与复活兜底。原文示例为默认 90 天复校验，零引用过期条目归档，后续被引用或点赞可自动复活。
6. **分发与消费**：平台按 Agent 场景主动注入知识包，而不是仅依赖 Agent 自行检索。每次注入都记录消费，便于追踪知识被谁使用、使用次数和无引用条目。

### 让知识飞轮运转

飞轮由生产、提炼、注入、消费、反馈、保鲜组成：交付越多，知识越厚，Agent 越强，交付更快。文章列出三个设计点：

- **用即积累**：复盘 Agent 定期分析会话，遇到未命中问题就提交知识更新；用户对话成为知识质量的隐式检验。
- **注入即记账**：自动记录每条知识的使用轨迹，用看板识别热门与无效内容。
- **敢于不沉淀**：无复用价值的需求不进入知识库；通过异步蒸馏降噪，优先提高知识密度而不是规模。

文章反对四类做法：用 KPI 强迫贡献、只进不出的无限膨胀、让专家隐性知识随人员流失、贡献与组织认可脱节。对应措施是流程自动沉淀、保鲜与退场机制、复盘和交接清单、可引用的贡献数据。

### 作者自述的效果与边界

原文称其系统带来组织记忆、新人加速、知识平权和自增强飞轮；新人上手从 30 天缩至 10 天，代码审查平均耗时降至 3.4 分钟，风险事件日处置量从 400 条升至 1,200 条。文中还称 99.7% 知识由流程或 AI 自动沉淀、过期治理完成率 90.2%、Agent 月调用 2,000 余次。

这些数字来自作者团队的实践描述，适合作为设计假设和评估指标的候选来源，不应直接外推为普遍因果结论。文章的可迁移建议是从一个具体场景先跑通闭环，再横向扩展；先让飞轮转起来，比一开始追求覆盖全部知识更重要。
