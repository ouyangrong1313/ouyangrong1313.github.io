## 核心观点

1. **意图识别只是业务理解的入口，不是业务理解本身**：识别出 `cancel_order` 并不等于知道哪张订单、当前是什么状态、哪版规则生效、谁有权执行以及结果是否真的完成。
2. **真正的业务语义至少要补六项**：统一术语、业务对象、实时状态、规则版本、权限边界、可执行动作，缺一项都容易把“听懂了”误当成“能动手了”。
3. **RAG 负责补背景，不负责裁决事实**：政策、SOP、历史案例适合检索；实时状态、权限结果、动作完成证据必须回到业务系统、授权系统和审计链路里读取。
4. **自然语言最好先编译成业务决策记录**：让 LLM 负责整理目标、对象线索和待确认项，让业务系统负责绑定真实对象、实时状态、规则版本、审批要求和动作计划。
5. **生产可用的 Agent 业务执行，最好拆成理解层、决策层、执行层**：理解层处理模糊表达，决策层绑定对象/状态/权限，执行层控制副作用并验证状态变化。

## 7 个分析角度

### 1. 为什么“听懂用户”还远远不够

- 分析：文章一开始就拿“取消订单并退券”的客服请求说明，模型可以正确抽出目标意图，却仍然不知道具体订单、当前履约状态、券类型、退款去向和操作权限。
- 开头钩子：
  1. Agent 最大的错觉，不是没听懂，而是太早以为自己听懂了。
  2. “取消订单”四个字背后，往往还藏着五个没被系统回答的问题。
  3. 识别出意图，只是拿到了业务入口的门牌号。

### 2. 为什么业务知识不能被等同成知识库

- 分析：文档、政策和案例可以检索，真实业务还多出三类动态事实：某个对象此刻的状态、当前用户当前组织里的权限、刚才那次动作到底成功到哪一步。
- 开头钩子：
  1. 资料找到了，不等于业务就懂了。
  2. RAG 能把政策送到模型眼前，送不过来的是当前订单状态和真实权限。
  3. 真正决定能不能执行的，往往不是知识库里那一页文档。

### 3. 六项业务语义为什么是最小语义层

- 分析：统一术语、业务对象、实时状态、规则版本、权限边界、可执行动作，是让一句自然语言真正落到业务现场的最小集合。
- 开头钩子：
  1. 不是所有团队都缺大模型，很多团队缺的是一张对象-状态-权限清单。
  2. 业务含义如果还散在 Prompt、口头经验和数据库字段里，Agent 只是替你更快地猜。
  3. 让 Agent 理解业务，第一步不是画图，而是先把词说准。

### 4. 为什么对话状态、业务状态、执行状态必须分开

- 分析：用户说“还没发货”只能进入对话状态，不能直接写成履约状态；订单真实状态、流程执行状态和会话推进状态分别属于不同真相源。
- 开头钩子：
  1. 最容易做坏的一步，是把“用户刚才说了什么”和“系统现在真的是什么状态”放进一个字段。
  2. 会聊天的 Agent，不代表会读状态。
  3. 对话顺不顺和业务真相往往不是一回事。

### 5. 为什么一句人话最好先编译成业务决策记录

- 分析：文章给出的 JSON 不是“给模型更多输出格式”，而是在强制分工：目标和对象线索可以由模型提取，状态、规则、计划和审批必须绑定明确真相源和策略系统。
- 开头钩子：
  1. 与其让 Agent 直接动手，不如先逼它交一份业务决策记录。
  2. 最值钱的不是 prompt，而是那张能被审计、能被验证、能被暂停的中间表。
  3. 自然语言进入业务现场前，最好先过一次编译器。

### 6. 为什么五份小合同比“企业知识库大全”更容易起步

- 分析：术语、状态、规则与权限、工具、验收五份小合同，比一开始做大而全知识平台更适合作为真实流程的起点。
- 开头钩子：
  1. 大而全知识库经常让团队更安心，却不一定让 Agent 更能执行。
  2. 真正适合起步的，不是知识库大全，而是五份写得清楚的小合同。
  3. 把“退款完成”定义写清楚，往往比再补一轮 Prompt 更值钱。

### 7. 为什么评估和放权边界要一起设计

- 分析：只看 intent accuracy 会把理解层、决策层、执行层的问题混成一个数字；上线初期更该先做历史回放、只读影子、低风险放开，再按失败证据扩大边界。
- 开头钩子：
  1. 业务 Agent 上线初期，最该少做一点，而不是多做一点。
  2. 一个整体 Accuracy，通常掩盖了三种完全不同的故障。
  3. 让 Agent 多自动一步之前，先问清楚：谁负责补偿，谁来证明它做对了。
