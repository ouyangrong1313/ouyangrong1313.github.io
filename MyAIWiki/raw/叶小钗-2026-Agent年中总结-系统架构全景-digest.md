## 一句话

Agent 的系统设计重点，是把模型的动态判断接入有权限边界、有状态恢复和外部验收的执行过程；Harness、Runtime、业务系统、Workflow、Skill 与评测分别承接不同职责，不必被实现成相互独立的服务。

## 五个核心观点

1. **Agent 是运行中的判断循环**：模型根据工具反馈决定继续、补查、调整或停止；Workflow 则预先固定一部分路径，两种方式可以组合。
2. **架构要分清控制、执行与业务事实**：Harness 组织上下文、工具、循环、权限和记录；Runtime 提供资源环境；CRM、ERP 等业务系统仍负责事实、事务和权限规则。
3. **工具与上下文决定判断质量**：工具描述需说明职责、参数、适用和失败情形；上下文要有明确来源、语义、时效和可见范围，状态摘要需支持继续执行。
4. **Skill 承载可复用的业务方法**：阈值、例外、补查条件、输入输出和转交规则比简单列出步骤更有用；工具粒度需在难以调整与难以组合之间取舍。
5. **可靠性来自可恢复执行和任务级评测**：记录任务状态与外部副作用，重启或超时后核验实际效果；从需求阶段定义任务样例、约束、验收证据和回归方式。

## 七个分析角度与开头钩子

### 1. 什么任务适合 Agent
- 信息能否取得、操作能否调用、结果能否验证、失败能否恢复？
- 如果任务的路径基本固定，为什么一定要让模型重新规划每一步？
- 自主程度应由任务需要决定，而不是由框架能力决定。

### 2. Agent 与 Workflow 如何分工
- 固定流程和动态判断不是二选一，关键在于把变化留在哪一层。
- 报销审核可以固定节点，复杂故障排查则可能需要根据新证据改方向。
- 哪些决定可以预先写成规则，哪些必须等现场反馈？

### 3. Harness、Runtime 与业务系统各管什么
- Agent 返回“完成”之前，谁确认消息真的发出、订单真的更新？
- 控制流程、承载执行和保存业务事实，为什么不应混为一个概念？
- 一张职责图不等于四个微服务，它首先是一种排查和设计方法。

### 4. 工具接口如何帮助 Agent 可靠行动
- “高级查询”听起来强大，却没有告诉模型何时该用。
- 工具失败只返回 `success: false`，下一步还得继续猜。
- 工具契约要覆盖选择、调用、结果解释和失败恢复。

### 5. 上下文与长期任务如何治理
- 数据接进来了，为什么 Agent 仍可能不懂“本月销售额”？
- 任务摘要如果没有保留已确认事项、未完成步骤和证据地址，还能恢复吗？
- 客户资料、团队知识和个人偏好，是否都应自动暴露给同一个 Agent？

### 6. Skill 如何沉淀业务经验
- “搜索、筛选、生成报告”容易写，什么情况该补查才是经验所在。
- Skill 太大难以调整，太碎又会增加选择和组合成本。
- 让 Agent 学会一套方法，究竟要写步骤，还是写判断边界？

### 7. 多 Agent 与评测何时有价值
- 多一个 Agent 带来的并行收益，能否超过协调与一致性成本？
- “任务成功”要看工具返回、交付物，还是实际业务状态？
- 如果模型、工具或 Skill 改了，哪些用例能证明没有退化？

## 最小实践

1. 挑一个具体业务任务，分别列出可固定步骤、需现场判断的分支、人工审批点和不可逆副作用。
2. 设计工具契约时写清用途、不适用场景、参数约束、成功回执，以及权限失效、冲突、超时等可恢复错误。
3. 将任务进度、业务事实、长期知识和原始执行记录分开保存，并为不同数据设置来源、时效与可见范围。
4. 将 Skill 写成可检查的业务方法：输入、输出、判断阈值、例外、证据要求和何时返回人工确认。
5. 在需求阶段建立按任务类型划分的验收样例；分别检查业务结果、约束、权限、实际副作用和运行成本。
6. 对超时或重启场景验证恢复逻辑：先查外部操作是否已经生效，再决定重试、回滚或交给人处理。
