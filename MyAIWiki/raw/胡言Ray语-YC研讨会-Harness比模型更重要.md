## 正文

今天的分享出自最近 Y Combinator 内部的一档闭门分享会——YC Paper Club。这档活动由 YC 资深合伙人 Jared Friedman 发起，本是围绕前沿论文与工程范式做深度的内部研讨。这一期被他特意取名为——Harness 之夜：不讲模型排名，只聊那个长期被视为"边角料"的运行时框架 Harness。



Jared 在开场抛出一个颇有点"叫板"的观察：过去一年多，社区习惯把功劳全部记在模型账上，下意识以为"模型够强，Agent 就水到渠成"。可翻开智能体能力演进曲线会发现——每一次数量级的跨越，推动它的往往不只是模型单体，还有模型的"外壳"。

原始大模型只是一台无状态的图灵机，而配齐了 Harness 的系统，才真正成为一台能自由读写、自我进化的冯·诺依曼计算机。基于这个判断，研讨会系统地梳理了 Harness 从"单轮模板"到"递归自进化"的四代演进，并请来三位一线构建者现身说法：Prime Intellect 的 Seth 讲如何在固定权重下把 ARC-AGI 从 30% 推到 95.5%；斯坦福的 John 讲如何把推理下沉到本地实现 800 倍降本；YC 内部的 Josh 与 Rean 则拆解了支撑全员运营的 QM 系统及三大反模式。

这场研讨的核心主题在于：在模型水平给定的前提下，Harness 的工程深度，才是决定谁能真正把 Agent 做成生产力的分水岭。

Jared Friedman【Y Combinator 资深合伙人 / Managing Director】

欢迎来到新一期的 YC Paper Club。今天我们想聊一个可能正在剧烈改变整个应用层 AI 格局的话题——为什么围绕模型构建的运行时脚手架（Harness），甚至比模型本身的权重更重要。

过去一年半里，几乎所有人的目光都紧紧盯在基础模型的每次发布上：更长的上下文窗口、更密集的思维链、更高的 MMLU 或 SWE-bench 跑分。大家潜意识里默认一个假设：只要模型足够强大，智能体的问题就会迎刃而解。但如果你真正在生产环境里部署过长周期、跨工具的复杂智能体，你会发现实际瓶颈往往并不在模型的推理智力，而在于模型所处的那个“外壳”——也就是 Harness。

如果把大模型类比为计算机体系里的图灵机或者 CPU，那么 Harness 就是让它真正具备实用价值的冯·诺依曼架构和操作系统。它负责管理寻址空间、控制寄存器与多级缓存、编排 I/O 交互，并在发生系统中断时提供异常恢复。今天我们请来了在这个方向上一线深耕的几位核心构建者，一起来拆解这个被严重低估的领域。

Seth Karten【Prime Intellect 核心研究员 / Prime Agent 核心作者】

非常高兴能在这里与大家分享。在进入具体的基准测试之前，我想先梳理一下社区在过去两年里摸索 Harness 过程中的四次范式演进：

第一代：单轮 Prompt 与 Few-Shot 模板


这是最基础的状态。模型被当作无状态的黑盒函数，所有的交互都是纯线性的输入-输出。一旦任务超出一次生成所能容纳的范畴，系统就彻底失效。
第二代：Chain（链式调用）与早期 RAG


以 LangChain 为代表，人们开始把任务拆分成线性的 DAG 流水线，并结合外挂向量库做上下文召回。但这种硬编码流水线极其脆弱，只要中间某一环产生幻觉或偏移，整条链路就会级联崩溃，无法实现自主闭环。
第三代：自治多 Agent 狂热（如 AutoGPT、CrewAI）


这一代试图通过把角色切分给多个独立 Agent 来解决问题，但在工程实践中暴露了致命缺陷：Agent 之间的多轮闲聊迅速消耗 Token，导致上下文窗口瞬间饱和，错误迅速级联放大，系统不可控且成本高昂。
第四代：操作系统内核级运行时与递归自进化（Self-Improving Harness）


这就是我们现在所处的分水岭。模型不再只是单纯输出文本，而是将自己的工作空间当作可编程对象。系统配备持久化的 IPython Kernel、结构化的多级缓存、递归子智能体协作，以及运行时的 /refine 机制——让智能体能够在执行中动态修改自己的提示词、记忆、技能和执行规范。

为了让这个体系运转，我们重新定义了上下文的层级结构：

L1（工作记忆 / 注意力窗口）
：当前轮次直接可见的活跃 Token，极其昂贵且容量有限，必须保持高纯度。
L2（会话级活跃缓存 / KV-Cache）
：保存当前任务相关的中间状态、子会话轨迹和执行日志，由解释器负责显式按需装载。
L3（持久化外部存储 / 长期资产）
：包括项目文档、历史成功的代码片段、蒸馏过的技能库与用户记忆，作为外存按需索引。

Seth Karten【Prime Intellect 核心研究员 / Prime Agent 核心作者】

很多人可能会问：优化 Harness 真的能带来数量级的能力飞跃吗？还是说它只是一种工程调优？

最好的证明就是 ARC-AGI-3 基准测试。在标准的单轮或简单 ReAct 框架下，即使接入当前最顶尖的推理模型，ARC-AGI 的平均得分通常也只在 30% 左右停滞不前。为什么？因为面对此前从未见过的抽象网格推理，模型单凭一次直觉推演极难击中答案。

而在 Prime Agent 中，我们保持底层模型权重完全不变，仅仅构建了一个具备完全编程控制权、持久化 REPL 环境与自修正循环的 Harness。当模型遇到阻碍时，它不是在上下文中盲目重试，而是能够写一段脚本探索规律、调用子进程验证猜想，并在失败后反思并改写当前的探索策略。

结果是：同样的模型，ARC-AGI-3 Best@1 得分从 ~30% 直接跳升至 95.5%，Best@3 甚至达到了 99.97%。

这向我们揭示了一个核心事实：我们今天对基础模型能力的度量，极大程度上受制于脆弱 Harness 所带来的“漏损”。一个设计拙劣的运行时会让模型在语法纠错、上下文迷失和无意义的格式转换中耗尽算力；而一个符合系统工程学原理的 Harness，能真正释放模型底层的最大能力。

Jon Saad-Falcon【斯坦福大学 AI 研究员 / OpenJarvis 创始人】

Seth 刚才讲了在云端使用顶尖模型极限推演的场景，而我们 OpenJarvis 正在探索另一个极端——端侧与本地智能体运行时。

很多人认为要做严肃的智能体任务，必须每一步都调用昂贵的云端超大模型。但如果我们仔细审视日常任务，会发现 80% 以上的操作其实只是文件检索、状态检查、格式整理和局部修改。如果每次动作都发起一次耗时数秒、消耗数万 Token 的云端往返，不仅成本难以承受，延迟和隐私问题也会直接劝退用户。

在设计端侧 Harness 时，我们遵循了三个核心原则：

1. 脑手解耦与本地下沉（Compute Tiering）：


日常的高频观察、工具调用路由和局部纠错完全交给本地运行的端侧小模型（如本地部署的开源量化模型）；只有在遭遇全局策略分歧或复杂多步推演时，才将蒸馏后的最小状态切片投递给云端大模型。这为我们带来了相比纯云端调用接近 800 倍的成本降幅。
2. 上下文渐进式披露（Progressive Disclosure）：


禁止将庞大的文档库或系统指令一次性塞入工作区。所有工具和文件首先仅以极简的元数据索引暴露，智能体根据需要自行发起二级甚至三级精确检索。
3. 不可变审计与快照回滚（Immutable Trace & Rollback）：


端侧环境直接面对用户的真实文件系统。Harness 必须充当一道严格的安全隔离层，每次执行写操作或外部系统交互前都进行状态快照，确保任何失控动作都能原子化回滚。

Josh France & JB Straubel-Regan【YC 内部工程团队】

Josh France：
在 YC 内部，我们目前部署了大约 50 个用于日常运营的自治智能体，统一运行在一个名为 QM 的调度架构下。它们每天处理大量的申请材料初筛、创始人日程协调、内部 Sandbox 运维以及跨部门知识同步。在数万次生产运行中，我们踩过了无数深坑，总结出了多智能体协作的三大经典“反模式”：

反模式一：多智能体自由交谈（The Gossip Trap）


让两个智能体直接在自然语言通道里互相推演讨论，看起来非常美妙，但在生产中是一场灾难。它们会迅速陷入彼此恭维或无休止的低效重述，消耗巨量 Token 却毫无实质产出。我们最终的方案是严格消除 Agent-to-Agent 的自发闲聊，所有多智能体协作必须通过强类型的事件总线（Event Bus）或共享数据表进行异步交换。
反模式二：上帝视角的巨无霸上下文（The Omni-Context Fallacy）


把公司所有 Notion 页面、Slack 频道和业务规范在系统初始化时一股脑塞给智能体。这会导致注意力弥散和指令跟随度急剧下降。
反模式三：缺乏确定性门禁的黑盒执行（No-Gate Autonomy）


完全相信模型自评已经完成任务。智能体对“已完成”的幻觉极强，必须由外部 Harness 编写独立于模型之外的确定性验证规则（如断言脚本、测试用例、编译检查）。

JB Straubel-Regan：
补充一点：企业级 Harness 最核心的基础设施实际上是“状态持久化”与“断点续跑机制”。现实业务中的任务往往跨越数小时甚至数天，外部 API 随时会超时，系统随时可能被中断。如果 Harness 无法把每次决策前的思维状态、局部产物和环境引用进行快照序列化，那长周期智能体就永远只能停留在 Demo 阶段。

现场互动 Q&A

问  未来随着基座模型的持续进化，比如更多模型原生内化了思维链与工具搜索能力，Harness 会不会像当年的许多上层封装一样被底层吞噬、逐渐变得多余？




Seth Karten：

我认为这是一种误解。模型内化的是推理本身的模式，但模型永远无法替代操作系统。无论模型怎么变强，它依然是一个受限于固定上下文长度的转换函数。它无法替你管理与本地操作系统的 Socket 通信，无法凭空维系跨越数周的状态机，也无法决定如何安全地对私有知识库进行分层缓存与淘汰。模型的提升只会让 Harness 变得更简洁、更专注在系统架构本身，而不是让它消失。




问  对于我们正在从零构建 Agent 的团队来说，今天最应该优先投资的是什么？




Jon Saad-Falcon：

停下无休止地追逐每个最新模型权重的脚步。找一个稳定、性价比高的主力模型，把 80% 的工程精力投入到你自己的 Harness 上：去精细化打磨你的工具调用协议、构建稳定可靠的执行沙盒、设计严格的断言校验、并让你的 Agent 具备观察自身历史轨迹并沉淀技能的能力。这是唯一能为你沉淀下确定性技术壁垒的地方。
