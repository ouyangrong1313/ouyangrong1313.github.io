## 核心观点（5 个）

1. **Graph Engineering 不是否定 Loop，而是把多个 Loop 组织起来**：Loop 仍然是基础结构；Graph 只是把自循环、顺序、分支、并行和回修显式放进流程图。
2. **Graph 的准入条件来自复杂度，而不是新词热度**：当任务需要不同角色、条件分支或并行搜索时，一个单 Loop 会角色混乱、控制流拧巴、串行成本过高。
3. **真正的新变量是“节点变成了 AI”**：传统流程图的节点确定可控；AI 节点会理解偏移、写坏状态、路由漂移、互相点头，因此图工程的核心是治理不确定节点。
4. **四个工程模块决定 Graph 是否可运行**：节点要有存在理由，状态要有结构和写权限，路由要尽量代码化，审阅要独立且锚定外部证据。
5. **新手路径应从强 Loop 到小 Graph 再到 Graph 串联**：先练会停止条件、验收标准和检查动作，再画节点/边/状态，最后把复杂任务拆成一串小 Graph。

## 7 个分析角度 + 21 个开头钩子

### 角度 1：范式迁移
- Hook 1：别急着宣布 Loop 死了，它只是被收编进了 Graph。
- Hook 2：AI 工作流的下一步，不是更长的 prompt，而是更清楚的交接关系。
- Hook 3：从一个 AI 自转，到一群 AI 接力，复杂任务的管理方式变了。

### 角度 2：准入判断
- Hook 1：如果一个 Loop 跑到第三轮还没收敛，问题可能不是模型，而是拓扑。
- Hook 2：需要角色、分支、并行的任务，天然不适合塞进一个大循环。
- Hook 3：Graph 的第一问不是“能不能画图”，而是“这个任务有没有真实协同”。

### 角度 3：节点治理
- Hook 1：拆节点不是越多越好，每个节点都要为自己的存在辩护。
- Hook 2：换不了模型、换不了工具、换不了角色的节点，大概率只是装饰。
- Hook 3：一个坏节点不仅会失败，还会把下游状态一起污染。

### 角度 4：状态管理
- Hook 1：Graph 里最危险的不是某一步错，而是错误沿着状态传下去。
- Hook 2：没有 schema 的共享状态，就是让多个 AI 同时改同一本乱账。
- Hook 3：每个节点只能写自己负责的字段，这是多 Agent 协作的最低纪律。

### 角度 5：路由确定性
- Hook 1：能写死的路由就写死，把 AI 留给真正需要判断的地方。
- Hook 2：让 AI 自己决定每一步看起来聪明，复现问题时会变成噩梦。
- Hook 3：Graph 的稳定性，很多时候来自几条朴素的 if/else。

### 角度 6：审阅独立性
- Hook 1：AI 审 AI 最大的问题不是不认真，而是太容易互相同意。
- Hook 2：审阅节点必须换上下文、换视角，最好还能锚定真实测试和证据。
- Hook 3：读可以并行，写要收口；多个 AI 同时改东西才是风险源。

### 角度 7：学习路径
- Hook 1：弱 Loop 拼成的 Graph，只是把失败分布式了。
- Hook 2：先在纸上画出节点、边、状态和停止条件，再谈工具框架。
- Hook 3：复杂任务的秘密不是超级 Graph，而是一串边界清楚的小 Graph。

## 可复用判断框架

### Graph 准入四问

1. 任务是否需要两个以上明确角色？
2. 是否存在“如果 A 就 B，否则 C”的条件分支？
3. 是否存在可以并行推进的独立子任务？
4. 单 Loop 是否已经反复修三轮仍不能稳定收敛？

四问中有两项为真，优先考虑 Graph；只有一项为真，先强化 Loop 的停止条件和验证器。

### 节点存在性检验

- 是否换了模型、工具集或角色视角？
- 是否有独立输入/输出和单一职责？
- 是否能合并进相邻节点而不损失质量？
- 是否只写自己负责的状态字段？

### 最小 Graph 模板

```text
任务：完成【目标】

节点：
- 节点 1：【角色/动作】读什么，写什么
- 节点 2：【角色/动作】读什么，写什么
- 节点 3：【验证/审阅】检查什么，失败如何退回

边：
- 节点 1 -> 节点 2
- 节点 2 -> 节点 3
- 节点 3 通过 -> 结束
- 节点 3 不通过 -> 节点 2，最多 N 次

状态：
- 字段 A：由节点 1 写，节点 2/3 读
- 字段 B：由节点 2 写，节点 3 读
- 字段 C：由节点 3 写，作为是否结束的判定

停止条件：
- 验证通过
- 达到最大重试次数
- 超出预算或状态缺失
```
