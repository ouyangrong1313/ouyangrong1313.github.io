## 核心观点

1. **FDE（Forward Deployed Engineering）把平台能力和客户业务结果绑定交付**：客户购买的不只是软件许可，还包括理解业务、构建方案和落地价值的工程服务。
2. **FDE 的触发条件是复杂度与买家能力错位**：复杂技术平台卖给缺少软件工程能力的业务型企业时，客户无法独立承担采用成本。
3. **共享基础组件是 FDE 能规模化的前提**：客户方案应尽量由可维护的平台能力组合而成，否则定制项目会退化成一次性外包和多仓库维护负担。
4. **平台与实施代码要按通用性分层**：独特需求留在客户代码库，可复用能力回流共享平台；一线项目因此也是产品发现渠道。
5. **FDE 团队的能力模型是客户理解力与软件工程力的交集**：工程师既要能发现真实业务问题，也要能亲手交付可验证的解决方案。

## 7 个分析角度

### 1. 它解决的核心问题
平台供应商如何跨过“买了能力却不会产生价值”的采用鸿沟，把产品交付从功能转成业务结果。

### 2. FDE 何时值得采用
只有当技术复杂度高、买家又缺少开发能力时，FDE 才是必要的市场策略；技术买家通常可由 DevRel 或产品文档服务。

### 3. 为什么共享底座决定利润
统一的数据模型、权限、工作流和应用组件能把项目差异限制在组合层；没有底座，每个客户都会产生独立系统和长期维护成本。

### 4. 定制与产品边界如何判断
判断标准不是“谁提出需求”，而是“是否有多个客户会需要”。单客户特例属于实施代码，跨客户能力才进入平台。

### 5. 组件颗粒度如何选择
客户行业越窄，基础组件可以封装更多业务逻辑；客户越广泛，越适合提供 AWS 式的通用积木。最低限度应避免每次重做数据模型。

### 6. 团队如何避免单点依赖
一个项目配置多名 FDE，并持续共享上下文，才能在人员休假、交接和跨供应商协作时保持交付连续性。

### 7. 对 AI 平台的启发
AI 让定制开发更便宜，却不会自动替客户补齐业务建模、流程设计和验收能力，因此平台越强，结果导向的实施能力可能越重要。

## 开头钩子（每个角度 3 个）

1. **平台采用成本**：软件买回家以后，谁负责把“能力”变成“结果”？ / 许可证之外最容易被忽略的成本是什么？ / 为什么强大平台反而更需要实施工程师？
2. **复杂度错位**：产品复杂不等于必须 FDE，真正的分水岭是什么？ / 把平台卖给非技术买家，会出现哪种采用断层？ / 为什么技术公司能自助使用，传统企业却需要驻场工程师？
3. **共享基础组件**：FDE 团队怎样避免变成外包开发工作室？ / 55 个客户仓库为何会成为维护灾难？ / 可复用底座如何把一次性交付变成产品能力？
4. **通用性边界**：一个客户的需求，什么时候值得写回平台？ / 代码该放实施库还是共享底座，谁来判断？ / 一线项目如何反过来发现下一项产品能力？
5. **组件颗粒度**：基础组件应该做成重型行业底座还是轻量积木？ / 60% 预构建与 40% 定制适用于什么场景？ / AWS 的通用组件经验为何不能机械照搬？
6. **共享知识**：为什么 FDE 项目不能只依赖一个人的记忆？ / 总包、分包关系不清会怎样影响交付？ / 多人协作如何降低客户上下文丢失？
7. **AI 时代 FDE**：代码更容易生成后，客户仍然缺什么能力？ / AI Agent 平台会让 FDE 消失，还是让它更关键？ / 软件供应商能否只交付模型而不交付结果？
