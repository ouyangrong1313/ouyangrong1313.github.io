## 正文

屎山源于不敢删，架构活于持续排熵。

架构腐朽你大概见过这样的系统。

它跑在生产环境里，承载着真实业务。没有人说得清它的全貌，但每个人都记得几条祖训：那个模块不要动；那张表有几个字段没人知道用途，但删过一次，回滚了四个小时；那段看起来明显写错的逻辑，千万别修——下游已经依赖了这个错误。

新人问为什么，老人说不知道，反正别动。

后来，提出重构的人来了一茬又一茬。立项材料都很漂亮：边界更清晰、性能更好、风险更低、可维护性更强。可是两年后，大多数人选择了绕道：在旧系统旁边再起一个新服务，用适配层接上。旧系统没有被替换，只是被包裹；问题没有消失，只是多了一层壳。

这种系统有个不雅但精确的俗名：屎山。

本文想处理三个问题：腐朽是什么？为什么它几乎必然发生？既然无法避免，如何让它慢一点？

先说明立场：软件工程对这组问题没有唯一答案，本文也不假装有。下面是一组分析框架和工作假设，混着一些我在不同项目里看到的真实模式。

### 什么是架构

要谈腐朽，先把"架构是什么"这个基本问题想清楚。

第一层：架构是那张图。这离工程现实最远。图是快照，画完那一刻就开始和现实脱钩。

第二层：架构是决策记录。它不是设计本身，而是"我们为什么这样选"的理由集。

第三层：架构是约束，是"你不许做什么"。这更近了。能做的事无穷多，好架构的贡献常常不是增加自由，而是把危险的自由收掉。

第四层：架构是运行时结构，模块边界、依赖方向、并发模型、可降级能力，这些是代码真正跑起来时呈现的样子。

第五层是我目前更愿意采用的工作定义：架构是那些删起来贵的部分。

这五种理解不互斥，但适合不同的场景：跟业务方对齐用第一层；写 ADR 用第二层；跟工程师对齐用第三层；做技术评审用第四层；判断代码质量用第五层。

用一句话总结这五个层次：架构是那些删起来贵的部分。

### 为什么几乎必然腐朽

"删起来贵"的原因会随时间变化。写代码的时候当然知道模块是干什么的，但人换了一茬又一茬，业务也跑了一年又一年，"这块代码为什么是这样" 变得越来越贵。三年前一个看似可笑的字段约定，今天可能承载着某种合规要求；五年前一个看起来绕的 if 分支，今天可能绕过了某个第三方 SDK 的 bug。

这种"历史负担"在任何长期运行的系统里都会积累。差异只在于积累速度和清理节奏。

光有历史负担还不够。还需要另一个条件——失败成本不对称。

一次错误的修改，代价可能远远高于一次正确的修改。所以工程师会倾向于保守：能不改就不改，能复制就不合并，能加新模块就不碰旧代码。

这两个条件叠在一起：历史负担越来越重，工程师越来越保守，系统就越来越没人敢动。

这就是为什么重构立项总是漂亮，而两年后总会出现一层包裹旧系统的新壳。

### 排熵的几种工作模式

熵增是热力学第二定律，代码世界也守这个规矩。但既然现实世界的生命体能在局部维持低熵，软件工程也能通过持续投入维持局部秩序。下面是几种见过的工作模式：

#### 1. Linux：稳定性预算必须花在正确的边界上

Linux 内核最值得学习的地方，不是"代码量巨大还能运行"，而是它对稳定性的分配极其不对称。

绝大多数 commit 不会进入稳定树。稳定性预算主要花在系统调用边界、驱动 API、文件系统语义这些"对外承诺"的接口上；内部实现频繁重写，反而是好事。

外紧内松。承诺稳定的是接口，不是实现；这是让超大代码库长期演化的关键。

对应到一般应用：识别哪些边界对你的用户是"对外承诺"——SDK 接口、持久化格式、对外 API、监控指标语义——把稳定性预算集中投在这些地方；内部实现可以激进重构。

#### 2. 提交即重构：把重构分摊到每一次提交里

另一种反模式是"等攒够一波再重构一次"。问题在于：

第一，攒得越多越不敢动；
第二，重构 PR 越大越难评审；
第三，大批量变更让 git bisect 失效；
第四，团队里其他人会在这段时间内继续往旧代码上加东西。

把重构分摊到每一次 commit 里会更健康。具体做法：

第一，小步前进。每一次提交只做一件事——要么加功能，要么重构，不混着来。
第二，保持主干可编译。每个 commit 之后，master 应该仍然能编译、能跑测试。
第三，重构不动语义。只改结构，不改行为；用现有测试覆盖；如果没有测试，先补。
第四，重构前先删死代码。删一段没人调用的代码比重构一段更省事，而且常常让重构变简单。
第五，命名即文档。让变量名、函数名、模块名把意图说清楚；十年后回来读代码，靠的是名字。

#### 3. 守卫自检：让检查器先证明自己还能失败

一个永远通过的检查，对判断当前代码是否破坏约束几乎没有信息量。它可能表示系统完美，也可能表示检查器早已失效。

好的检查器应该自带"故障注入"能力：能故意失败一次，让自己证明自己还在工作。

具体到工具链：

第一，CI 上跑 lint、类型检查、迁移检查、测试覆盖率门禁。
第二，每条规则配套一个反例测试：故意写一个违反规则的 commit，让 CI 报错；然后回滚。
第三，检查可执行。不要指望模型"记住"所有规则。让规则进入 CI、类型系统、测试、lint、迁移检查和发布门禁。模型可以忘，流水线不能忘。

#### 4. 删比改更重要

前面说的"祖训"——那个模块不要动，那张表有几个字段别删，那段逻辑别修——每一个都是软件熵的化石。

很多人对祖训的态度是"既然没人敢动，那就留着"。

但每一句祖训背后都有一个真实的失败故事。每次有人试图改动失败，团队就会加一条新的"不要动"。十年下来，祖训变成了一道墙，把整个系统封死在历史里。

删的勇气，比改的能力更难培养。

具体做法：

第一，定期盘点。每季度列一次"已知死代码"清单，列出从未被引用的函数、表里没人读过的字段、SDK 里没人用的方法。
第二，让删变成正常开发动作。在 review checklist 里加一项"能不能删"，让删代码和加代码获得同等待遇。
第三，删前加监控。对要删的代码加引用监控；监控一段时间后真没人调用，再删。

### Loop Engineering

前面说的都是软件工程的老话题。在 AI Coding 工具大规模落地之后，这个老话题有了新的紧迫性。

模型可以一晚上生成几千行代码。工程师用 AI 写的代码量在过去两年增长了一个数量级。

代码生成的边际成本已经接近于零。这不是夸张。一个熟练的工程师 + Claude Code + 良好的 harness，一周可以写出以前一个团队一个月的代码量。

边际成本接近零意味着什么？意味着过去因为成本太高而不敢做的实验，现在变得可以做了。

但这同样意味着腐朽的速率可以翻倍。一个以前需要工程师时间才能写出的烂代码，现在用一个 prompt 就能生成出来。

这就把"持续排熵"的负担放大了十倍。系统熵增的来源从"工程师手写 bug"变成"模型批量生成烂代码 + 工程师审核不过来"。

把架构约束转化为 Loop。

这是一个关键转变：架构师的工作不再是画一张漂亮的图，而是把约束编码到 Loop 里，让 Loop 自动维护这些约束。

"模块不能相互直接调用，只能通过 service mesh"——这不是写在 wiki 上的文档，而是 Loop 启动时自动检查的规约。
"表 schema 一旦发布不允许删除字段"——这不是约定，而是 Loop 在每个 PR 上自动跑的迁移检查。
"新人不能直接 push 到 master"——这不是文化，而是 Loop 在 git push 时自动执行的保护。

架构的代码化：把架构约束从文档转移到代码里。这不是新想法——内核接口稳定性、SOLID、契约测试都是这个方向——但在 AI Coding 时代变得格外紧迫，因为人写代码的速度赶不上代码腐朽的速度。

约束进 Loop，Loop 进 CI，CI 不可绕过。

### 一些收尾的话

架构腐朽不会消失。但可以通过两种方式缓解：

第一，把稳定性预算集中在对外承诺的接口上，让内部实现可以激进演化。Linux 内核就是这么干的。

第二，把架构约束编码到 Loop 里，让机器维护机器能维护的部分。

剩下的部分——架构决策、权衡取舍、命名、删的勇气——还是要人来负责。

最后一句：屎山源于不敢删，架构活于持续排熵。
