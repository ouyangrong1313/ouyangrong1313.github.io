# 原文摘要 - Karpathy autoresearch：从上下文工程到自主研究循环

## 一句话总结

这篇公众号文真正对应的不是“Karpathy 新论文”，而是 `karpathy/autoresearch`：一个把 **固定评测 + 单一可编辑面 + 5 分钟预算 + Git 保留/回退 + 实验账本** 组合成自主研究循环的开源实现。

## 核心观点

1. **可自动评分比“更聪明的 Agent”更先决**：没有稳定、不可被 Agent 改写的指标，就无法比较实验，也无法形成可信的自动循环。
2. **搜索空间必须收窄**：官方只允许改 `train.py`；`prepare.py` 固定数据、时间预算和评测，避免 Agent 通过修改试验条件“刷分”。
3. **固定 5 分钟让实验可比较**：不论模型结构、批大小或优化器怎么变，每次训练都以 300 秒为预算，指标才可横向比较。
4. **Git 不是保存工具，而是棘轮状态机**：改善则保留 commit，持平或变差则回退，分支只累积经过评分验证的改动。
5. **公众号的 DAG 说法是延伸，不是官方基线**：Karpathy 的基础实现是单 Agent、单分支、单 GPU；多 Agent 和 Worktree 是可能的扩展，但必须另行设计共享指标、任务分工和合并边界。

## 实现骨架

1. 选定一个不可变、自动化、方向明确的评分函数。
2. 将评分器、数据和时间预算置于只读区。
3. 把 Agent 搜索空间收束到一个或极少数可编辑文件。
4. 先跑不改代码的基线并记录。
5. 每次变更后提交、运行、抽取指标、写入账本。
6. 指标改善才推进分支，否则回退。
7. 以 Git Diff、日志和 TSV 为验收证据，不以 Agent 自述替代验证。

## 七个分析角度与开头钩子

### 1. 可验证性

- 没有评分器，Agent 不是研究员，只是在随机改代码。
- “代码看起来更好”为什么不能成为自动化目标？
- 能否自动回退，决定了 Agent 能不能放心多试。

### 2. 反作弊边界

- 最危险的优化，是 Agent 把评分器也一起优化了。
- 为什么 `prepare.py` 必须锁死，而不是交给 Agent 重构？
- 一套可被修改的评测，如何制造虚假的进步？

### 3. 固定预算

- 5 分钟不是性能限制，而是实验的共同货币。
- 不同模型怎么在同一张 GPU 上公平比较？
- 时间预算为何比“跑到收敛”更适合 Agent 搜索？

### 4. Git 棘轮

- Git commit 在 autoresearch 里不是备份，而是实验状态机。
- 指标差一点也要回退，为什么这不是浪费？
- 如何让代码库只积累被数据证明更好的改动？

### 5. 上下文工程

- `program.md` 不是一次性 prompt，而是研究组织的可版本化操作规程。
- 为什么人应该改指令文件，而不是和 Agent 逐轮聊天？
- 上下文怎样从聊天记录变成可复用的研究制度？

### 6. 多 Agent 边界

- 单 Agent 已跑通后，为什么不能直接堆多个 Agent？
- 多 Agent 的第一道问题不是模型能力，而是共享评测与写入冲突。
- Worktree 能隔离代码，但不能自动解决指标归因。

### 7. 迁移限制

- 为什么 autoresearch 不能直接套到任意业务仓库？
- 训练损失可自动评分，产品需求如何找到等价指标？
- “永不暂停”在哪些场景会从效率机制变成安全事故？

## 备注与限制

- 官方 README 的运行前提是单张 NVIDIA GPU，已在 H100 测试；需要 Python 3.10+ 和 `uv`。
- `NEVER STOP` 只适用于隔离、低风险、可回退的研究循环。涉及生产发布、外部写操作、安全或数据变更时，必须设置停止条件与人工审批。
