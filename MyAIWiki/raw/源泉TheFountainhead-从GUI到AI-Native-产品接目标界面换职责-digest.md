# 从 GUI 到 AI Native：产品接目标，界面换职责 - 拆解

- 对应原文：[[源泉TheFountainhead-从GUI到AI-Native-产品接目标界面换职责]]
- 来源：微信公众号「源泉TheFountainhead」；作者：巫師Sorcerer；发布：2026-08-31
- 文章性质：产品设计方法论与作者案例复盘，不是可直接套用的行业标准或实证研究。

## 一句话

AI Native 的关键不是把聊天框加到 GUI 上，而是将目标、意图校准、计划、授权、动作证据、结果追踪和人工接管设计成一条可治理的任务回路；界面由操作入口升级为控制面。

## 五个核心观点

1. **产品责任迁移**：传统软件接收用户拆好的操作；动作型 AI 产品要承接从目标到结果的一部分认知与执行劳动。
2. **意图必须校准**：Goal 说明终态，Intent 解释当前目的、约束和授权；不确定性与行动代价同时升高时，应提高确认强度。
3. **结果不能靠自报**：执行成功、任务解决和用户价值是三层不同结果，完成条件必须有外部回执或可观察证据。
4. **自治需要分级**：能力、权限、角色、状态/记忆和恢复要显式设计；授权执行与受约束自治的区别在于授权发生的时点与范围。
5. **界面变为控制面**：聊天适合表达目标与补充语境，结构化 UI 适合审查、编辑、授权和接管；二者共同支撑持续协作。

## 七个分析角度与开头钩子

### 1. 聊天框为什么不等于 AI Native
- 为什么在旧产品上加一个聊天框，常常只是换了输入法？
- 当系统开始替用户拆步骤、调工具、改外部状态，产品责任哪里变了？
- AI Native 的分水岭，是“能聊天”还是“能拿结果”？

### 2. Goal 和 Intent 如何分工
- 用户说“提高转化率”时，系统还缺哪些执行信息？
- 终态目标和当前约束，为什么不能混成一条 Prompt？
- 什么时候该追问，什么时候该先执行？

### 3. 如何设计确认强度
- 为什么把所有信息都塞给 Agent，反而可能让它报错价格？
- 不确定性和行动代价同时升高时，确认应该怎样变化？
- 低价值澄清和高风险批准，为什么不能用同一种交互？

### 4. 什么算真正完成
- Agent 说“已完成”，为什么可能一条 CRM 记录也没写进去？
- 执行结果、任务结果和用户结果，分别需要什么证据？
- 为什么点击减少并不代表体验或业务价值变好？

### 5. 角色、能力与权限怎样拆
- 一个会做事的 Agent，为什么要分开写角色、能力和权限？
- 系统能改配置，与它现在可以改配置，为什么是两回事？
- 授权时点、额度和异常升级条件，应该落在哪一层？

### 6. 自治怎样升级才不失控
- 为什么高自治不是越高越好？
- 逐次确认和受约束自治之间，真正差的是什么？
- 哪些任务适合提高自治，哪些必须保留强人工判断？

### 7. 控制面由谁来设计
- AI 接手行动后，界面为什么不再只是操作面板？
- 用户从哪里看见系统停了，又从哪里接管？
- 设计师为什么需要参与状态、授权和恢复，而不是只设计聊天气泡？

## 最小实践

1. 对每个动作型任务写一份目标契约：目标结果、约束、允许动作、确认点、验收证据、失败补偿和升级对象。
2. 把自然语言解释与真实业务判断拆开：模型可提出意图和候选计划，实时状态、规则与权限必须来自权威系统。
3. 按风险定义自治等级：低风险可撤销动作允许在预设范围内执行；金额高、不可逆或低频动作逐次确认。
4. 在 UI 中稳定呈现计划、当前状态、工具回执、待确认项、可撤销窗口和人工接管入口。
5. 用外部状态复核替代模型自报：每次写入后读取目标系统，确认真实状态、记录证据并更新任务进度。
