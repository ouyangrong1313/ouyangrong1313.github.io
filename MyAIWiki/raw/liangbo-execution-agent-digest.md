## 一句话总结

**这篇案例真正讲清的是：对报销、薪资组搭建、入职办理这类执行型 Agent，不能把关键 API 参数绑定交给 LLM 临场生成；要把“控制信号 / 任务调度 / 机械参数 / 叙事记忆”拆成不同平面，用 Orchestrator + 规划执行 + 机械状态平面 + 三权分立会话状态把不确定性关进笼子。**

## 核心观点（8 条）

1. **执行型 Agent 和内容生成型 Agent 是两种不同物种**  
   前者交付真实业务状态变更，后者交付文本内容结果；两者的复杂度不在一个量级。
2. **MCP 不是坏方案，但不适合做强约束事务主干**  
   如果步骤之间靠 `id`、`template_id`、审批状态这类机械参数串联，就不能把绑定责任交给 LLM 概率生成。
3. **业务目标必须先否决伪需求**  
   东方屹腾最终没做“AI 分析报表”，而是锁定“薪资组快速搭建”这种真实高痛点事务冷启动。
4. **控制平面 / 叙事平面二元论是认知地基**  
   先把活的、不确定的东西收敛成死的、可控的控制信号，再让叙事上下文去承载理解和生成。
5. **Orchestrator + 意图网关是所有能力的家**  
   理解、路由、推理、检索、行动、总结，都挂在统一编排器上。
6. **ReAct 够灵活，但遇到严格递进任务会漏步**  
   于是系统进一步长出任务 DAG、状态机、规划器和执行器，进入 Plan-and-Execute。
7. **机械状态平面是最核心发明**  
   用独立状态平面 + Provenance 坐标保存参数生产/消费关系，避免 LLM 去“猜”确定性 id。
8. **会话统一状态平面要三权分立**  
   叙事状态平面管进展，机械状态平面管参数，任务调度状态平面管顺序；再叠加锚、账、集和 L1/L2/L3 记忆体系。

## 7 个分析角度

### 角度 1：为什么 MCP 在这个场景里会失效

- 问题不在“能不能调用工具”，而在“谁来保证参数绑定 100% 正确”
- MCP 把参数理解和生成责任交给 LLM，这对文本型任务可以接受，对事务型任务风险过高
- 关键判断：**确定就不能只靠概率**

### 角度 2：为什么业务锚点要先选对

- 生成型分析任务看起来更像 AI，但未必是用户刚需
- 真正愿意付费的痛点在“第一次配置太难”和“每月重复操作太烦”
- 锚点场景选成薪资组快速搭建，后面整套架构才有了落脚点

### 角度 3：控制 / 叙事二元论

| 平面 | 回答什么问题 | 数据性格 |
|---|---|---|
| 控制平面 | 现在该走哪条执行流 | 结构化、机械、可驱动 |
| 叙事平面 | 用户要什么、上下文发生了什么 | 自然语言、可推理、可压缩 |

### 角度 4：ReAct -> 规划执行 -> HITL 的演进链

- ReAct 适合“干一步、看一步”
- 一旦任务出现严格先后依赖，就要把步骤先钉死，进入规划执行
- 有了任务 DAG 和状态机，HITL 阻塞与续作就顺理成章长出来

### 角度 5：机械状态平面到底解决了什么

- 它解决的不是“上下文不够长”，而是“确定性参数不该由 LLM 生成”
- 每个参数都变成独立坐标：谁生产、在哪个运行层级产出、谁来消费
- 这是从“让模型猜”改成“让系统读格子”

### 角度 6：会话统一状态平面的三权分立

| 平面 | 负责内容 | 典型对象 |
|---|---|---|
| SessionNarrative | 目标与进展 | 锚 / 账 / 集 |
| SessionState | API 参数与契约 | key / scope / provenance |
| Workspace | 任务依赖与调度 | DAG / ready / completed |

### 角度 7：迁移前的判断清单

只有同时满足下面几条，这套架构才值得搬：

1. 任务步骤明确，且存在严格依赖
2. 参数错一位会直接失败或写坏业务数据
3. 你控制工具注册和系统边界，是封闭企业体系
4. 你需要的不是“生成一份内容”，而是“真正改动业务系统状态”

## 5 个关键提醒

1. **不要让 LLM 负责复制随机 id。**
2. **前端和可观测性要比你想得更早做。**
3. **任务图和状态机不是过度设计，而是执行型 Agent 的底座。**
4. **HITL 最好长在状态机上，不要后面再补丁式接进去。**
5. **如果本质还是内容生成场景，就别硬上这套重机制。**
