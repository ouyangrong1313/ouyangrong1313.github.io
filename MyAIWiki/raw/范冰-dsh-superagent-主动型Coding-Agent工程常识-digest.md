## 核心观点

1. **主动型 Agent 的工程目标是减少人的注意力占用。** 文章将 dsh-superagent 描述为把前台交互与后台执行拆开的 Coding Agent 原型：Router 保持对话连续，Worker 承接代码、测试等长任务。
2. **注意力纪律是架构的一部分。** 作者主张只在需要人作决定或有可用阶段性成果时打扰用户；介入时一次问一个结构化问题，过程进展留在日志，状态与失败如实标记。
3. **Trigger 与 Thread 把事件并行性和顺序一致性分开处理。** 外部输入先作为不可变 Trigger 记录，再按来源进入 Thread；同一 Thread 串行评估并暂存新事件，不同 Thread 可并行，LLM 前另有轻量过滤。
4. **异步执行、Watchdog 与持久化状态共同处理长任务故障。** 文章称前台命令超过 5 秒转后台、任务完成后唤醒 Worker，后台任务 30 分钟超时；Stored Work 与 Outbox 则先记账再产生外部副作用，以便恢复和重试。
5. **权限应由可检查的策略约束，而不只靠提示词。** 版本化 Policy 与不可变 Mandate 记录任务权限及依据；record-only 影子模式被文章明确描述为设计蓝图中的方案，尚不能当作已实现能力。
6. **作者把这套设计用于审视自己的个人自动化。** 他归纳出定时轮询、只报警不自愈、散文式规约、易失标记和通知分散五类问题；这些是作者自述的诊断与迁移设想，不是独立评测。

## 7 个分析角度与 21 个开头钩子

### 1. 文章要解决的核心问题
- 一个 Coding Agent 怎样在执行长任务时仍能回应人？
- 如果 Agent 要主动干活，怎样避免它先占满人的注意力？
- 让系统持续做事与让人随时能插话，必须二选一吗？

### 2. 旧工程常识为何仍有价值
- Agent 工程需要的未必是新提示词，而可能是几十年前就成熟的状态与故障处理方法。
- 这篇文章谈的重点不是模型更聪明，而是怎样把不可靠组件接进可靠流程。
- 当“主动性”成为目标，操作系统和分布式系统的老办法反而重新变得重要。

### 3. 注意力纪律与前后台分离
- 长任务运行时，最让人不安的不是等待，而是系统突然听不见人。
- 如果每一步都推送进度，真正重要的故障也会被通知噪声淹没。
- Agent 需要打扰人的时机，应该由结果或决策边界决定，而不是由进度条决定。

### 4. 事件驱动与 Thread 一致性
- 每条新消息都另起一个 Agent，看似并发，实际可能让多个上下文同时改同一份工作。
- 同一来源的事件先排队、不同来源并行，给并发和一致性划出不同边界。
- 把外部变化记成不可变事件，能让后续评估围绕事实记录展开，而不是改写历史。

### 5. 长任务的故障恢复
- 一个编译命令超过几秒后，执行者是否还应该被它绑在原地？
- 只知道进程活着不够；后台任务还需要超时、唤醒和失败恢复。
- 断点续跑的关键不是留下一个“正在运行”标记，而是先把已发生和待发生的动作记清楚。

### 6. 自主权限与影子验证
- “请谨慎操作”很难审计，机器可读的权限边界更容易在执行前检查。
- 先记录 Agent 打算做什么、暂不执行，是自动化从建议走向行动的一种过渡方式。
- 影子模式能否有效，取决于记录是否覆盖真实风险；它本身并不证明放权后安全。

### 7. 个人系统迁移与证据边界
- 作者用五个具体故障模式检查自己的自动化系统，而不止停留在架构名词上。
- 定时轮询、被动告警和临时标记未必处处错误，关键是它们是否匹配任务频率与失败后果。
- 这是一份原型设计的工程解读，不是 dsh-superagent 在生产环境中的可靠性评测。
