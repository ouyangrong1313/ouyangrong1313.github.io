## 一句话

Skills 可以把 Agent 的临时发挥变成可复用、可检查的工作方法；应按当前工作流的能力缺口分层补充，并把验证与供应链治理纳入使用过程，而不是一次性安装完整清单。

## 五个核心观点

1. **Skill 封装的不只是动作**：设计良好的 Skill 同时提供触发条件、工作方法和检查边界，让重复任务不必每次从零组织。
2. **完整工作流跨越多个能力层**：文章将仓库分为 Research、Engineering、Create、Grow + Ship，串起发现问题、理解系统、构建成果、检查结果与发布反馈。
3. **先补上下文与工程纪律**：Research 提供证据，代码库图谱和仓库记忆补足系统知识，YAGNI 式决策减少无用实现和技术债。
4. **生成与执行、验证应分离**：Creative Skill 规划期望产物，确定性工具负责执行，contracts、doctor 或其他机器可检查的门禁验证结果。
5. **Skill 本身需要治理**：Skill 文档可能触发 Shell、文件、网络和依赖安装操作；应审查来源、限制权限、固定版本，并将只读研究能力与可变更能力区分。

## 七个分析角度与开头钩子

### 1. 为什么不需要一次性安装所有 Skill
- 有二十个热门 Skills，就意味着团队应该安装二十个吗？
- 如果 Agent 已能写代码，却不会验证和发布，缺的究竟是哪一层？
- 先找到工作流里的缺口，再补能力，比堆工具更容易看出效果。

### 2. Skill 如何从提示变成工作方法
- 好的 Skill 不只是告诉 Agent 做什么，还要说明如何工作。
- 同一个任务每次都要重新解释，说明哪一段流程还没有被封装？
- 触发条件、操作步骤和可检查输出，如何组成可复用的工作单元？

### 3. 为什么研究应在推理前发生
- 上下文不完整时，Agent 也能给出听起来很自信的结论。
- Web access 解决了资料可达，却不自动证明资料可信。
- 多来源研究、用户研究与本地 Markdown 检索分别适合回答什么问题？

### 4. 代码库理解怎样减少错误改动
- Agent 会 grep，不代表它理解架构、依赖影响和历史错误。
- 在读取大量源码前先建立仓库地图，能改变后续什么行为？
- 记住一次修正和减少一次过度构建，是两种不同的工程收益。

### 5. 为什么生成与验证应分层
- 产物技术上正确，为什么仍可能无法被人使用？
- Creative Skill 负责构想，确定性工具负责执行，谁来检查最终结果？
- 把 geometry、间距和语义约束变成机器检查项，会改变生成流程什么？

### 6. 发布为什么仍属于 Agent Loop
- 功能交付后，用户是否找到并用上它，如何回到下一轮改进？
- SEO、内容编辑、视频生成和媒体验证分别处于工作流的哪一段？
- Planner 和 tool 不必是同一个东西，边界分开有什么好处？

### 7. 如何把第三方 Skill 当作依赖治理
- 一个看起来像文档的 SKILL.md，为什么可能成为执行策略？
- 安装脚本能读文件、联网和写入产物时，权限该怎样给？
- 固定版本、检查脚本、分离只读与变更能力，分别解决什么风险？

## 最小实践

1. 画出现有 Agent 工作流，标记研究、系统理解、构建、检查和发布中真正缺失的环节。
2. 只添加一个项目级 Skill，并明确触发条件、输入、输出、转交边界和验收方法。
3. 在授权之前审阅 Skill 正文、脚本和安装步骤，确认文件读写、网络访问和依赖变更范围。
4. 对生产工作流固定版本；在可用时先运行 doctor、preflight 或 contract 检查。
5. 把生成性步骤与确定性验证分开，保存验证失败和本地修正，作为后续维护依据。
