## 正文

DeepSeek Harness 发布的 Super-agent 构想，在负责执行任务的主 Agent 之上再增加一层，希望同时处理跨任务连续性、任务吞吐量与长期记忆等问题。




DeepSeek 产品部负责人、原文章最终审稿人之一崔添翼亲自回答，从命名由来、双层架构的动机，到原型距离现实落地仍需解决的问题，对这项探索作出了完整说明。







如何评价 DeepSeek Harness 发布的 Super-agent 构想？







答主丨崔添翼（2300+人赞同）







谢邀，我是 DeepSeek 产品部的崔添翼，也是 Super-agent 这篇文章的最终审稿人之一。文章主体、设计、代码和实验都来自于 DeepSeek Harness 组的其他同事，尤其是一作 Yujia Qiao 同学。我来解读这篇文章不一定是最合适的，不过我会尝试一下。




首先，这个概念为何命名为「Super-agent」？




并不是因为这个架构会让 Agent 变得多么「超级」或者「superior」，而是因为「super-」是表示「above, over」的英语词汇前缀，和表示「under, below」的「sub-」是相对的。（例如 superscript vs subscript，superclass vs subclass，superlinear vs sublinear，superset vs subset。）「Super-agent」是在干活的主 Agent 的上面加了一层，与在下面加了一层的「Sub-agent」恰恰相反。这个名字是这么来的。




正如我们文章中提到的，「我们并没有提出全新的理论」。在文章发表之后，我们收到了大量「英雄所见略同」类的反馈。和业内同行交流中，也发现这套架构基本已经是业界内前沿团队的共识，有多个团队在好几个月前就尝试过了。在 Agent 时代，从代码维度上，把所有新可能性的排列组合尝试一遍不难。看清和坚定选择长期、全局最优的方向，这可太难了。我们目前的 Super-agent 的实现的 repo 叫做 dsh-superagent-prototype，是个纯原型探索阶段的东西。文章里的部分设计，比如说「计算和状态、环境」解耦想要在 dsh 里实现还有非常多工作要做。




Super-agent 采用双层架构的一个动机是，长程记忆的解决方案始终没有共识（这导致 DeepSeek Harness 直到现在也没有内置的跨 session 长程记忆能力，不过可能快有了）。基于此，我们认为 Agent 跨任务的连续性和任务的吞吐量成为了一对根本的 tradeoff，是当前长程 Agent 设计的一个需要解决的根本问题。具体采用的实现不一定最优，但我们希望能提供一种思考和问题拆解的方式。




我们这套系统之所以能够在内部的实践中以较低的复杂度运作，很大程度上是因为我们在当前阶段做出了一系列工程和场景简化。想进一步在现实大部规模落地，需要解决文章第八节中的开放问题，比如双层架构的扩展（8.1 节）、脱离 Session 后的人机协作（8.2 节）、上下文边界与 A2A（8.3 节），以及安全与隐私（8.4 节）。评论区的很多问题在其中已有提出。文章中的 Super-agent 原型只在公司内这一较小规模的受信环境跑通了。而现实世界是非常复杂的，还有许多问题需要进一步解决，希望能和大家共同探索。···




DeepSeek 产品部希望能做出世界一流的 Agent 产品。做 Agent 产品，DeepSeek 有一流的模型、算法、基建，有极其优秀的研究员和工程师。但是，想做一流产品，目前 DS 产品部内优秀的产品经理和产品设计师的数量还远远不够。
