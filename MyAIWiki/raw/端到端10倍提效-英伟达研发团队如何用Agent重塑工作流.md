# 端到端10倍提效：英伟达研发团队如何用Agent重塑工作流

## 正文

如果一家最懂 AI 基础设施的公司，开始把 AI Agent 当成默认工作工具，会发生什么？
最近看到OpenAI在官方披露了Codex在英伟达内部的真实用法：约 4 万名员工拥有使用权限；工程师用它把内部系统从 MVP 推向生产，研究人员让它从论文阅读一路做到远程实验。受访研究人员称，
端到端研究流程提速了 10 倍。
（文末有链接）
虽然时间过去了3个月，且当时案例还是5.5模型（现在是5.6），但是里面提到的地处工作流的重塑和具体做法，仍值得参考。
案例里面核心提到了两条过去需要多人、多工具、多次交接的工作链，开始被一个 Agent 串起来：
• 工程侧：需求 → 开发 → 测试 → 生产化；
• 科研侧：论文 → 证据 → 假设 → 远程实验。
Codex 不再只是代码补全工具，而是在目标明确、环境可用的前提下，把任务持续推进到可验证结果的“数字工程师”。
一、先看结果：4 万人可用，研究流程提速 10 倍
几个数字最能说明变化：
• 约
4 万名英伟达员工
拥有 Codex 使用权限；
• 研究人员称，端到端机器学习研究流程获得了约
10 倍提速
；
• 一个受隐私要求约束的内部播客录制应用，过去仅采购软件可能就要数周，现在借助 Codex
几小时内完成搭建
；
• 一些团队正在把性能不理想的 Python 项目改写成 Rust，案例中提到的性能提升可达到约

这些数字来自具体团队的实践反馈，不代表所有任务都能获得同样提升。但它们说明：当 Agent 能长时间保持上下文、调用工具并自我检查，效率提升会从单个编码环节扩展到整条工作链。
二、工程团队怎么做：把一个想法直接推到生产
英伟达内部的 coding agents 团队，负责帮助不同业务接入 AI 开发工具。Codex 已成为复杂工程任务的常用选择：它能围绕一个目标持续工作，在多次上下文压缩后保留任务主线，并按需选择工具和技能。
这套工程工作方式可以拆成五步。
第一步：给目标，不只给一段代码需求
传统代码助手擅长补全代码、解释报错等局部任务。英伟达则把 Codex 用在更完整的目标上，例如：
• 把内部平台从 MVP 升级为生产系统；
• 改善系统的可扩展性与可靠性；
• 在隐私约束下快速搭建内部应用；
• 将旧代码库迁移到性能更高的语言和架构。
这类任务无法靠一句指令完成。Agent 要先理解代码库和约束，再拆解任务。因此，任务描述至少要说清：解决什么问题、现状是什么、哪些约束不能破坏、怎样才算完成。
第二步：让 Agent 进入真实环境，而不是只在对话框里回答
Codex 可以读取代码和文档、调用工具、运行测试、观察结果，再继续修改。原文提到，它由 GPT‑5.5 驱动，并运行在英伟达 GB200 和 GB300 基础设施上，能够承担更长、更自主的任务。
因此，人不必来回复制中间结果，Agent 可以在工作环境里形成闭环：
读取现状 → 制订计划 → 修改代码 → 运行系统 → 检查结果 → 继续修正。
它的价值也由“给答案”变成“推进工作”。
第三步：把开发与测试交给同一个闭环
内部播客录制应用是一个典型案例。
受隐私要求影响，采购外部软件可能需要数周，团队却借助 Codex 在数小时内搭出了内部应用。
更关键的是，Codex 桌面应用具备计算机交互能力。Agent 不只提交代码，还能像用户一样操作界面，测试音视频录制，并根据结果继续修复。这把开发与验收接进了同一条反馈回路。
第四步：让 Agent 主动暴露遗漏，而不是被动等报错
英伟达工程师提到，新的 Codex 会发现原始指令未覆盖的问题，包括程序缺陷和逻辑空白。它在推进主任务时，还能检查边界条件、依赖关系和可靠性风险。
人仍要决定哪些问题值得处理、哪些改动可以进入生产，但 Agent 能让隐藏风险更早暴露。
第五步：从“能运行”继续推进到“能生产”
一名英伟达高级软件工程师已经用 Codex 把内部平台从 MVP 推进成生产级系统，并补强扩展性和可靠性。
真实企业软件最难的部分往往在演示之后：权限、异常处理、稳定性、监控、测试和系统集成。
Agent 如果只能生成原型，改变的只是启动速度；如果还能持续修改并通过验证，才可能改变软件交付方式。
三、研究团队怎么做：把论文阅读一直连到远程实验
研究团队没有只让 Codex 写训练代码，而是让它参与完整研究循环：阅读论文、整理证据、提出假设、编写脚本，再到远程计算资源上执行实验。
1. 把论文库变成可追踪的证据网络
案例中提到英伟达研究人员会把一个领域的大量论文交给 Codex，例如强化学习文献。Agent 不只逐篇摘要，还会跨论文追踪证据，梳理观点之间的联系，并建议用知识图谱呈现概念关系。
人负责判断问题是否重要，Agent 则扩大检索范围、整理证据链，并暴露容易被忽略的关联。
2. 从证据出发形成可验证假设
有了证据网络，下一步是形成可被实验验证的假设。人和 Agent 的分工是：
• Agent 可以提出方向、比较证据、生成候选解释；
• 研究者负责判断假设是否新颖、是否有意义、是否值得投入算力验证。
AI 是创造力放大器，不是科研责任的替代者。
3. 把假设直接翻译成训练脚本
假设确定后，Codex 会继续编写实验脚本并适配研究基础设施。因为它已经理解前面的论文和假设，可以沿着同一上下文直接生成实验，减少从“想法”到“实现”的交接损耗。
4. 通过 SSH 运行远程实验
Codex 应用支持 SSH。研究人员可以在笔记本上发起任务，让 Agent 连接远程主机、配置环境、提交任务并查看日志。
最终，研究流程变成了：
论文语料 → 证据链 → 知识图谱 → 研究假设 → 实验脚本 → 远程训练 → 结果反馈。
所谓 10 倍提升，来自这条端到端链路，而不只是某段代码写得更快。
四、为什么英伟达能做到：不是一条提示词，而是四个条件
很多团队会问：他们用了什么提示词？原文真正透露的答案，是一套工作环境，而不是一句神奇指令。
1. 足够强、能长时间自主工作的模型
Agent 要在长时间任务中维持目标，经历多轮修改和上下文压缩后仍然知道做到哪一步。自主性越强，对目标、约束和验收标准的要求越高。
2. 可调用的工具与技能
模型必须能读取代码、运行测试、连接远程机器，必要时操作真实界面。没有工具，Agent 只能建议；有了工具，它才能行动。
3. 可观察、可验证的反馈
Agent 修改代码后，需要看到测试结果、运行日志、界面状态和实验输出。没有可观察性，它就无法判断任务是否完成。
4. 明确的人类责任
AI 可以找问题、提假设、写脚本和运行实验，但价值判断、生产风险和研究结论仍由人负责。Agent 接走的是执行与反馈循环，不是最终责任。
五、普通企业可以怎么复制：先从一条闭环开始
大多数企业无法照搬英伟达的基础设施，但可以先复制一条高频、可验证、有清晰边界的工作链。
第一步：选对任务
适合 Agent 的任务通常具备三个特点：
• 输入材料相对完整；
• 过程可以被工具执行；
• 结果能够用测试、数据或明确标准验证。
旧系统的小规模迁移、内部工具开发、测试补齐、文献梳理和实验脚本生成，都比“替公司想一个战略”更适合作为起点。
第二步：把任务说明改成四段式
给 Agent 的任务不要只写“帮我做一个系统”，至少要包含：
1.
目标
：最终要解决什么问题；
2.
背景
：现有系统、材料和用户是谁；
3.
约束
：隐私、安全、技术栈和不能改变的部分；
4.
验收
：哪些测试通过，结果才算完成。
Agent 越自主，任务边界越要清楚。
第三步：打通行动权限
让 Agent 能在安全边界内读取资料、运行工具、调用测试环境和观察结果。权限可以从只读代码库、沙盒环境和非生产数据开始，再按风险逐步扩大。
第四步：建立自动反馈回路
为结果设计机器可读的检查方式，例如单元测试、性能基线、日志规则或界面检查清单。不要把“生成完成”当作结束，而要让发现的问题回到下一轮修改。
第五步：每次失败都升级环境
如果 Agent 表现不好，不要只换种说法再问一次。应追问：
缺少哪份资料、哪个工具、哪条验收标准，哪个环节看不到反馈？
把答案沉淀到文档、技能、测试和权限配置中，让一次失败变成下一次成功的基础设施。
六、这件事真正改变的，是“什么值得做”
英伟达工程师提到，Codex 已经改变了他们判断“什么值得开发”的门槛。
过去，一个内部工具即使有用，也可能因采购慢、开发成本高而被搁置。现在，如果 Agent 能在几小时内完成开发与测试，许多不值得排期的小需求突然可以被解决。
科研也一样。论文阅读
和实验准备成本下降，
更多想法能更快进入验证。
Agent 不只是让同样的工作更快，还会让组织重新计算每件事的成本，进而改变需求优先级、研发边界和创新密度。
当大模型能力边际效益逐步降低时，未来真正带来生产力提升的，不是谁更早买了 AI 工具，而是谁先把工作改造成一条 Agent 能持续行动、获得反馈并交付结果的完整闭环。
