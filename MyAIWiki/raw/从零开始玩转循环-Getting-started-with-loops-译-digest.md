## 核心观点

1. **Loop 不是“多问几轮 AI”，而是让智能体重复执行工作周期，直到满足明确的停止条件。**
2. **Claude Code 的 loop 选择顺序应该从最轻的开始：turn-based → `/goal` → `/loop` / `/schedule` → proactive，复杂度跟着任务而不是跟着想象走。**
3. **真正把 turn-based loop 拉开质量差距的不是 prompt 词藻，而是把人工验收写进 `SKILL.md`，让 Claude 能自证结果。**
4. **高质量 loop 的核心不是自动化本身，而是触发器、停止条件、验证器和成本边界一起设计。**
5. **一次失败如果只修 bug 不改规则，loop 只会重复犯错；教训要沉淀进 skill、review 规范和 verifier。**

## 7 个分析角度

### 1. 为什么这篇文章值钱

- 它把“loop 到底是什么”从口号拉回到 4 个可操作维度：触发、停止、原语、任务适配。
- 它不是在教你“怎么写一条更长的 prompt”，而是在教你如何设计一个能收敛的工作循环。
- 这让 loop 从概念炒作，变成了能落到团队工作流上的控制面。

### 2. Turn-based loop 的真正升级点

- 每条 prompt 本来就是一个 loop；差别只在于你把多少检查还留给了人。
- 文章最实用的一点，是把人工“看一眼”翻译成 `SKILL.md` 里的可执行 verifier。
- 这也是 Claude Code 从聊天框工具升级成工程助手的分水岭。

### 3. `/goal` 为什么常比“多补一句 prompt”更有效

- 因为它把“什么时候算完成”写死了，模型没法靠体感提前收工。
- 对复杂任务，很多时候问题不在不会做，而在“差不多就停”。
- 明确成功标准和尝试上限，本质上是在给 loop 加刹车和计分板。

### 4. `/loop` 和 `/schedule` 的分水岭

- `/loop` 适合本地、临时、可见的轮询式工作；`/schedule` 才像长期在云端上班的例行程序。
- 真正应该关注的不是命令名，而是任务是不是会持续收到外部世界的新输入。
- 如果输入变化很慢，用盲目高频轮询只会把 token 烧成噪声。

### 5. 主动式 loop 的组成件

- `schedule + goal + skills + dynamic workflows + auto mode` 是一套组合拳，不是单指令的魔法。
- 它的难点不在“让 AI 去做”，而在“让 AI 知道何时开始、何时停、怎样自证、何时交给人”。
- 一旦这些部件接好，AI 才更像一个岗位，而不是一次性对话。

### 6. 代码质量如何不被自动化稀释

- 干净代码库、第二个 reviewer agent、官方文档可达、失败教训回写规则，这四件事决定 loop 是生产力还是噪声机。
- 文章把“第二个 agent 做 review”讲得很轻，但其实点破了 agent 自我偏袒的问题。
- 你不是在追求更会写代码的模型，而是在搭一个更会自检的系统。

### 7. Token 账单怎么控

- 小任务用小 loop、小模型和脚本化动作；高频轮询改事件触发；大规模部署前先试水。
- 真正贵的不是一次调用，而是没有边界的 while 循环。
- 这篇文章最成熟的地方，是它从头到尾都在提醒“别为 loop 而 loop”。

## 21 个开头钩子

### 角度 1：定义

1. 你以为 loop 是“让 AI 多试几次”，Claude Code 团队真正强调的是“先写停止条件”。
2. 很多人在讨论 loop 时盯着模型聪不聪明，这篇文章盯的是触发器、原语和退出条件。
3. 如果你还把 loop 理解成 prompt 的加长版，那你漏掉的是控制面，而不是语气词。

### 角度 2：Turn-based

1. 每一次你给 AI 发消息，其实都已经启动了一个 turn-based loop。
2. 真正拉开差距的不是 prompt 写得像不像魔法咒语，而是你有没有把验收步骤写成 skill。
3. “人工看一眼”如果不能被翻译成 verifier，就永远只能靠人兜底。

### 角度 3：`/goal`

1. `/goal` 最有价值的地方，不是让 AI 更努力，而是禁止它太早宣布结束。
2. 当完成标准不明确时，模型最常见的问题不是完全不会做，而是太早交卷。
3. 你不是需要一个更勤奋的 agent，你需要一个更明确的 stop condition。

### 角度 4：`/loop` 与 `/schedule`

1. 不是所有循环都该按 5 分钟轮一次，很多 loop 一开始就输在触发器设计上。
2. `/loop` 适合本地实验，`/schedule` 才像真正的长期生产岗位。
3. 周期性任务最怕的不是跑不起来，而是一直在盲刷一个根本没变化的世界。

### 角度 5：主动式 loop

1. 真正的 proactive loop 不是一个命令，而是一套“调度 + 验证 + 审查”的组合系统。
2. 当 `schedule`、`goal`、skills 和 workflows 接在一起，AI 才开始像一个岗位而不是一个聊天框。
3. 很多所谓自动化，只做到了自动执行，还没做到自动收敛。

### 角度 6：质量

1. Claude 会模仿你的代码库，这句话背后的意思其实很残酷：烂仓库会稳定地产出烂代码。
2. 第二个 agent 的价值不是“多一个模型”，而是给主执行链路一个没被污染的审查视角。
3. 如果失败教训没有回写规则，下一轮自动化就只是在更快复现同一个错误。

### 角度 7：成本

1. Token 成本失控，通常不是因为模型太贵，而是因为 loop 没边界。
2. 大模型最适合做难判断，不适合拿来高频刷新一个低变化输入源。
3. 在大规模上自动化之前，先跑一个小闭环试水，这不是保守，是算账。

## 可复用框架

- 选 loop 先问四件事：`谁触发 / 何时停止 / 用什么原语 / 哪类任务最适配`
- 写 verifier 先问三件事：`能否直接观察结果 / 能否自动重跑 / 失败后是否必须回到步骤 1`
- 控成本先问三件事：`能不能用更小模型 / 能不能事件触发 / 能不能脚本替代推理`
