## 一句话

Graph Engineering 的核心不是多画一张流程图，而是把任务、能力、状态、证据、权限与恢复提升为可查询、可验证、可调度的系统对象，使概率性的 Agent 组件能在复杂生产任务中稳定协作。

## 五个核心观点

1. **系统智能是新瓶颈**：复杂任务需要任务组织、Agent 协调和运行时状态治理，继续给单 Agent 堆上下文或工具无法消除架构错配。
2. **计划必须显式化**：任务依赖、并行、验证和重规划要从 Prompt 文字外化为可调度的动态图。
3. **Runtime State 不等于 Memory**：权威状态应记录证据、来源与版本，并经过提议、验证、提交的边界治理。
4. **恢复是系统能力**：故障定位依赖状态转换与验证证据；恢复需要区分撤销、重放与对不可逆副作用的补偿。
5. **Agent OS 需要控制面**：能力发现、路由、权限、状态存储、checkpoint、回放、回滚与可观测性应成为共享运行时能力。

## 七个分析角度与开头钩子

### 1. 为什么单 Agent 会失控
- 给 Agent 继续加工具，为什么复杂任务反而更难管？
- 当所有工作都压进一个 Loop，最先崩的是上下文还是状态？
- 单 Agent 的能力上限，可能其实是系统组织的下限。

### 2. 计划为何要变成图
- Prompt 里的计划，为什么不能直接成为生产调度器？
- 哪些任务应该立刻并行，哪些必须等待验证？
- 图的价值不在可视化，而在让运行时真正看见依赖。

### 3. Memory 和 State 差在哪
- “记住了”为什么不等于“系统可恢复”？
- 一个 Agent 提出的事实，什么时候才能成为共享权威状态？
- 没有来源和版本的记忆，出了错该从哪里开始查？

### 4. 如何从失败中恢复
- 第 50 步暴露的错误，为什么根因可能在第 20 步？
- 回滚之前，系统必须先回答哪些状态真的还能撤销？
- 外部副作用不能回滚时，补偿动作如何进入 Agent 设计？

### 5. 多 Agent 怎样动态调度
- “研究员、工程师、审阅者”这些角色名，为什么不足以让系统选对人？
- 权限、成本、可靠性变化后，谁来寻找可替代的执行者？
- 通信更多时，协作为什么可能反而更差？

### 6. Control Plane 管什么
- 多 Agent 系统缺的不是更多角色，而是哪一层控制面？
- 谁应统一管理任务图、权限、状态和证据？
- 当每个框架都维护自己的对象模型，企业系统会发生什么？

### 7. Ontology 为什么进入 Agent
- “任务完成”由谁定义，为什么不能只让模型自己判断？
- 证据充分、状态有效和权限合法，怎样变成共同语义？
- Agent 自演化为什么必须留下可回放和可撤销的轨迹？

## 最小实践

1. 为长程 Agent 定义状态对象：任务、负责人、输入输出、证据、版本、权限、检查点与外部副作用。
2. 将任何共享状态写入设计为 proposal -> validation -> commit，不让模型输出直接覆盖权威事实。
3. 每个关键节点记录 actor、transition、dependency 与 validation evidence，支持后续故障归因。
4. 先列出可重放、可回滚和只能补偿的操作，再设计恢复边界。
5. 用可查询的能力、成本、权限和可靠性属性做路由，而非仅依赖固定角色名。
