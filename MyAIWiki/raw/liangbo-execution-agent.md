## 摘要（编译者注）

这篇案例最有价值的地方，不是再讲一遍“Agent 会调工具”，而是把一个企业 SaaS 场景里真正会把系统搞崩的部分掰开讲透：

1. **执行型 Agent 不是内容生成型 Agent**  
   对报销、薪资组搭建、入职办理这类事务流来说，步骤之间传递的不是“文本语义”，而是严肃的机械参数绑定关系。参数错一位，不是回答偏一点，而是业务失败甚至脏写数据。
2. **MCP 不是不行，而是不适合拿来承载这类强约束执行主干**  
   MCP 适合“查资料 -> 总结 -> 写报告 -> 做 PPT”这类内容型任务；不适合把 `template_id`、`申请 id` 这类必须 100% 正确的参数传递交给 LLM 临场生成。
3. **整套架构的核心发明是“机械状态平面”**  
   真正决定这套执行型 Agent 稳不稳定的，不是 prompt 写得多漂亮，而是把参数生产、消费、绑定、取用都从叙事上下文中剥离出来，变成独立、可审计、可 fail-fast 的状态平面。
4. **会话状态要三权分立**  
   叙事状态平面负责“用户要什么、做到哪了”；机械状态平面负责“API 参数从哪来、对不对”；任务调度状态平面负责“先跑哪步、跑完没有”。
5. **这是很强的执行型 Agent 迁移判据**  
   如果你的业务满足“步骤明确、参数强依赖、错一位就失败、系统是封闭企业体系”这四条，那么这篇案例给的是工程骨架，不只是观点。

## 原文正文（按章节清洗整理，保留核心段落）

**证据边界：**本文是一线实践者主导的架构复盘。实现主张、业务规模与效果数据由案例方提供，尚未经过独立审计；迁移建议只在文中列明的业务与系统条件下成立。

## 一、先把分野划清楚：执行型 Agent 不是内容生成型 Agent

东方屹腾原有产品是一套面向企业人事、组织、考勤、审批、薪酬的 SaaS 服务矩阵，向下打通银行和税局，已经稳定服务两万多家企业。大模型起来之后，团队最初也想过把原有 API 按 MCP 协议暴露成 MCP Server，让 Agent 去自动完成复杂业务流程。

真正开始拿核心业务场景落地，这条路很快就暴露出问题。MCP 的价值在于开放和灵活：Agent 感知工具、调用工具、再把工具结果以文本形式塞回上下文；至于参数怎么理解、怎么准备、怎么绑定，全部交给 LLM。对于通用内容型任务，这个模式非常强大；但东方屹腾要落地的是执行，不是内容生成。

案例用“报销”举例说明这个差异：在费控系统里，流程通常是“先创建申请、再上传发票、再提交审批、再查询结果”。人在 GUI 上操作时，参数绑定由程序写死；交给 Agent 后，步骤顺序和参数准备都要由 Agent 自己处理。这里最致命的问题不是“理解错了业务意图”，而是上传发票时绑定的申请 id 必须是上一步接口刚返回的那个 id，不能随便生成一个，更不能让 LLM 靠概率去“猜对”。

因此，作者把这类场景定义为**执行型 Agent**：目标是把口语化业务意图转成对一连串业务 API 的可靠编排调用，并准确维护业务实体状态。对应地，查资料、生成报告、写 PPT 这类主要传递文本内容结果的场景，才是**内容生成型 Agent**。两者的核心复杂性根本不是一个量级。

## 二、业务目标：先否决伪需求，再锁定真痛点

在技术架构之前，团队先解决的是“到底落地什么场景才有价值”。他们一开始也讨论过让 Agent 辅助企业做分析决策，例如用工分析、薪酬结构优化、考勤报表分析。这类任务更容易展示“AI 很聪明”，但团队最终把它们都否决了，因为这没有抓住用户真正愿意为之付费的痛点。

真正的痛点在事务冷启动和重复操作里。东方屹腾的 SaaS 已经能做到“一键算薪、一键代发、一键报税”，但用户仍然觉得系统学起来太难，问题主要出在第一次配置：薪资组、薪资项、组织架构、定薪调薪、考勤组、审批规则，全都要先搭起来。

因此团队最终锁定的价值定位是：让一个没有专业 HR 能力的小企业老板，只需要说“我希望以每月 1 万元综合成本使用这个人力资源”，系统就能在后台自动把工资、补贴、社保、公积金、报税等细节全部配置和执行正确。这个被选中的第一锚点场景，就是**薪资组快速搭建**。

## 三、渐进式起步：让问题推着思考走，前端尽早做精美，可观测性先行

后端语言选的是 Go，不用现成 Agent 框架。作者强调，最重要的不是技术选型，而是起步策略：**先走一小步，让问题本身推动后续抽象，而不是一开始就把全部复杂性扛在脑子里。**

第一步并不复杂：先把“用户说话 -> Agent 回复”这套基本对话管道接通。工具怎么注册、技能怎么管理、复杂工作流怎么规划，先都往后放。

这里有两条很企业化的经验：

1. **前端要尽早同步做，而且要做得像样。**  
   在企业里，一个好看的前端不是装饰，而是降低内部阻力、换取资源和信心的现实抓手。
2. **可观测性要一开始就搭足。**  
   这里的可观测不是 Agent 对世界的感知，而是开发者对 Agent“意识和行为”的可观测：一次对话里每一步 Thought / Action / LLM 调用 / 成本 / 工具动作，都要能按时间轴透明展示出来。

## 四、二元论：先把活的不确定的，转成死的可控的

往上堆的第一个能力是意图识别。作者的关键抽象是：让 LLM 不只“理解用户在说什么”，还要把理解结果**收敛成可以驱动程序执行流的控制信号**。

早期系统把意图大致分成三类：闲聊、知识咨询、任务执行。更重要的是，在这个阶段团队第一次明确识别出 Agent 运行态里同时存在两种不同的上下文：

- **控制平面**：稳定、机械、用于驱动执行分支
- **叙事平面**：自然语言、用于推理、总结、理解和生成

作者把这条原则总结成非常硬的一句话：**先把活的、不确定的，转成死的、可控的，因为只有死的东西才先能控制。**

## 五、Orchestrator：所有能力的家，加上意图网关的拦截路由

拿到意图识别的控制信号后，系统自然长出一个关键组件：**Orchestrator**。它是整个运行态的编排器，所有能力都挂在它上面。

作者的描述很清楚：最外层可以有一个 MessageHandler 这样的薄门面，负责对接用户输入和 SSE 展示；真正的控制逻辑放在 Orchestrator 里。Orchestrator 根据控制信号决定后面是结束对话、检索知识、进入推理，还是进入任务执行。

与之配套的，是一个**意图网关**：它不是“理解”本身，而是控制信号的消费者，把不同信号路由到不同的下游活动链。

## 六、推理：链式推理，每步既贡献叙事又产出控制信号

当意图是任务执行时，仅靠粗粒度意图还不够，系统需要进一步把用户目标映射到“下一步能先做什么”的问题空间里。这一层作者用的是**链式推理（Chain of Thought）**。

这里最关键的设计不是“让模型多想几步”，而是要求每一步推理的输出都必须回到结构化控制信号，明确指出下一步可以做什么：检索知识库、调用工具技能、继续推理、进入规划执行，或者直接结束对话。

作者还强调一个工程约束：**只让推理产出“下一步行动”，不要过早把全部行动一次性定死。** 因为世界状态在不断变化，每走一步都应该根据最新上下文重新决定下一步。

## 七、行动：ReAct，工具调用封装在行动能力之内

推理给出“下一步”，行动层就要承接它。作者这里不是直接裸调函数，而是把推理和行动封成一个循环能力，这就是 ReAct。

在实现上，每一轮 ReAct 都有明确的 Thought、Action、Observation 三元结构，并被追加到一个叫**草稿纸看板（scratchpad）**的结构中，后续步骤沿着这条 block chain 继续推进。

这个设计的重要点在于：**工具调用不是 Orchestrator 层的裸调用，而是行动能力内部的一部分。** 一次工具调用周围往往包着提示、校验、状态写入、观察反馈这些东西，所以它必须成为一个“行动模式”的组成部分。

## 八、规划执行：被 ReAct 的跨步漏步逼出来的

当 mock 工具、技能和知识库接上以后，团队很快发现：ReAct 适合“干一步看一步”，但不适合那种步骤顺序严格、跨步漏步就会失败的场景。

薪资组快速搭建就是这样一个例子：先匹配模板，再建立快照，再导入模板，失败则回滚。最初团队试图把这套顺序写在叙事上下文里，让 ReAct 自己沿着上下文跑。结果是：有时对，有时错，有时跨步，有时漏步。

于是系统长出了第二种行动模式：**规划执行（Plan-and-Execute）**。这不再是单纯循环，而是明确规划出任务 DAG、执行器、验收器和任务状态机。每个节点的调度条件、依赖状态和完成条件，都由程序来维护，而不是让 LLM 临场判断。

## 九、治理：HITL 关键任务阻塞与人审续作，借状态机水到渠成

有了任务 DAG 和状态机之后，企业级场景里很自然就会接上**HITL（人在回路）**。

作者把这类人审续作分成两种：

1. **叙事型续作**：本轮对话结束，用户在下一轮输入“继续/确认”，Agent 从叙事上下文继续做；
2. **阻塞型续作**：执行流在当前轮次某个节点阻塞，等待人工审批通过，再从阻塞点恢复。

第二种更复杂，但一旦任务图和状态机已经存在，实现起来就顺理成章：哪些节点需要人工审批，可以用声明式配置挂到任务或工具上。

## 十、机械状态平面：这套系统最核心的复杂性

这是全文最关键的一节。

作者指出：即使有了规划执行，如果任务之间的参数传递仍然是“把上一步结果塞进对话上下文，让模型从里面取出 template_id 再传给下一步”，系统依然不稳定。因为 LLM 本质上不是在“读取参数”，而是在“尝试生成参数”。

在薪资组场景里，`template_id` 往往是 64 位甚至 128 位随机字符串。让模型原样复现这种字符串，本质上是拿概率模型去做确定性键值复制。这不是提示词工程能根治的问题。

团队最终的解法是严格分离出一个**机械状态平面（SessionState）**：

- 所有工具在注册时就声明自己会生产什么参数、消费什么参数；
- 参数不是混在叙事上下文里，而是写进一个独立的、按坐标管理的状态平面；
- 每个参数都有唯一坐标和 Provenance（来源坐标）；
- 消费者去“读格子”，而不是让模型去“猜字符串”。

作者把这套机制的执行链路概括为：**Skill 声明 SOP，Workspace 保证顺序，Tool 声明状态的生产与消费，SessionState 存值加 Provenance，RunPipeline 统一解析。**

## 十一、会话统一状态平面：三权分立

当叙事平面和机械状态平面都清晰之后，团队进一步把运行态收敛成一套**会话统一状态平面**的三分法：

1. **叙事状态平面（SessionNarrative）**  
   回答“用户要什么、做到哪了”，负责目标、进展、总结和对话理解。
2. **机械状态平面（SessionState）**  
   回答“API 参数从哪来、对不对”，负责严格键值、契约和参数绑定。
3. **任务调度状态平面（Workspace）**  
   回答“先跑哪步、跑完没有”，负责 DAG、节点状态和调度语义。

作者认为，把这三件事拆开，是执行型 Agent 真正稳定交付的根本。

## 十二、叙事平面的核心三件套：锚、账、集

叙事平面内部，作者又给出了一套非常实用的三件套：

- **锚（anchor）**：固定保留用户原始目标，防止长链路推理逐渐偏题；
- **账（ledger）**：按里程碑追加关键进展摘要；
- **集（collection）**：在关键推理入口，从账里再做一次蒸馏投影，形成当轮需要注入的临时上下文。

这套设计本质上是在回答：“长任务怎么记住初心，又不让 prompt 被历史信息塞爆？”

## 十三、记忆体系：L1 / L2 / L3 分层与经验教训召回

除了会话内状态，系统还配了分层记忆：

- **L1 / L2** 负责不同粒度的事实和持久信息；
- **L3** 保存经验教训类语义，在关键推理入口被召回。

作者特别提醒：**不要每一步推理都召回记忆。** 成本太高，也会加重噪声。更好的做法是在链式推理入口、ReAct 首轮、任务规划等关键入口召回 L3，让“第一步走对”的概率更高。

## 十四、架构全貌与迁移指南

全文最后把这条演化路径收束成一条清晰主线：

1. 先区分执行型 Agent 和内容生成型 Agent；
2. 锁定真实痛点，而不是做漂亮但无刚需的生成式分析；
3. 从 ChatLoop 起步，前端和可观测性先行；
4. 在意图识别处识别出控制平面与叙事平面的二元论；
5. 长出 Orchestrator 和意图网关；
6. 用链式推理和 ReAct 把 Agent 跑起来；
7. 被 ReAct 的漏步问题逼出规划执行、DAG 与状态机；
8. 基于状态机顺势接上 HITL；
9. 为了解决最核心的参数绑定问题，长出机械状态平面；
10. 最终收敛成三权分立的会话统一状态平面，加上锚账集与 L1 / L2 / L3 记忆体系。

作者给出的迁移判据也很硬：

- 你的场景是不是**执行型**？
- 步骤之间是不是有严格依赖和参数传递？
- 参数错一位会不会导致失败甚至破坏数据？
- 系统是不是企业级封闭体系，工具由你自己统一注册和治理？

如果答案是“是”，那么这篇案例给出的不是观点，而是一套很值得照搬的执行型 Agent 工程骨架。反之，如果你的场景本质上还是文本内容生成，那 MCP 本来就是好方案，不必把任务图、状态机、机械状态平面这整套重机制硬搬进去。
