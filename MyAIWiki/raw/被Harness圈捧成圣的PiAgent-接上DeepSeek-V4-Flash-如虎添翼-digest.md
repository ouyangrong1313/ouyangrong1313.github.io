## 一句话总结

Pi 将 Coding Agent 做成只提供少量原语的薄 Harness：把模型、上下文、工具和工作流的选择还给使用者；文章以 Pi 搭配 DeepSeek-V4-Flash 的跑分为例，主张端到端成本更取决于上下文纪律，而非模型单价。

## 核心观点

1. **原语优先**：Pi 默认只暴露 read、write、edit、bash 等基础能力；子代理、计划、MCP、权限与 UI 均作为可选扩展，反对将所有能力固化进内核。
2. **上下文是成本变量**：文章的关键判断不是“薄一定更强”，而是工作集更小、稳定前缀更长时，模型可减少重复预填充和无效来回，从而同时改善延迟与总成本。
3. **模型和 Harness 应分开评估**：同一模型放进不同 Harness，质量、工具调用次数和端到端成本会显著不同；文章援引 Databricks 与 Composio 的测试，但这些数字应回到原始基准核验。
4. **模型路由按任务能力切换**：DeepSeek-V4-Flash 被用于低成本文本任务；Doubao-Seed-Evolving 被用于截图、录屏、PDF 等多模态任务。两者是能力互补，不是单一模型的替代关系。
5. **可扩展性是 Pi 的主要价值**：TypeScript 扩展、按需加载的 skill、会话树、跨会话记忆与子代理均可后装；用户可把高频工作流沉为自己的扩展，而非等待产品内置。

## 8 个知识节点

- **薄 Harness**：只保留模型执行所需的最小脚手架，把高层工作流变成可替换扩展。
- **原语优先**：优先提供可组合的基础操作，不把每一种使用方式预制为内核功能。
- **上下文纪律**：稳定前缀、按需加载和旁路隔离共同减少无关上下文进入每轮请求。
- **端到端成本**：评价 Agent 不只看 token 单价，还要合并成功率、输入量、轮数、延迟和人工补救成本。
- **模型路由**：按文本、视觉、长上下文或速度需求选择模型，并在会话中切换。
- **扩展热加载**：以外部模块增加能力，使工具链和工作流可快速试验、替换与回滚。
- **摘要回传**：多 Agent 任务只回传必要结论，避免子任务日志污染主会话上下文。
- **扩展治理**：插件越多并非越好；兼容性、权限、维护成本与上下文开销都应成为准入条件。

## 对 Seetong / MyAIWiki 的启发

1. 为每个 Agent 任务记录输入 token、轮次、成功率和人工返工，而不是只比较模型价格。
2. 将项目规则、任务证据和高频 SOP 分为始终加载、按需检索和子任务隔离三层，避免规则堆入系统提示词。
3. 先为视觉审查、代码编辑、知识检索定义模型路由表，再决定是否引入多模型，而不是按宣传选择模型。
4. 对 Skill 或插件建立最小准入项：用途、权限、依赖、上下文代价、验证方式、卸载路径。
5. 多 Agent 的主线程只接收结构化摘要与证据链接，完整日志留在子任务侧，降低上下文污染。

## 证据边界

- 文中的 GitHub star、模型供应商数量、Databricks/Composio 跑分、成功率和美元成本均来自公众号转述，尚未在本次编译中回查原始项目和 benchmark。
- "Pi + DeepSeek-V4-Flash 最便宜且通过最多任务"只适用于文章所述任务集与配置，不能外推为所有仓库或工作流的结论。
- 插件、模型支持和订阅授权的可用性会随版本和地区变化，实际采用前应读取 Pi、模型服务商和扩展项目的当前文档。
