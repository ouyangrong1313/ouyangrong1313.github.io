## 一句话

把 Agent 的工作起点从人的逐条指令改为事件触发，再用统一路由、专属 Skill、隔离 CI 和风险分级审批，让任务自行推进，只把真正需要判断的事项交还给人。

## 五个核心观点

1. **自动化的目标是释放注意力**：聊天式使用仍由人启动、盯进度和分拣结果；定时任务、Webhook 等事件可让系统先行动，人只处理例外与关键决策。
2. **控制面统一事件再调度**：事件被规范成来源、类型、对象、摘要和原处链接，由规则选择 Agent、模型、工作目录、Skill、并发量及通知策略；本地接单器通过长轮询接收任务。
3. **模型与 Skill 分别承担能力和流程**：按任务特点分配不同模型，Skill 固化可维护的 SOP；作者把自动化执行放在可访问本地代码和账号的设备上。
4. **交付必须越过代码生成**：文章描述的 CI 顺序是只读审查、隔离环境检查、受保护合并、隔离发布和线上版本核实；作者称其流程限制最多三轮审查。
5. **人类介入按风险而非通知来源决定**：删除、停服、花钱、外发消息、改方向、密钥和权限等事项请求确认；已作出的决定与拒绝项留存，用户反馈仍由作者亲自筛选。

## 七个分析角度与开头钩子

### 1. 为什么增加 Agent 不会自动增加产能
- 如果瓶颈不是模型，而是人只能盯住几个活跃会话，继续开窗口能解决问题吗？
- Agent 越能并行工作，谁来负责接收、排序和验收它们的结果？
- 自动化系统真正要省下的，可能不是输入时间，而是注意力切换。

### 2. 事件如何取代人工启动
- 如果每件事都要等人打开窗口，Agent 还算自动化吗？
- 定时轮询和 Webhook，分别适合发现哪类工作？
- 把任务起点从人移到事件，系统需要先定义什么？

### 3. 为什么需要统一中台
- 十几种消息来源、多个模型和一堆脚本，怎样避免调度规则散落各处？
- 一条事件至少要带什么信息，才能交给另一个 Agent 继续处理？
- 事件入口统一以后，路由规则和执行器能否独立更换？

### 4. 本地接单和去重解决什么问题
- 内网机器不能被公网直接访问，任务仍如何及时到达？
- 同一反馈被重复投递时，怎样避免多个 Agent 同时改同一件事？
- 长轮询、幂等键和任务状态，分别解决了哪一层可靠性问题？

### 5. CI 为什么要与 Agent 执行分开
- Agent 写完代码后，谁来证明它真的通过检查并成功上线？
- 只读审查、干净虚拟机和线上核实，分别阻断哪类失误？
- 如果审查可以无限重试，怎样避免流程陷入无休止挑错？

### 6. 什么事情必须推给人
- 怎样让审批卡片只代表真正需要承担的风险，而不是另一个消息入口？
- 删除、密钥、权限和对外表达，为什么不该与普通可逆任务同级？
- 记住已批准与已拒绝的决定，能减少哪些重复打断？

### 7. 个人案例能否直接复制
- 一套在作者本地设备上跑顺的系统，迁移到团队时还缺哪些控制？
- 高并发合并请求与专用设备，是否是其速度数据成立的前提？
- 可以迁移的也许不是某台 Mac，而是事件、证据、权限和审批边界。

## 可借鉴的工程检查

1. 为事件定义稳定字段、来源校验、幂等键、状态和原始对象链接。
2. 将路由配置与 Agent 执行逻辑分开，同时限制可用模型、工作目录、并发数和网络权限。
3. 将代码审查设为只读；在隔离、短生命周期环境中运行不可信改动，并由受保护规则控制合并与发布。
4. 对外部副作用配置风险级别、幂等/对账方式、回滚或补偿路径及人工升级条件。
5. 记录派发、尝试、证据、结果和决策，观察重复事件、失败类型、通知量与真实成本，再调整路由。

## 证据边界

298 个合并请求、333 条审查问题、306 条修复、51 条最高级别问题，以及中位数时长、Token 占比和成本对比，都是作者对其四个项目及特定两周/月份的自述，不是独立审计或通用基准。文中关于 DeepSeek 的会话数量及朱元璋奏折的历史叙述也未在本次入库中另行核实。系统表现还可能依赖单一操作者、统一技术栈、专用机器和作者对业务的熟悉程度；文中未充分交代队列认证、密钥隔离、故障恢复和完整回滚机制，不能据此直接推断适用于多租户或高风险生产环境。
