## 核心观点

1. **Super-agent 的命名说的是架构位置，不是能力等级。** 它指在执行任务的主 Agent 之上增加一层协调角色；不是宣称 Agent 变得“更超级”。
2. **它试图处理跨任务连续性与任务吞吐量之间的张力。** 长程记忆尚无行业共识；回答者称截至这次回答时，DeepSeek Harness 尚无内置跨 Session 长期记忆，后续状态可能变化。
3. **双层架构是一种问题拆解方式，而非已证明的唯一最优实现。** 主 Agent 负责跨任务判断与协调，执行 Agent 负责具体 Ticket；层间上下文和授权边界决定了复杂度。
4. **dsh-superagent-prototype 仍是受限原型。** 回答者称它在小规模、受信任的内部环境运行；文章提及的计算、状态、环境解耦等部分设计在当时仍有较多实现工作。
5. **扩展到真实团队前仍有开放问题。** 回答者点名双层架构扩展、Session 外人机协作、上下文边界与 A2A，以及安全和隐私；不能把概念方案等同于生产成熟度。

## 7 个分析角度与 21 个开头钩子

### 1. “Super”到底表示什么
- Super-agent 是能力更强的 Agent，还是站在执行者上方的调度层？
- 先弄清命名来自架构位置，才能看懂它与 Sub-agent 的关系。
- 多一层 Agent 不自动代表更强；关键是它负责什么、何时交给执行者。

### 2. 连续性和吞吐量为何冲突
- 一个 Session 同时维持大量历史与快速并行处理多个任务，为什么容易互相牵制？
- 双层设计试图把跨任务判断和单任务执行拆开，但代价是更多交接与上下文边界。
- 长程 Agent 的难题不只是记住更多，而是如何在连续性、并行度和控制成本间取舍。

### 3. “记忆”不是一个问题
- 一个 Agent 能恢复未完成工单，不等于它拥有跨项目的长期语义记忆。
- 如果长期记忆方案尚无共识，调度层就不应被误读成完整记忆系统。
- 任务状态、会话历史和可检索的项目知识，是三个不同的持久化问题。

### 4. 设计蓝图与可运行实现的距离
- 文章中的理想结构，哪些已经进入原型，哪些还停在设计讨论？
- 计算、状态和环境解耦听起来整洁，真正落地还要处理恢复、权限和工具边界。
- 读 Agent 架构文章时，先问“代码里实现了什么”，再讨论它“理论上能做什么”。

### 5. 小规模受信环境不能证明规模化
- 一个内部团队跑通原型，能证明什么，又不能证明什么？
- 当参与者、权限和任务范围都较小，系统复杂度可能被暂时压低。
- 从内部实验走向真实团队，需要重新验证身份、上下文、审核和故障恢复。

### 6. Session 外协作与上下文边界
- 人不在 Agent Session 里时，任务如何继续、插话、暂停和恢复？
- A2A 不只是让 Agent 互相发消息，还要说明谁拥有任务、哪些上下文能共享。
- 上下文越多不一定越安全；跨任务传递前要先确认范围和数据来源。

### 7. 如何迁移到 APP 研发
- 要借鉴 Super-agent，先找现有工作流的真实瓶颈，而不是先装一个新框架。
- 事件入口、Ticket 状态和人工放行若已存在，新增运行时可能反而复制控制面。
- 试点要证明的是少了多少人工协调、恢复是否可靠、风险是否可控，而不是 Agent 数量增加了多少。
