## 核心观点

1. **流程不变，执行权变化**：可行性、设计、原型、实现、验证仍需存在；Agent 接管执行，人保留方向、取舍和验收。
2. **文档即跨 Session 记忆**：设计文档既供人审查，也是将已确认决策传给后续 Agent 的上下文载体。
3. **高精度原型是低成本确认点**：把需求、交互和 UI 尽可能合并到可修改的原型，避免实现后返工。
4. **验证应分层**：Agent 先跑测试、调试和截图；人再以普通用户视角做黑盒验收，并按风险决定是否增加 Code Review。
5. **Skill 投资应移向代码两侧**：模型编码能力足够时，设计确认、测试、部署和发布自动化比复杂 prompt 更值得优先建设。

## 七个分析角度与开头钩子

### 角色迁移
- AI 没有删掉研发流程，它把执行者换成了 Agent。
- 不写每一行代码后，工程师真正负责什么？
- 编码变快后，技术负责人该把时间花在哪里？

### 可行性先行
- 最省 token 的功能，往往是从未开工的错误功能。
- 让 Agent 给方案很容易，真正难的是人敢不敢砍掉它。
- 可行性分析为何在 AI 时代反而更重要？

### 文档即记忆
- 新 Session 从零开始，不是模型的问题，而是决策没有留下来。
- 设计文档在 Agent 时代重新变成基础设施。
- 一句“按这个文档实现”如何替代一长串重复解释？

### 原型即确认
- 实现前多花一小时改原型，可能省下几天重写代码。
- 高保真原型正在把 PRD、交互和 UI 拉到同一张桌子上。
- 用户体验的判断，为什么不应等到功能写完？

### 自验证闭环
- 最有价值的不是让 Agent 写代码，而是让它先发现自己的错。
- 测试、截图和调试如何让人少介入一轮？
- 没有反馈循环的 Agent，只是在更快地产生初稿。

### 黑盒验收边界
- 不看代码就合并，什么时候可以，什么时候不可以？
- 开发者测试通过，不代表普通用户用得明白。
- 两层验证如何替代部分人工确认，而非取消确认？

### Skill 投资重排
- 模型会写代码后，开发类 Skill 还该优先装吗？
- 代码两侧才是 AI 原生开发的新瓶颈。
- 比起打磨 prompt，为什么更该投资设计与发布自动化？

## 证据边界

- 本文是单个 BaoCut 功能迭代的实战复盘，不是不同项目、模型或风险等级上的对照实验。
- “大部分功能可只做黑盒测试”是作者的风险取舍，不能直接用于安全、金融、隐私或高可用核心链路。
- 对编码类 Skills 的评价是作者经验判断；复杂遗留系统、特定领域或受监管项目仍可能需要专门规则和工具。
