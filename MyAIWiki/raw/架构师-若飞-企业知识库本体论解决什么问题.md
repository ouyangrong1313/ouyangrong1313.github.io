## 正文

### 文档找到了，事实还没有成立

文章从供应商付款案例开始：准入材料称品牌甲的收款主体为乙公司，合同却称签约主体为丙公司。系统可检索到两段原文并给出引用，但无法把答案交给付款流程，因为收款主体与签约主体不是同一种关系；两份材料的生效时间、权威性，以及缺页是“不存在”还是“未知”，都不能由相似度决定。

作者将本体定位为共同语义：对象、关系和状态进入系统后，组织是否在说同一件事。RAG 擅长找依据，但不裁决冲突与有效性；SQL 或业务 API 适合查询权威系统的当前状态，但不能自动解释字段语义、权限和跨系统使用边界；知识图谱显式保存实体、关系和路径，但不决定一条边的业务含义、有效时间或确认人；本体、关系字典和领域规则补的是类型、约束和推理规则。工作流、Agent、策略系统负责查询、审批和动作，但不能反向补齐缺失事实。

### 本体是语义合同，不是复杂关系图

本体首先要求对象有稳定身份：品牌甲、甲品牌和系统中的 `brand_1024` 可能同一对象，名称可变而身份不能漂移。其次关系必须具有明确谓词：签约主体、收款主体、开票主体虽然两端均是公司，却服务不同判断；将其合并为 `related_to` 会使付款、开票和合同核验失去依据。

真实关系还需要有效期、版本和状态。模型刚抽出的候选、业务已确认的事实和被来源撤回的关系应可区分；“最新写入”不等于“当前有效”。缺失与冲突也必须显式表达：未出现收款主体不等于不存在，两份材料冲突不能静默择一。未知、冲突、待确认和已撤回应当成为系统结果。

本体不能证明合同真实、替负责人批准事实或给 Agent 发付款权限。它约束如何理解，不包办来源可信与动作获权。

### 为什么模型时代更需要语义治理

文章认为 LLM Wiki、GraphRAG 与 Palantir Ontology 代表三条相关但不同的线。LLM Wiki 以 Markdown 中间层整理主题、实体、交叉引用和矛盾，减少重复研究，但仍是整理层，不能自动获得版本、责任人和确认状态。GraphRAG 在索引阶段抽实体、关系与声明，帮助跨文档综合，但模型产出首先是候选，仍可能别名合错、关系抽反或把推测写成事实。Palantir 将对象、属性、链接、动作、函数和安全治理纳入企业平台；它不能直接等同于 OWL 标准，也不要求每个企业复制其形态。

模型越快地整理、抽取和编排，未解决的语义分歧就被越快放大。本体处理的是组织对知识的共同理解，而不是替换 RAG 或知识图谱。

### 从证据到动作的四层责任

作者建议将企业知识库拆为四层：

1. **证据层**：保存合同、制度、网页、接口响应及来源、时间和版本，尽量保留原貌。
2. **事实层**：保存从证据提出的主张，附稳定 ID、来源、有效期、状态、模式版本和责任人；候选不能与已确认事实混同。
3. **语义控制面**：本体、关系字典和领域规则规定对象类型、谓词含义、两端约束、可做推断和必须暴露给人的冲突。
4. **动作层**：权限、审批、幂等、回滚和审计；Agent 可查询和请求确认，业务完成证据仍来自外部系统。

推理、校验和授权应分开。OWL 2 可表达类别、关系及部分推断；在开放世界假设中，缺少一条事实通常代表未知而非假。SHACL 可检查图数据是否满足形状和字段约束，但通过校验不证明来源可靠。权限、批准和执行仍属于策略系统。付款流程未找到当前有效收款主体时，应返回证据不足并暂停补证，而非推断不存在或默认放行。

### 从一个真实决定开始实施

不要先设计全公司概念模型。应从供应商准入主体核验、设备与配件适配或故障服务归属等具体决定开始，先明确输入、输出、责任人和失败后果。

第一步是来源地图：哪些材料只能提出候选，哪套系统记录当前状态，冲突由谁确认，何时旧材料失效。第二步是最小语义合同：先定义少量对象和关系，并写清关系含义、主宾语类型、多值性、有效时间、发布所需证据、冲突和缺失返回方式及使用流程。第三步是事实生命周期：模型抽取主张进入候选区；经实体消歧、关系校验和必要人工复核后进入 `validated` 或 `published`；来源有误则进入 `retracted`，不能静默覆盖旧事实。

最后应以反例验收：冲突的收款主体能否阻断自动动作，缺少生效日期是否返回未知，来源撤回能否重算下游结果，关系谓词抽错在哪层被拦住，Agent 无写权限时是否只读核验并拒绝执行。

### 什么时候不必做本体

只需找到制度原文时，全文检索或 RAG 往往足够；查询当前订单和库存时，直接接权威 SQL 或 API 更合适；对象少、规则稳定时，关系表加校验器可能优于完整语义技术栈。只有同一组对象和关系被多个系统与流程长期复用、语义分歧已造成真实错误，且有人能持续维护版本、冲突和责任归属时，本体投入才有意义。
