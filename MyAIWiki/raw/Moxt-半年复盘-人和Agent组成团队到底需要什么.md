## 01 Agent 能干活了，为什么进不了团队工作？

团队中越来越多人使用 Claude Code 和 Cursor。它们不再只是研发工具，产品和运营也用 Agent 处理数据、做调研、生成报告、写网页和搭建内部工具；代码成为 Agent 操作数字世界的方式。但 Agent 很少参与功能定位、需求价值分析和 PRD，因为它不了解产品现状、历史决策和决策原因。

为让 Agent 参与更多工作，作者会把文档导为 Markdown 放到本地，再在 Prompt 中补充散落在脑中的背景。这只能服务一次任务、一个人；换同事要重新找资料、重新讲背景，洞察和产物也无法自然流入其他人的 Agent。Agent 已能干活，但每次开工前人仍要替它临时搭工作环境。第一层认知是：AI 协作的前提不是 Agent 够聪明，而是团队 Context 可共享、可获取。

## 02 给了 Context 还不够，读得到和能信赖是两回事

Moxt 的第一个 demo 用文件系统作为共同工作空间，优先使用 Markdown、CSV 和 HTML：Markdown 承载文档，CSV 保存结构化数据，HTML 可长成页面、看板和内部工具。人和 Agent 操作同一份材料，Agent 可把 CSV 分析写入 Markdown，并生成读取同一数据的 HTML 看板，产物留在团队空间供同事和其他 Agent 继续处理。

内容较少时，Agent 易掌握现状；内容积累后，它难以辨别已拍板的当前结论、个人草稿与失效材料。对话式 Memory 同样可能记得讨论，却不知道结论是否采用、后来是否被推翻。来源、时效和事实层级混在一起时，读得到反而更危险。第二层认知是：Context 不仅要足够多，还要有信任结构。原始事实、分析过程与最终结论需要在结构上区分，并用内容位置、维护责任和更新路径表达可信度。

## 03 能力共享之后，真正要回答的是谁来负责

数据分析和 Bug 分拣等工作会反复发生，且依赖统一的业务口径和规则。若每个人都在自己的 Agent 中重建，既重复建设，又无法把改进变为共同能力。因此团队除个人助手外，也需要共同使用、共同维护的 AI 角色。

Moxt 将角色分为随个人工作的助手 momo 与团队共用的 AI Teammate，底层结构均为 Rules、Skills 和 Memory。此时问题从“会不会做”变为谁可修改规则、谁可派活、角色能访问什么信息、表现不好由谁负责。团队曾为很多一次性任务创建角色，后来发现职责重叠而清理合并。第三层认知是：AI Teammate 的拆分是划分可长期管理的责任，而不是把能力切得越细越好。角色是责任单元而非功能切片；角色过宽会让 Rules 与 Memory 膨胀，角色过多也会增加规则、权限与关系的维护成本。

## 04 有了人和角色，为什么整件事还是靠人调度？

传统管理组织人、事、流程。Agent 进入团队后，流程也要把人和 Agent 组织起来，明确每一步由谁负责、完成后交给谁。团队曾要求 Agent 完成后通过文档或评论中的 @ 交给下一个 Agent。这能串起流程，但每次都要重新说明交接对象和材料，任一步漏交接就会停滞。

单个节点越快，人的协调压力可能越大：PM 更快完成调研与 PRD 后，讲解、评审和研发对接仍需人工推动，产出越多协调越多。第四层认知是：AI Team 需要显式 Workflow，明确任务在谁手上、完成后交给谁、卡住时谁判断。Workflow 不是追求全自动，而是重新安排人在流程中的位置。

## 05 Workflow 解决什么问题，人如何参与？

Moxt 在 6 月初内部灰度 Workflow，6 月 24 日正式上线。其 Workflow 不是把几个 Agent 串成无人介入的流水线，而是人和 Agent 共用的责任系统：一件事对应一个 Task，Task 在状态间移动，每个状态有明确负责人，负责人可以是人或 Agent。系统必须回答任务在何处、谁负责、当前交什么、下一步谁接；产品方向、技术风险、体验品味与最终验收交给人，Agent 遇到证据不足、风险过高或权限不足也要明确交回。

### 选择 Workflow 化什么

文章主张优先改造占据大量团队时间的主链，而不是只自动化低占比小任务：占用 1% 时间的工作即使完全自动化，整体只省 1%；占用一半时间的工作即使仅减少一半人工投入，整体可省 25%。

产品到研发主链的例子是：反馈进入产品判断流后，Agent 保留原始信息、查重、定义问题；证据不足时补代码现状、用户反馈或外部信息，最后把带证据的决策建议交给 PM。决定做后，Agent 起草 PRD，另一 Agent 独立检查事实与完整性，再进入技术方案和开发。明确边界内 Agent 可实现；缺信息、权限不足或无法独立验证时，由研发接手或协作。代码合并后，产品沉淀流更新内部功能说明，帮助文档流判断是否更新用户内容，使本次产物成为下次任务的可信 Context。

### 从同步跟着做，到异步审阅

同步参与时，人持续给材料、拆任务、看过程、纠错，时间并未释放；审阅式参与让 Agent 带着完整 Context 先交一份产物，人异步留下意见，Task 再回到 Agent 修改。

截至 8 月 4 日，Moxt 自述：106 份进入后续阶段的 PRD 中有 98 份（92.5%）按审阅制完成，8 份需 PM 持续对话；审阅制 PRD 的 90% 在三轮内定稿，中位数一轮。168 个可判断实现方式的已完成任务中，67 个由 Coding Agent 独立实现、研发主要审阅（39.9%），34 个先由 Agent 完成后转为人工接管或共同收口。五条主干流在不到两个月承载 1,386 张 Task；每周需求产出约为此前 5 倍，平均单需求实现规模约为此前 60%；PRD 撰写至进入开发由 5.3 天降至 3.1 天，至交付由 14.6 天降至 9.0 天。以上是单团队自述，缺少独立对照或可复现数据。

## 06 从完成这一次，到持续迭代和进化

日常使用 Agent 的目标是完成本次任务；建设 AI Native Team 还要让下次更好。现场纠正 Agent 能恢复当前任务，却不保证经验留下。团队应把 AI Teammate 当作需要持续维护的产品并指定负责人，依次检查目标是否清晰、输入是否完整、信源是否可靠、路径是否明确、工具权限是否到位、人的反馈是否沉淀进 Rules、Skills 和 Memory。

文章称，Agent 每晚回顾当日工作与协作并做自评和 360 度环评；人和 Agent 都可提交问题。角色自身问题进入“AI 员工改进” Workflow，跨角色问题进入“协作机制升级” Workflow。验收不是改完规则或流程，而是在下一次真实任务中检查同类问题是否还会发生；缺回退路径就补回退，交接含糊就写清责任，具体做法留在对应 Skill 中。第五层认知是：AI Team 需要持续改进闭环，且改进标准是同类问题下次不再发生。治理也会消耗注意力，过度立项或加规则可能让系统更复杂却不更可靠，故还要评估维护成本是否值得。

## 07 回头看，AI 是怎样进入团队的

AI 进入团队经历思考伙伴、个人助手、团队成员和团队日常运行方式四个阶段。关键在于准确 Context 与主动推进的 Workflow：Agent 要能检索团队知识并区分当前事实、过程草稿和过期材料；也要知道任务停在何处、完成后交给谁、受阻时谁判断、失败如何被发现。

文章用一个思想实验判断 Agent 是否真正进入团队运行方式：撤掉所有 Agent 后，团队只是变慢，还是必须换回另一套工作方式？若只是变慢，AI 仍是效率工具；若责任分配、交接方式、知识组织和人的参与位置都要重建，Agent 已进入组织运行。结论是，AI Native Team 不是预先设计出来的，而是在真实工作里持续观察停点、解释原因、调整 Context、角色和 Workflow 后逐层形成。
