## 正文

每天挑选一期硅谷 AI 科技值得关注的播客，让你与前沿同频。如果你现在没空可以收藏进 晚点再听 LaterCast，在通勤、走路或做家务时一篇篇轻松听完。

- "AI 会写代码，但你仍然应该学习编程。"
- "把太多思考外包给 AI，人会离亲自解决问题越来越远。"
- "去做东西，做有人使用、有人喜欢的东西。"

Chris Piech 是斯坦福大学计算机科学教授，他发起的在线编程项目 Code in Place 已经运行六年，课程横跨 Cursor、Claude Code 出现前后，他正好能看到学生如何使用 AI，也能看到哪些用法让学习变快，哪些用法会把人推向放弃。

机器已经会写代码，为什么还要花时间学编程？Piech 谈到 AI 导师为何会打击动力、真人十分钟的帮助怎样改变完课率，也分析了把代码交给 Claude 五周后可能冒出的架构问题。

### 四年后的不确定性，让学生失去学习动力

Code in Place 的报名人数几乎翻了一倍，想学编程的人比以前更多。与此同时，Piech 看到的动力危机也比过去明显。一个学生现在选择四年制专业，既要考虑今天能做什么，也要猜 2030 年的岗位会长什么样，那时的 AI 又比现在多走了四年。

"如果你开始一个四年项目，就得想想 AI 再进步四年后，2030 年还有哪些工作。"

这种焦虑很容易把"AI 能做"变成"我不必再学"，编程、写作、概率论和论证能力都受到影响。Piech 拒绝顺着这条路往下走，因为工具能完成任务，并不等于使用者可以放弃理解。**当 AI 放大一个人的能力时，原有基础会决定这次放大究竟带来产出，还是带来一堆自己看不懂的结果。**

他提到一位能力很强的学生，对方一直用 AI 做东西、解决问题，状态反而很好。Piech 问他如何看待 AI 的未来，学生说自己基本不想这些，只管保持好奇、继续学习。这个回答让每天要想十次 AI 的 Piech 停下来重新看问题：反复预测未来，有时只是在消耗今天动手的力气。

### 计算器普及以后，孩子仍然要懂乘法

Piech 用乘法解释这件事：计算器早就能算出 13 乘 7，孩子依然需要理解乘法是什么，只是背诵每一道算式的重要性降低了。编程也会出现类似变化，记住每条命令的价值正在下降，理解程序如何表示问题、数据如何进入算法，仍然需要自己掌握。

"我们不能跳过基础，但可以更讲究把时间花在哪些基础上。"

他把编程学习拆成两块：一块是告诉计算机做什么的语法，另一块是把大问题拆开、组织数据和设计算法。AI 会越来越擅长前一块，人的训练重心自然会向后一块移动。**基础课的目标也该随之改变，少考一点记忆，多让学生解释自己的拆解过程和架构选择。**

Piech 当年刚接触编程时，很快被创造东西的感觉吸引。两周知识已经足够让他开始制作，他随后愿意主动投入 40 个小时，把还不熟悉的概念一个个补起来。先让学生体验自己能做出什么，再沿着作品追索原理，这种动力比一张命令清单更耐久。

### 真人聊十分钟，完课率提高十个百分点

Code in Place 起源于疫情初期，斯坦福的旗舰编程入门课当时被迫转到线上。Piech 和团队想把课程开放给更多人，却发现只上传视频远远不够。斯坦福学生身边原本有一位年纪稍长、经验多一点的助教，愿意花时间陪他把问题想清楚，这层支持在线上最容易丢失。

项目六年里试过不同剂量的 AI，直接把聊天机器人交给学生，退课和失去动力的情况会增加。团队后来把 AI 放进学习过程的恰当位置，效果才开始改善。**答案是否准确只是其中一层，课程还要判断学生何时需要提示、何时需要自己卡一会儿，以及谁来让他愿意继续。**

学生写代码时会收到一个弹窗：有位教师在线，愿意和你聊十分钟，要不要接通？只要学生选择愿意，完成课程的概率就会提高 10 个百分点。团队回看过这些对话，AI 给出的答案通常正确，真人教师反倒偶尔会说错，决定结果的是有人在乎学生是否继续成长。

"AI 的答案是对的，真人并不总是对，可人与人的接触会带来动力。"

聊天机器人擅长回答已经被提出的问题，教师还会主动拿出一个学生从未想到的概率题，让他兴奋到整天都想继续研究。要做到这件事，教师需要知道学生处于什么水平、准备往哪里走，再挑一个刚好够难的例子。**清晰解释可以规模化，点燃好奇心却依赖关系和上下文，当前 AI 导师恰好缺少这一层。**

### 原型第一天能跑，架构问题第五周才出现

Piech 自己经常用 AI 编程，也有足够的编程和架构经验检查结果。他观察到，AI 做出的坏选择未必会在原型阶段暴露，麻烦可能等到五周后，学生开始使用产品时才变成奇怪的错误。那时如果开发者看不懂架构，连问题藏在哪里都很难判断。

"我用 AI 编程很多，但我碰巧也懂编程和架构。"

论文和代码面对同样的风险，AI 代写得越多，亲自写作和完成关键架构的能力越容易生疏。Piech 并不反对使用工具，他要求学生留意自己是否和 AI 一起成长。**产出看起来越来越快时，使用者可能正慢慢失去判断质量、追查错误和接管工作的能力。**

他把这个边界问得很朴素：如果 AI 写了太多论文，一个人会在什么时候失去独立写作能力；如果 AI 接手太多代码，他又会在什么时候无法完成架构里最有价值的部分。工具用得越顺，越需要定期关掉自动驾驶，确认自己还会做哪些事。

### 学编程，是为了获得快速而诚实的反馈

编程有一种很少见的训练价值：反馈来得快，也可以被证伪。逻辑错了，程序就不能工作，改完以后结果马上变化。生活中的判断常常要几个月甚至几年才看得出后果，一个人很难用同样密度练习拆解问题和修正决定。

"AI 会非常擅长语法，未来更重要的是你会不会解决问题。"

Piech 因此仍然鼓励学生学习编程，因为未来工程师即使不再靠记住 API 获得优势，也要判断需求、拆开任务、验证假设，并在工具走偏时把系统拉回来。**代码只是练习场，被反复训练的是面对一个模糊问题时，怎样把它变成可以检验的一连串选择。**

### Claude Code 最好的用法，是边做边补课

Piech 给年轻人的练法很直接：用 Claude Code 做大量原型，同时让它解释完成这个原型所需的核心概念。这样既能利用工具降低制作门槛，也能在一次次迭代里补上知识。他把高贡献工程师的成长归结为一件朴素的事，一个人亲手创造的时间有多少。

"我会做很多 Claude Code 原型，再让它教我完成这些东西所需的核心知识。"

这里要分清"你在创造"和"你把任务交给 Claude"所占的比例。只看生成了多少代码，很容易把调用工具的熟练度误当成工程能力。**更有效的循环是先做出东西，再追问工具替你做了哪些决定，随后自己修改、验证，直到能说清系统为什么这样工作。**

"花在任务上的时间"听起来很老派，却能抵抗一种常见错觉：原型生成得快，经验就积累得快。Piech 更看重学生在多次迭代里遇到不同失败，再把重要概念从工具手里拿回来。完成十个小产品，也该留下十次自己做判断的痕迹。

### 初级工程师可以更早面对真实用户

AI 降低了进入软件开发的门槛，一个 18 岁的高中毕业生和朋友已经可能做出质量不错的代码库，甚至围绕它创办公司。过去往往要到资深阶段才接触的问题，如今会提前摆到初级工程师面前：什么值得做、用户到底需要什么、哪个功能能让对方继续推进工作。

"如果我是初级工程师，我会现在就练习理解什么值得做，不会等到成为资深工程师。"

Piech 认为，顶尖工程师未必是记得最多代码的人，更可能是能把现实中的人类问题接到应用、数据科学和研究上的人，这也为职业阶梯增加了一条新入口。**年轻工程师不用等权限和年资慢慢下放，可以借助 AI 提前练习选问题、见用户，并承担自己做出的产品选择。**

### 职业变化通常比演示视频慢得多

Piech 在 2011、2012 年读博时，已经看到自动驾驶取得重大进展，当时很多人以为出租车和卡车司机很快会消失，实际结果是卡车司机的就业人数仍在增长。真实道路有大量长尾情况，价值昂贵的货物也需要有人负责，演示中的能力因此迟迟无法完整替代一项职业。

"公路上 99% 的情况可以相同，剩下 1% 的不同仍然很难让 AI 全部掌握。"

他相信完全自动驾驶最终会到来，只是人们严重高估了抵达那一天的速度。软件工作也可能经历类似过程，局部任务迅速自动化，整套岗位则受责任、协作和异常处理牵制。**与其反复猜五年后的岗位名称，不如观察今天哪些任务已经交给 AI，以及自己是否仍能处理那 1% 的意外。**

Piech 最后把 AI 形容为人的乘数，关心病人的医生可以借它做得更快，关心学生的教师也能把时间放到更需要人的地方。前提始终是人先有方向、有责任感，也保留足够能力检查结果，因为再强的乘数也无法替使用者决定什么值得做。

## 写在最后

学习编程的理由已经变了：先用 AI 做一个有人愿意使用的小东西，再回头补上架构、算法和需求判断，过程中保留一部分必须亲手完成的工作。工具会继续变快，你能否解释选择、发现错误，并把真实问题转成可运行的产品，决定了这次放大最终属于谁。
