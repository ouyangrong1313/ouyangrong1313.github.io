# Harness Inspector：交付证据链与 SKILL 自动沉淀速查

- 原文：[[phodal-Harness-Inspector-Agent交付可观察可检查可追溯]]

## 五个核心观点

1. Session 只能描述过程，不能独自证明任务缘由或最终交付。
2. Story/Issue/Spec、Session、Commit 分别是意图、过程、产出的证据锚点，真实关系是多对多图。
3. Workbench 看关系，Trace 看结构，Replay 看顺序，三者不可互相替代。
4. 工具应保留证据边界：不映射不确定关系，不补全未记录推理，不重跑历史动作。
5. Skill 候选来自被产出和验证支持的跨任务稳定路径，不来自高频 Tool Call。

## 七个分析角度与开头钩子

### 交付全貌
- “看完完整 Session，为什么仍不知道这次改动算不算交付？”
- “对话不是交付，提交也不是全部上下文。”
- “需求、会话、提交连起来，才有资格评价 Agent。”

### 证据图
- “Agent 的工作不是流水账，而是从需求到提交的证据图。”
- “一个 Story 多次会话、一次会话多个 Commit，线性时间线不够用。”
- “可追溯不是存更多日志，而是让意图、过程、产出互相指向。”

### 证据边界
- “关系证据不足时，系统最重要的输出可能是‘不知道’。”
- “不要用相邻日志拼出看似完整的 Agent 故事。”
- “专业的可观测工具不替你补写没记录的过程。”

### 三层阅读
- “Workbench、Trace、Replay 不是三个页面，而是关系、结构、顺序三种问题。”
- “先确认是谁的任务，再看怎么做，最后复查关键转折。”
- “数百次 Tool Call 不可读时，缺的通常是阅读层次。”

### 只读回放
- “回放不是重跑，它不恢复工作区，也不替 Agent 重走旧路。”
- “审查历史要保留缺口，不能用今天状态覆盖当时事实。”
- “只读回放让复盘回到已保存事件。”

### Skill 发现
- “出现最多的 Tool Call，往往最不值得写成 Skill。”
- “重复读文件可能是经验，也可能是上下文不足的噪声。”
- “可复用的是被多次交付验证过的工作路径。”

### 改进闭环
- “先看清交付，才谈得上让下一次更好。”
- “Skill 不是聊天记录改名，而是带边界、步骤和验证的稳定路径。”
- “经验沉淀从可检查的事实开始。”
