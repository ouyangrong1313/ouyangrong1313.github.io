# 企业知识库本体论：拆解

- 对应原文：[[架构师-若飞-企业知识库本体论解决什么问题]]
- 核心命题：本体不是替代检索的“更强图谱”，而是让对象身份、关系含义、有效状态和冲突处理可被共同解释的语义合同。

## 核心观点

1. **召回不是事实**：RAG 找到证据不代表系统知道当前哪条关系可用于业务动作。
2. **关系必须带语义**：签约、收款与开票主体不能压缩为同一条模糊关联。
3. **未知是合法结果**：缺失、冲突、待确认和撤回必须被显式表达，不能静默猜测。
4. **四层责任不可混同**：证据、事实、语义控制与动作授权各有不同所有者与验证方式。
5. **候选不能直接成为生产事实**：模型抽取应先进入生命周期，再经校验和确认发布。

## 七个分析角度与开头钩子

### 1. 检索与事实
- RAG 能给出两段冲突合同，为什么付款流程仍不能执行？
- 文档被找到了，事实为何仍没有成立？
- 能引用原文，离能执行还差哪几层？

### 2. 关系语义
- 两家公司之间有关系，不等于系统知道这是不是收款关系。
- 图谱最危险的边，往往是看起来最通用的 `related_to`。
- 为什么签约、收款、开票三种关系不能合并？

### 3. 时间与状态
- 最新写入为什么不必然等于当前有效？
- 一条模型抽取的关系，何时才有资格进入付款流程？
- 来源撤回后，系统该怎样让旧事实失效？

### 4. 语义与授权
- 本体能让系统理解业务，却不能替系统获得付款权限。
- 通过 SHACL 校验，为什么仍不能证明来源可靠？
- 推理、校验和授权，为什么必须由不同层负责？

### 5. LLM Wiki 与 GraphRAG
- Markdown Wiki 能整理知识，为什么还不能承担事实台账？
- GraphRAG 把关系抽出来后，谁来决定它能否发布？
- 模型越会抽取关系，为什么语义治理越不能后置？

### 6. 最小语义合同
- 做本体的第一步不是画全局图，而是找一个必须做决定的流程。
- 每条关系都要写什么，才能从术语表变成可测试合同？
- 来源优先级没定，关系图再整齐有什么用？

### 7. 反例验收
- 两份材料给出不同收款主体时，系统应该回答什么？
- 缺少生效日期，为什么“未知”比默认永久有效更安全？
- Agent 没有写权限时，如何既完成核验又拒绝执行？

## 证据边界

- 文章是作者的工程观点与架构建议，供应商案例、2025 年实践回顾及方法论未提供可复现数据。
- LLM Wiki、GraphRAG、Palantir、OWL 和 SHACL 的描述应以各官方文档为准；本文未在本次归档中逐项复核。
- 本体价值取决于持续维护来源、状态、冲突和责任人的组织能力，不是引入某个图数据库或规范即可获得。
