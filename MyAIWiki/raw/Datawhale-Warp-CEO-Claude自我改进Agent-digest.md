## 一句话

不要把每次人工纠错停留在会话里：将任务规范保存在可版本化的 base skill，把反馈汇集给定期运行的 improver skill，由它提出最小 PR，并用评测和人工审查决定是否成为下一轮默认行为。

## 五个核心观点

1. **反馈沉淀**：80% 正确的 review Agent 仍可能因 20% 噪声消耗大量审查注意力；问题不一定在模型，而在反馈没有跨会话保留。
2. **双 Skill 闭环**：base skill 执行领域任务，improver skill 从已解释的人类反馈中提出最小修改，二者用 PR 串联。
3. **Skill 不是 Memory**：稳定、程序性的“怎样做”进入可审查的 Skill；瞬态推理记录不应直接变成任务规范。
4. **反馈质量优先**：能说明“为何错、期望行为为何”的反馈更可行动；反馈入口应嵌入 PR 与 issue 等既有工作流。
5. **评测与人类门禁不可省略**：错误反馈、不可验证领域和可被同一优化器修改的门禁，会让系统系统性地学错。

## 最小闭环

| 环节 | 输入 | 产物 | 门禁 |
| --- | --- | --- | --- |
| 任务执行 | base skill + 任务上下文 | review / triage / spec 结果 | 正常任务检查 |
| 反馈捕获 | 人类评论、点赞或修正 | 带理由的反馈记录 | 来源与上下文完整性 |
| 改进提案 | 聚合反馈与原输出 | base skill 最小 PR | 变更范围与归因 |
| 验证发布 | PR 与回归证据 | 已合并的新版 Skill | 人工 review、评测、可回滚 |

## 七个分析角度与开头钩子

### 1. 80% 正确为何仍不可用

- 80% 正确的 Agent，为什么可能比完全错误更消耗团队？
- 一条无用 code review 评论，究竟偷走了谁的时间？
- 真正危险的不是 Agent 出错，而是人必须逐条判断它是否出错。

### 2. 反馈为何总是失效

- 你纠正了 Agent 一百次，为什么第一百零一次还会重犯？
- 很多 Prompt 工程的尽头，是反馈在会话结束时蒸发。
- Agent 不是没听懂，是没有地方把教训留下来。

### 3. 双 Skill 如何分工

- 一个负责干活，一个负责复盘：自我改进 Agent 只需要两类 Skill。
- 不必每个任务结束都自改；让 improver 按节奏看反馈，反而更稳。
- 最小改动为什么比“重写整个 Prompt”更接近工程实践？

### 4. Skill 与 Memory 的边界

- 什么该写进 Memory，什么必须变成受审查的 Skill？
- 动态记录可以频繁变化，任务规范不能悄悄漂移。
- 当“怎么做”进入版本控制，Agent 才真正拥有组织记忆。

### 5. 让反馈低摩擦

- 用户已经在 PR 里工作，为什么还要让他再填一张反馈表？
- 点赞能告诉系统“好”，却很少告诉它“下次怎么做”。
- 最有价值的反馈不是最长的，而是能解释期望和原因的。

### 6. PR 是改进控制面

- 把 Skill 当代码 review，能避开哪些自动进化陷阱？
- 每次经验升级都留下 PR，才有可追溯的组织学习。
- 可回滚的改进，比自动写入的“聪明”更值得信任。

### 7. 自我改进何时会学错

- Agent 真正的风险不是不会学习，而是系统地学会错误规律。
- 没有验证 harness 的“自动进化”，为什么常常只是自动漂移？
- 反馈源、评测器和最终放行，至少要有一层留在人手中。

## 最小实践

1. 选择一个结果可验证、低副作用的 Agent（如 issue triage 或静态 review）作为试点。
2. 将当前稳定规范拆成小型 base skill；把参考资料和脚本改为按需引用。
3. 在现有 PR/issue 流程记录带理由的反馈，保留原输出、反馈和任务上下文。
4. 让 improver 只生成最小候选 PR，不直接修改现网 Skill。
5. 对候选运行回归或人工抽样；失败时保留为反例，不升级为默认规则。
