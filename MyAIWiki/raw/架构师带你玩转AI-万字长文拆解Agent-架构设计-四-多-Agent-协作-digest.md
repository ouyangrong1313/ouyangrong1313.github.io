> 原文主题：Claude Code 的多 Agent 架构并不是“给同一个模型分配不同超能力”，而是通过上下文隔离让每个子 Agent 在干净桌面上完成读大材料、出短结论的工作

---

## 一句话总结

**这篇文章最值得长期保留的判断是：多 Agent 协作切分的不是能力，而是上下文。子 Agent 之所以有价值，不是因为它比主 Agent 更懂，而是因为它在全新的上下文里处理局部材料，最后只把浓缩结论交回父上下文。**

## 核心观点（5 条）

1. **多 Agent 的收益来自上下文切分，不来自能力切分**：同一个模型换成子 Agent 并不会突然更聪明，真正的提升来自把大任务拆成多个干净窗口，降低注意力稀释和 lost-in-the-middle。
2. **编排者与执行者要有互补权限**：父 Agent 负责规划、分解、汇总和派发，默认不给副作用工具；子 Agent 负责具体执行，默认不给 task，防止调度树失控。
3. **Task 本质上是一个委派接口**：派子 Agent 不需要单独造“调度系统”，它就是一个普通工具调用，输入只有任务 prompt 和子 Agent 类型，输出只有最后一条消息。
4. **子 Agent 定义文件本身就是接口契约**：`description` 给父 Agent 选择角色，`tools` 给权限系统做白名单，正文给子 Agent 做 system prompt；写得模糊，就会派错活。
5. **多 Agent 框架真正新增的代码极少**：并行与串行的判断不是硬编码调度器，而是模型在一轮里发几个 task 调用的选择；框架只提供干净上下文、权限裁剪和结果回收这几个原语。

## 关键结构

| 结构 | 作用 | 为什么重要 |
|---|---|---|
| Orchestrator / Subagent 分层 | 规划与执行分离 | 防止父 Agent 越权执行，也防止子 Agent 递归膨胀 |
| `task` 工具 | 统一委派入口 | 让子 Agent 在实现上仍然是普通工具，降低框架复杂度 |
| Markdown 子 Agent 定义 | 统一角色声明 | 同时服务模型选人、权限控制和 system prompt 三个读者 |
| 全新上下文启动 | 只传任务描述 | 把历史噪声挡在外面，子 Agent 只围绕当前任务工作 |
| 最后一条消息回传 | 中间过程不回流 | 父上下文只接结论，不接整个执行轨迹 |
| 权限交集 + 预算继承 | 默认收敛边界 | 工具权限只减不增，token 预算只减不增 |

## 5 句核心金句

1. "多 Agent 协作切分的不是能力，而是上下文。"
2. "description 写得含糊就会派错活——它本质上也是一份接口。"
3. "子 Agent 不比主 Agent 多懂什么，它强的地方只是'桌子干净'。"
4. "子 Agent 需要知道的一切，都应该写在 taskPrompt 里。"
5. "我们没有写调度器，模型就是调度器。"

## 6 个对 MyAIWiki / Seetong 可借鉴动作

1. **拆多 Agent 前先问上下文是否过载**：只有当单个上下文已经读不下、记不住、聚不焦时，才值得拆子 Agent。
2. **把主线程限制成编排者**：研究、汇总、审查类任务里，主线程优先只保留 `task`、只读和汇总能力，避免一边规划一边直接修改外部环境。
3. **子 Agent 定义分三层写清楚**：`description` 写任务边界，`tools` 写白名单，正文写 system prompt，不要把三种责任混成一段长说明。
4. **子 Agent 输出强制“短结论”**：不把中间轨迹默认塞回父上下文，优先让子 Agent 只返回结构化结论、风险点或最终摘要。
5. **权限默认做交集裁剪**：父线程不拥有的工具，子线程不能拿；高风险工具默认不传递；递归派发默认关闭。
6. **并行交给模型，但边界由系统兜住**：让模型判断哪些任务值得并行，同时用预算、权限、返回格式约束住运行时爆炸。
