# Moxt 半年复盘：人和 Agent 组成团队，到底需要什么？拆解

- 原文：https://mp.weixin.qq.com/s/uQePtJ92Qi-r0XZq48NMwg
- 来源：微信公众号「Founder Park」；Moxt 团队供稿
- 获取时间：2026-08-28

## 核心观点

1. Agent 进入团队核心工作，首先受限于共享 Context，而不是单次 Prompt 或模型能力。
2. 知识库必须表达来源、时效、维护责任和事实层级，否则读得到也可能误判。
3. 团队 Agent 应按可长期维护的责任划分，不能把一次性工作都包装成角色。
4. Workflow 的价值是显式责任、交接与异常回退，让人从同步盯过程移到异步审阅和关键判断。
5. 改进是否有效，应以真实后续任务是否少犯同类错验收，而非以规则、角色数量或单次演示衡量。

## 七个分析角度与开头钩子

### 1. Context 从资料堆到信任结构
- “Agent 读不到资料只是表面问题，真正危险的是它读到了过期结论。”
- “知识库越大，为什么 Agent 反而越容易做错决定？”
- “不要再问 Agent 知道多少，先问它凭什么相信这份资料。”

### 2. AI Teammate 的责任边界
- “团队不是缺第十个 Agent，而是缺一个真正负责的角色。”
- “角色拆得越细，为什么团队反而越难用 AI？”
- “AI Teammate 不是功能菜单，而是可长期维护的责任单元。”

### 3. Workflow 取代人工追着交接
- “Agent 变快之后，最先爆炸的常常是人的协调成本。”
- “一条 @ 能串起 Agent，但救不了一个不清晰的交接系统。”
- “自动化不是终点，下一步谁负责才是。”

### 4. 人的参与从同步指导到异步审阅
- “人一直盯着 Agent 做事，效率没有真正释放。”
- “好的 Agent 交付不是连续对话，而是一份可审阅的完整产物。”
- “把人放回判断、品味和验收，才是人机协作的正确分工。”

### 5. 选择高杠杆工作流
- “把 1% 的工作全自动化，不如把 50% 的主链减半。”
- “最酷的自动化，未必是最值得做的自动化。”
- “先改团队时间花得最多的链路，再讨论无人值守。”

### 6. 可信 Context 的生产线
- “代码合并不是终点，它应该更新下一次 Agent 要相信的事实。”
- “没有回写的交付，只是在消耗团队记忆。”
- “让产物成为下一个任务的 Context，才能形成复利。”

### 7. 持续改进的验收标准
- “规则改了不算进化，同类错误不再发生才算。”
- “每次现场教会 Agent，为什么下次它还是会犯错？”
- “别用更多规则掩盖问题，先验证维护成本是否值得。”

## 可执行检查清单

- 标明当前结论、过程草稿、原始事实和失效内容，并定义维护责任。
- 仅为稳定、可评价、可长期维护的责任创建团队 Agent；定期合并重叠角色。
- 为主链任务定义状态、负责人、输入/输出、交接对象、人工决策点与异常回退。
- 优先将高人力占比流程改成“Agent 先交付，人异步审阅”。
- 将问题沉淀为可验证改进项，在下一次真实任务中检查是否复发。
