2026 Agent 年中总结：从整体架构到关键细节

核心结论（一句话）

Agent 系统的重点不是把模型接上工具，而是把模型的动态判断接入有权限边界、有状态恢复和外部验收的执行闭环；Harness、Runtime、业务系统、Workflow、Skill 与评测各有职责，但不必被拆成独立服务。

  • 场景：Agent 产品设计、企业任务自动化、Coding Agent、产研架构评审

知识节点

  • Agent任务循环：Agent 根据工具结果和环境状态决定下一步、补充信息或停止，Workflow 可预先确定其中稳定的路径。
  • 任务适配条件：评估 Agent 场景时检查信息可获得性、工具可用性、结果可验证性和失败可恢复性。
  • Harness控制层：Harness 组织上下文、工具调用、循环控制、暂停恢复、权限检查和运行记录，具体边界随实现而变。
  • Runtime执行环境：Runtime 决定操作在哪个资源环境运行，以及依赖、文件、浏览器和计算资源如何提供。
  • 工具反馈契约：工具定义应让 Agent 能选对能力、传对参数、理解回执，并区分冲突、权限、空结果和超时等错误。
  • 上下文治理：上下文需要明确来源、语义、时效和访问范围，并区分任务进度、业务知识、长期记忆与原始执行记录。
  • Skill业务方法：Skill 把业务阈值、例外、补查条件、证据要求和交接规则沉淀为可复用流程。
  • 任务状态恢复：长任务需记录工作进度与已发生的外部效果，超时或重启后先核实状态再重试。
  • Agent评测闭环：从需求阶段定义任务样例、约束和完成证据，再用追踪、归因、回归和线上失败回流推动改进。

正文要点

  1. Agent 是模型判断与工具执行组成的循环。 搜索不足可补查，数据冲突可核实，满足条件后停止；固定 Workflow 和动态 Agent 可以组合，自主程度应跟随任务需要。
  2. 场景适配要看四个条件。 信息是否取得、工具是否可用、结果是否可验证、失败是否可恢复；资料分散、接口缺失、规则只存在于专家经验中，会增加企业落地成本。
  3. 职责图不是微服务拆分图。 Harness 管执行与控制，Runtime 承载资源和操作，业务系统维护业务事实、事务与权限；任务控制、判断执行、状态资料、观察改进可作为分析视角。
  4. 工具回执必须支撑下一步决策。 模糊描述增加选择成本；只返回失败标记无法恢复。消息版本冲突、权限失效、空查询和超时应提供可区分的结果，并在执行外部动作前绑定并核验用户授权。
  5. 上下文质量不仅是检索。 业务术语、数据口径、隐藏在沟通中的经验、信息新鲜度和可见范围都会影响判断；大数据应由程序过滤聚合，再把结果与出处交给模型。
  6. Skill 记录的是判断方法。 在固定步骤与动态调整之间选择，保存中间产物和依赖关系，使分析师修改一项参数时可以局部重跑，而不是从头执行或只保留最终报告。
  7. 多 Agent 并行需要任务独立和所有权。 委派应明确目标、范围、输入、工具、输出和验收；共享写入需隔离或版本控制，验证者应查实际产物而非只读执行者总结。
  8. 长任务要把进度与业务效果一并保存。 重启、超时或取消后，先检查付款、订单或消息是否已经生效，避免新旧执行者重复写入；本地、云端和沙箱分别对应资源位置与隔离方式。
  9. 评测应从需求开始。 按知识问答、查询、报告和执行等任务定义验收；区分工具成功、任务完成和业务收益，记录 Trace、约束、成本与人工介入，并把线上失败纳入回归。

备注

  • 本文是作者的概念综述和实践总结，并非行业标准或受控架构比较；“四组职责”是分析方式，不要求部署成四个服务。
  • 出海营销 Agent 和咨询分析流程为作者叙述，未提供独立测量数据。142/144 条消息版本、十万行订单是解释冲突与数据处理的示例，不是实测结果。
  • “2025 年是 Agent 元年”是作者的回顾性判断；文中对 MCP、Agent Skills 规范的描述未在本次摄取中独立核验。
