## 核心结论（一句话）

> 将 Agent 的启动改为事件驱动，以统一控制面完成路由、去重、执行与验证，并按风险过滤人工审批，才能把人的注意力留给少数真正需要判断的事项。

## 知识节点（9 个独立概念）

- **事件驱动触发**：定时轮询或 Webhook 将外部变化转成 Agent 任务入口，减少对人工逐条启动的依赖。
- **统一事件格式**：用来源、类型、对象、摘要和原处链接描述事件，让不同系统接入后可由同一套规则处理。
- **规则路由**：按事件属性配置执行 Agent、模型、工作目录、Skill、并发数和通知条件，使路由能独立于执行器调整。
- **长轮询接单**：由内网执行机器主动向中台轮询领取任务，避免要求中台直接连入不可公网访问的设备。
- **任务去重**：识别重复投递或同一事项的连续更新，避免多个执行器对同一目标并发产生冲突副作用。
- **模型与 Skill 分工**：按任务能力选择模型，以可维护的 Skill 固化流程、规则和参考资料。
- **CI 五阶段**：将只读审查、隔离检查、受保护合并、隔离发布和线上版本核实串成完整交付链。
- **风险分级审批**：低风险工作可自动继续；删除、支付、停服、密钥、权限和对外表达等高影响动作升级给人。
- **决策记忆**：记录已批准和已拒绝的决定及其原话、日期，减少重复询问并保留决策依据。

## 正文要点

1. **把任务起点从人移到事件。** 作者将聊天窗口式使用视为注意力瓶颈，尝试以定时任务、Webhook 和外部信号触发执行，让人不必逐个启动每项工作。
2. **由中台统一接入和派发。** 事件被压缩成稳定字段，再按 rules.json 选择模型、Agent、Skill、工作目录、并发度和通知策略；本地接单器长轮询领取任务，事件记录则用于追踪来源、执行与结果。
3. **模型负责执行，Skill 固化 SOP。** 作者按开发、运维和浏览器操作分配不同模型，并把任务细节沉淀到专属 Skill；执行端保留在可访问本地代码、账号和设备的机器上。
4. **CI 把 Agent 的提交与线上交付隔离。** 文章描述的五步是审查、检查、合并、发布、核实。审查只读且最多三轮；检查和发布在临时虚拟机中运行；合并受 GitHub 规则约束，最后查询线上版本确认交付。
5. **只在高影响决策上打断人。** 删除数据、停服、花钱、外发消息、产品方向、密钥和权限变更等事项需要确认。既有决定与“不做”事项被记录；产品反馈则由作者亲自筛选后再交给 Agent。
6. **记录与可视化服务于持续调度。** 中台保留事件、执行器、结论及会话链接，作者再用仪表盘观察任务流；这些数据可辅助调整规则，但不自动证明系统安全或效果可外推。

## 证据与限制

- 本文是作者对近一年个人与公司实践的经验分享，不是独立评测。文中 298 个合并请求、333 条审查问题、306 条修复、51 条最高级别问题，以及审查/上线耗时和成本均按作者口径记录，未独立审计。
- “3 到 5 个会话”的说法归于文中引用的 DeepSeek 文章；朱元璋奏折故事亦为作者的历史类比，本条目未另行核实。模型名称、订阅价格和服务能力会随时间变化。
- 观察到的效率可能同时来自作者单人负责、统一技术栈、较高的业务熟悉度和专用设备，并不能单独归因于自动化中台。文中未充分说明队列认证、密钥隔离、Webhook 验签、故障恢复和回滚实现。
- 本地执行能减少凭证复制和跨境网络依赖，但也让持有浏览器登录态、发布权限与代码的设备成为高价值边界；临时虚拟机、最小权限、审计和对账不可省略。
