AI时代-软件的终局

核心结论（一句话）

作者提出，AI时代的软件可能从预设界面和业务烟囱转向以对象语义、可复用能力和受治理Agent为核心；这是趋势判断，不是已证实的行业终局。

知识节点（8 个独立概念）

  • GUI价值迁移：当采集和调用自动化后，界面可从重复录入转向异常处理、结果审计和人工接管。
  • 无预设UI：界面可按当前意图和权限临时生成，而非为每条路径预先开发固定页面。
  • 对象中心契约：Agent 可面向完整业务对象及其语义操作，底层再按访问模式选择不同存储结构。
  • 能力层与编排层：能力层提供可复用 API 或 Skills，编排层按意图与场景组合这些能力。
  • 技能复利闭环：重复需求调用已有技能，新需求生成能力并验证，合格后沉淀为后续可复用资产。
  • 受治理的自进化Agent：Agent 可持续扩展能力，但每次进化都需评测、权限检查、灰度、回滚和审计。
  • 本体模型层：本体把业务对象、关系、规则、约束和动作表达为供 Agent 推理与执行的领域语义模型。
  • 统一语义契约：跨系统能力只有共享对象与规则含义，才能从“接口可调用”推进到“业务可编排”。

正文要点

  1. 作者把AI视为软件形态变化的驱动，而非传统软件的简单增强。 RPA 和 Computer Use 被作者判断为兼容存量系统的过渡方式；这属于作者对技术路线的预测。
  2. UI从主操作路径转为人的控制与兜底面。 采集、查询和调用若可自动完成，固定录入与查询页面的比重可能下降；异常处理、审批、审计和人工介入仍需要界面。
  3. “无预设UI”意味着按任务生成临时交互层，不意味着没有交互。 作者认为底层 API 契约严格时，呈现布局可以动态变化而不改变业务动作语义；这一前提仍需通过权限、可访问性和结果校验验证。
  4. 作者提出从“对象到表再映射回来”转向对象中心的数据契约。 物理层可以按事务、分析等负载采用不同存储；高频事务的强一致、低延迟与分析吞吐要求仍然存在，文章并未论证应移除结构化数据库。
  5. 软件可能由一次性交付物变成“稳定内核 + 技能资产 + 生成器 + 运行反馈”。 高频需求优先复用技能，空缺能力可动态生成，验证通过后再沉淀；否则动态生成只会增加不可重复和不可控的成本。
  6. Agent 架构被概括为能力层和意图编排层。 存量系统需抽取并封装能力；跨能力协作仍依赖统一术语、主数据和规则，可靠流程应将成熟经验固化为 Workflow，而不是每次自由发挥。
  7. 本体模型被描述为可操作的业务语义层。 它不只是静态对象图，还要表达行为、规则、约束与场景经验，并与 Skills/API 契约相连，减少“有接口但不懂业务”的错用。
  8. 文章把成败条件归纳为能力原子化、语义统一和治理内建。 这是文章的架构主张；是否成立需由具体业务中的端到端成功率、人工接管、错误恢复、成本和审计结果验证。

机制解释

当数据可机器读取、动作可经稳定 API 执行时，固定表单的重复操作价值可能降低；而当 Agent 要跨能力完成任务，语义契约帮助解释对象和规则，复用技能减少重复生成，治理则限制新能力造成的副作用。界面因而可能从操作入口转向授权、异常处置与结果核验。

替代解释与适用限制

  • 预设 UI 对审计、可访问性、精确编辑、低延迟和人工控制仍有价值；动态界面也带来一致性、权限呈现与可测试性成本。
  • 关系型数据库的事务、一致性、约束与成熟运维仍重要。Agent 可以在现有系统之上使用对象语义层和 API，而不必取代底层存储。
  • API 或 MCP 暴露能力并不自动带来统一语义；主数据、权限、状态、规则版本、失败补偿和责任归属仍须明确建模。
  • 文中关于“软件/IT咨询进入夕阳期”的判断，以及埃森哲拟退出大中华区这一背景，本条未独立核验；单一企业动向不足以证明全行业的长期就业趋势。
  • “软件终局”是作者的方向性观点。文章未提供生产系统、对照实验、行业样本、迁移成本或效果指标，不能据此直接决定企业架构迁移。

最小验证路径（编者推导）

选择一个重复、低风险且可回滚的业务任务，盘点真实对象、数据源、规则、权限和完成证据；只暴露最小 API/Skill，再比较原有 UI/Workflow 与 Agent 编排在任务完成率、人工介入、错误恢复、耗时和总成本上的表现。通过评测、审计与回滚门槛后再扩大范围，不从“软件终局”口号直接推导全量替换。
