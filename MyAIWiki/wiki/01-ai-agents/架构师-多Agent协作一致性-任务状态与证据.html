核心结论（一句话）

多 Agent 系统真正要对齐的不是最终答案，而是同一个任务、同一份事实和同一套状态；模型负责判断下一步，运行时负责证明版本、证据、副作用和完成条件确实成立。

知识节点（10 个独立概念）

  • 一致性三件事：多 Agent 应对齐任务身份、事实依据和状态推进，而不是被迫输出相同观点。
  • 任务边界与并行：能否并行由任务依赖决定，如何并行由调度器、身份和动态任务图保证。
  • 可执行交接状态：下游需要版本快照、证据、假设、权限、产物和验收条件，而不是一句自然语言结论。
  • 权威事实：聊天是历史、摘要是工作集，代码库、测试、部署和业务数据库才可能是事实来源。
  • 版本化任务状态：全局任务、子任务、Agent、尝试次数、版本、租约和结果引用要能被运行时追踪。
  • 结果契约：不同 Agent 的输出要有统一结构、来源和状态，区分候选、已验证、冲突和已否决。
  • 验收证据：完成必须绑定 commit、命令、退出码、报告和审查结果，不能由 Agent 自报完成。
  • 局部重试与幂等：失败优先在子任务层恢复，副作用动作需幂等键、远端查询和安全重放条件。
  • 租约与接管：任务认领用租约和心跳控制，过期后才允许接管，避免旧执行者与新执行者并发操作。
  • Harness 运行时：Harness 提供工作集、动作边界、真实记录和失败恢复，把模型判断接入可控系统。

正文要点

  1. 多 Agent 角色图并不能证明架构成立；围绕同一个 user-service 故障追问代码版本、日志版本、事实与判断、验收版本，才能暴露一致性空白。
  2. 并行的前提是任务依赖清楚。任务可以并行不代表编排可以静态固定，执行中的新证据可能要求暂停、合并、收回或重新拆分。
  3. Agent 交接应传递可继续工作的状态：输入快照、证据引用、假设、能力约束、产物地址和验收标准必须分开表达。
  4. 结果冲突本身有价值，危险的是不同 commit、时间窗口或配置被系统当成同一现实；结果契约应保留来源和状态。
  5. 超时不能一律重试。查询可重试，写入、发布、扣款等副作用必须先查远端状态，区分未执行、已执行和状态未知。
  6. 全局失败不能掩盖子任务状态；租约、心跳、attempt、version、幂等键和补偿流程共同构成可恢复运行时。
  7. 多 Agent 没有绕开分布式系统老问题，只是把服务和线程换成了会自主判断的执行者，因此模型判断与运行时证明必须分层。
