# 工厂工程师,不是产品工程师 — Warp 创始人 Zach Lloyd 内部备忘录编译

- **原始作者**:Zach Lloyd(Warp 终端创始人,前 Google Docs 首席工程师)
- **编译来源**:微信公众号「深思 SenseAI」2026-06

## 核心结论(一句话)

> **"工程师的活,从造车变成了造工厂"** — Warp 创始人 Zach Lloyd 宣布团队从"产品工程师"升级为"工厂工程师";**成功 = 工厂效率 ≈ 出货产品 / (推理成本 + 人的时间成本)**;**人在环里 = 需要复盘的失败**;8 步流水线 + **递归自我改进** = 黄金路径。深思圈主编反对无脑造工厂,主张**看任务分工** — 工厂自动化"怎么做",人攥"做什么"和"为什么"。

- **场景**:大厂 AI Coding 1.0 → 2.0 范式迁移的"工程师角色重定义"反思
- **类型**:内部备忘录编译 + 行业反思(非工程方法论、非行业宏观战略)
- **关键证据**:Warp 6 万星开源仓库的 Oz 工厂平台 + 1300 个"可实现"待办 + 工厂效率公式

## 知识节点(8 个)

- **工厂工程师思维**:从"造车"到"造造车的工厂";"成功" = 工厂效率 = 出货产品 / (推理成本 + 人的时间成本);不再看你交付多少功能(失败指标),而看"全自动"发出去的比例 + 花了多少钱
- **COGS 重定义**:软件生产从 R&D(固定研发开支)→ COGS(可变成本);老板像盯工厂良率一样盯;"给所有工程师无限 token 预算、去玩交互式 agent 的日子,要结束了"
- **人在环里=失败**:"以后你每用一次'人在环里'的 agent 去写代码,都要把它当成一次需要复盘的失败";**人在公式分母里,是要被往下压的成本**
- **八步流水线**:分诊 agent → spec agent → 实现 agent → code review agent → 验证 agent(computer-use)→ 人审 → CI/CD → 监控 agent(闭环);已在 Warp 6 万星开源仓库跑起,自评"半成品"
- **递归自我改进**:每次人不得不介入,平台 Oz 记下 → "自我改进 agent" 优化 → 争取下次人不必介入;agent 扫所有工厂对话找浪费 token;**黄金路径 = 工厂进入"递归自我改进"**
- **Bakaus vs Lloyd 两极**:同一个月(2026-05/06)两个创始人完全相反 — Paul Bakaus(设计工具)"别把人推出循环,人留最后 20%" vs Zach Lloyd(Warp)"人在环里=失败";两人都卖自己的东西(Bakaus 卖品味工具,Lloyd 卖工厂平台 Oz)
- **做什么 vs 怎么做**:深思圈主编的中间路线 — **能被机器校验对错的活(怎么做:实现/验证/监控)→ 工厂(Lloyd 对)**,**靠判断定生死的活(做什么:做哪个/产品观点/为什么)→ 留住人(Bakaus 对)**;工厂自动化"怎么做",**人依然攥"做什么"和"为什么"**
- **1300 待办反思**:Lloyd 说"看着面板上 1300 个'可实现'状态的 issue,让 agent 去实现啊";深思圈补刀:真正问题不是"谁来实现"而是"哪些根本不该做" → **无脑地、更快地造更多,从来不是战略**

### 正文要点(3 段)

**1. 范式迁移**:过去 1 年从"AI 自动补全"走到"交互式编码 agent";接下来 6 个月范式再变一次 → "**自动化开发**";工程师从"直接做产品"变成"造一个做产品的东西";成功定义当场颠倒:**不再看你交付多少功能(失败指标),而是看"全自动"发出去的比例 + 花了多少钱**

**2. 工厂效率公式**:工厂效率 ≈ 出货产品 / (推理成本 + **人的时间成本**);软件生产从 R&D → **可变成本(COGS)**;老板像盯工厂良率一样盯:**"我多投一块钱在自动化上,业务能不能多赚回超过一块钱"**;分母里"人的时间"是要被往下压的成本

**3. 8 步流水线 + 递归自我改进**:分诊 → spec → 实现 → review → 验证(computer-use)→ 人审 → CI/CD → 监控(闭环);每次人介入,平台 Oz 记下 → **自我改进 agent 优化** → 争取下次人不必介入 → **黄金路径 = 递归自我改进**

### 5 个对 Seetong 团队可借鉴动作

1. **COGS 视角体检**:Seetong AI Coding 算"研发开支"还是"可变成本"?**把"AI Coding 投入产出比"作为最高级指标**
2. **1300 待办反思**:Seetong TAPD 几百个"待实现"需求里,真正"该做"的占多少?**先盘"不该做"的,再谈"谁能做"**
3. **做什么 vs 怎么做的边界**:①"怎么做"(需求明确后实现/测试/Review/部署)→ 工厂化 ②"做什么"(该不该做/优先级/方向)→ 留住人
4. **递归自我改进雏形**:Seetong 跑分失败 → 沉淀为 Skill 约束 → 下次自动跑(对照 [[02-ai-coding/面向Skills编程-淘宝企业购端到端研发提效实践]] ADJUSTMENT_PLAN);不要每次都"人在环里"修同类问题
5. **人在环里 = 失败的纪律**:经常介入同一类问题,**优先补 Skill 约束或自动化工具**,而不是让人继续"复盘"
