# AI Wiki Schema

这是 AI Wiki 的维护规则。AI（Claude Code / Codex 等）在处理知识库时必须遵循这些规则。

> **设计哲学（2026-06 升级）**：参考 LLM-Wiki Skill 的核心方法论——**用结构化存储降低输入成本，用 grep 命令式查询降低输出成本**。
> - **输入端**：每篇文章拆出独立"知识节点"+ `frontmatter` 元数据
> - **输出端**：基于 ripgrep 的轻量查询，绕开意图识别
> - **关联**：节点间显式声明关系，形成可 grep 的图谱

---

## 核心原则

1. **AI 写 wiki，人类读 wiki** - AI 负责所有维护工作，人类只做高价值决策
2. **持久复合** - wiki 是累积的产物，不是每次重新发现知识
3. **透明可追踪** - 所有变更记录到 log.md
4. **结构化优先**（新规则） - 知识必须拆成可独立检索的"节点"，而不是堆在一篇文章里
5. **查询低成本**（新规则） - 不依赖 LLM 意图识别，靠 grep / ripgrep 完成检索

## 操作规则

### Ingest（摄取新来源）

当用户发来文章链接时，执行以下步骤：

1. **保存原文** → `raw/{slug}.md`
   - 包含原文链接、作者、日期、完整正文
   - 底部添加标签行：`标签： #主题/xxx #手法/xxx #场景/xxx`

2. **生成拆解** → `raw/{slug}-digest.md`
   - 核心观点（3-5 个）
   - 7 个分析角度，每个角度配 3 个开头钩子（共 21 个钩子）

3. **编译 wiki** → `wiki/{分类}/{slug}.md`（**遵循新模板，见下方**）
   - **新文章必须**带 YAML `frontmatter`（tags / nodes / links / category / date）
   - 结构：核心结论 → 分类提炼 → **知识节点** → **关联图谱** → 相关链接
   - 简洁，移除冗余描述

4. **更新索引** → `wiki/{分类}/index.md` 和 `wiki/master-index.md`

5. **记录日志** → `wiki/log.md`

### 摄取状态与发布门禁

- 新摄取遵循 `fetched -> drafted -> polished -> validated -> published`；状态元数据存于 `.wiki-state/ingests/`，不保存正文、Cookie 或凭据。
- `drafted` 页面不得更新分类索引、总索引或日志；只有包含完整 frontmatter、至少一个真实内链与三段关联图谱的 `published` 页面才可发布。
- `raw/{slug}.md` 必须保存完整正文、抓取方式与正文 SHA-256。空正文、`环境异常` 或其他抓取失败不得写入正式产物。

### Query（查询知识库）

> **新规则（2026-06）**：优先用 `wiki-query` 脚本做命令式查询，**只有在 grep 收窄后仍不足时才用 LLM 总结**。

**轻量查询流程**（推荐）：
```bash
# 1. 按标签/节点 grep
python3 scripts/wiki-query.py node "LLM-Wiki"
python3 scripts/wiki-query.py tag "#主题/AI-Agent"
python3 scripts/wiki-query.py text "知识库"

# 2. 多轮收窄（主题 → 标签 → 文章）
python3 scripts/theme-search.py "知识工作者编排 Agent"
```

**重查询流程**（必要时）：
1. 读 `wiki/master-index.md` 找到相关目录
2. 读对应 `index.md` 找到相关页面
3. 综合多个页面的内容回答
4. **好的答案必须归档回 wiki**（作为新页面或现有页面的更新）

### Lint（健康检查）

每月底执行一次：

```bash
python3 scripts/wiki-health-check.py

# 检查单篇待发布条目
python3 scripts/wiki-health-check.py --scope "{slug}"

# 仅修复唯一匹配的链接别名，并补齐索引入口
python3 scripts/wiki-health-check.py --fix-link-aliases --fix-indexes

# 检查 raw 归档是否出现日期目录、articles/ 或日期前缀文件名
python3 scripts/normalize_raw_archive.py --check
```

```
Read every file in wiki/. Find:
- contradictions between pages（页面间矛盾）
- orphan pages with no inbound links（孤立页面）
- concepts mentioned but lacking dedicated pages（提到但无专属页的概念）
- stale claims superseded by newer sources（过时声明）
- 知识节点未关联：每篇文章的 nodes 至少要有 1 个 inbound 链接
- frontmatter 缺失：新文章必须带 YAML 头

Write health report to wiki/lint-report-YYYY-MM.md
```

### Wiki 页面结构（**新模板，2026-06 起生效**）

```markdown
---
title: 文章标题
category: 02-ai-coding
tags:

nodes: [LLM-Wiki, Codex, 知识工作者, 工作流编排]
links: [[Codex才是最适合普通人的顶级牛马-Agent]], [[AI-Coding的顿悟时刻]]
date: 2026-06-04
source: 微信公众号 / 智见AI
---

# 文章标题

- 原文链接：https://...
- 来源：...
- 获取时间：YYYY-MM-DD

## 核心结论（一句话）

...

## 分类提炼
- 场景：
- 标签：
- 类型：

## 知识节点（5-10 个独立概念）  ← 【重命名】原来是"要点列表"

- **节点 1**：一句话定义这个概念
- **节点 2**：一句话定义这个概念
- **节点 3**：一句话定义这个概念

> 节点原则：每条**独立成段可理解**，**对应一个 grep 关键词**，**不与同篇其他节点重叠**

## 关联图谱 ← 【新增】

### 上游（基于 / 来自）
- [[上游文章1]]：本文的哪些节点基于它
- [[上游文章2]]：...

### 下游（应用于 / 验证于）
- [[下游文章1]]：本文的哪些节点被它应用
- [[下游文章2]]：...

### 同级（横向 / 并列）
- [[同级文章1]]：哪些节点是同一主题的不同视角
- [[同级文章2]]：...

## 正文要点（3-7 条）

## 相关链接
```

> **老文章处理**：133 篇存量文章**不强制升级**，但 lint 报告会标记"缺 frontmatter / 缺关联图谱"。

### 知识节点提取规范（**新规则**）

**什么是合格的"知识节点"**：
- ✅ 独立成段可被理解（不依赖本文其他段落）
- ✅ 对应一个可 grep 的关键词（建议中文 2-6 字 / 英文 1-3 词）
- ✅ 不与同篇其他节点语义重叠
- ✅ 至少被 1 篇文章 inbound 引用（否则是孤立节点）

**反例**（不能作为节点）：
- ❌ "Codex 是 OpenAI 的编程工具" — 太宽泛，是定义不是节点
- ❌ "Harness 层" — 没具体含义，需要更细的拆解
- ❌ 长句子（超过 30 字）— 应该拆成多个节点

### Frontmatter 规范

| 字段 | 必填 | 说明 |
|------|------|------|
| `title` | ✅ | 文章标题 |
| `category` | ✅ | 分类目录（01-ai-agents / 02-ai-coding ...） |
| `tags` | ✅ | 标签数组 |
| `nodes` | ✅ | 知识节点数组（5-10 个） |
| `links` | ⚠️ | 至少 1 个内链（推荐 3+） |
| `date` | ✅ | 写入日期 YYYY-MM-DD |
| `source` | ⚠️ | 原始来源 |

### 命名规范

- 统一用 `-` 连字符
- 英文小写，中文保持原样
- `digest` 后缀表示拆解版
- `_v1` / `_v2` 表示版本

### 标签体系

- YAML frontmatter 的 `tags` 值不带 `#`，例如 `主题/AI-Coding`。
- 正文中的 Obsidian 标签必须位于行首或空白字符之后，例如 `标签： #主题/AI-Coding`；不要写成 `标签：#主题/AI-Coding`。

**按主题**：`#主题/AI-Agent` `#主题/APP研发` `#主题/AI-Coding` `#主题/内容创作` `#主题/效率`

**按手法**：`#手法/焦虑共鸣` `#手法/对比冲突` `#手法/好奇心循环` `#手法/权威背书`

**按场景**：`#场景/知识付费` `#场景/技术博客` `#场景/公众号长文` `#场景/产品介绍`

**按节点主题**（**新体系**）：`#节点/LLM-Wiki` `#节点/Codex` `#节点/Harness` `#节点/Context-Engineering` `#节点/Memory` `#节点/Skill` `#节点/Agent-Loop`

## 工具建议

### 输入端
- **Obsidian Web Clipper**：网页 → markdown
- **Claude / Codex**：文章 → 结构化知识节点

### 输出端（**新建议**）
- **`scripts/wiki-query.py`**：基于 ripgrep 的标签/节点/全文查询（**最常用**）
- **`scripts/theme-search.py`**：主题 → 多轮 ripgrep 收窄 → 文章列表
- **`scripts/theme-merge.py`**：基于多篇文章融合生成新内容
- **`scripts/morning-digest.py`**：每日发芽报告（已升级支持节点融合）
- **Obsidian 反链视图**：浏览关联图谱

### 高级（可选）
- **qmd**：本地搜索（BM25 + 向量 + LLM 重排）
- **Git**：版本历史、分支、协作
- **Marp**：生成幻灯片
- **Dataview**：基于 frontmatter 的复杂查询
